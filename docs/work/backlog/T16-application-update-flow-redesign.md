# T16：应用更新链路重设计

> 更新时间：2026-08-28
> 状态：✅ 开发完成，待真实安装包验收
> 优先级：P1

## 1. 背景与问题

d2-tools 最终以 Windows `exe` 安装包发布。当前应用更新已经接入 `electron-updater`、主进程 IPC 和后台任务，但更新状态、后台任务状态和设置页操作没有形成一条完整的用户链路。

当前链路为：

```text
应用启动 → 延迟检查 → 主进程 updates IPC → electron-updater
  → updates:status 事件 → Renderer Hook → 顶部版本状态 → 设置页操作
```

需要解决的问题：

- `updates:check` 和 `updates:download` 可能在后台任务真正开始前返回旧快照，Renderer 会短暂显示错误状态。
- `AppUpdateSnapshot` 与 `BackgroundTaskSnapshot` 没有统一操作 ID、重试信息和错误归属。
- 后台任务切换菜单后仍会运行，但没有共享任务 Dock，用户只能进入设置诊断查看。
- 检查、下载缺少统一互斥控制，不能明确阻止冲突操作。
- “重启并安装”没有共享确认弹窗，也没有和 runtime shutdown / `before-quit` 建立明确顺序。
- 更新状态只保存在主进程内存，应用重启后不能可靠恢复“已下载、待重启安装”。
- 国内网络只能通过环境变量配置 Feed，手动下载页仍固定指向 GitHub，缺少稳定的官方源 / 国内镜像回退策略。
- 当前 Windows 发布可以不依赖代码签名；签名属于可选的后续安全增强，不阻断自动下载和手动重启安装链路。

## 2. 范围

### 包含

- Windows 应用 `exe` 的检查、下载、待安装、重启安装和失败恢复。
- 主进程更新协调器、IPC 契约、事件广播和最小状态持久化。
- 共享 Shell 更新状态、右下角后台任务 Dock 和设置页更新工作区。
- 官方更新源、国内 CDN / 镜像源和手动下载回退。
- 更新操作的键盘焦点、确认弹窗、响应式布局和无障碍状态表达。
- 更新相关的行为、架构、发布和视觉验收。

### 不包含

- Bungie 资料库更新业务逻辑；资料库更新继续由 Manifest IPC 和独立后台任务负责。
- 账号刷新、商人刷新、首页简报等业务数据刷新。
- 自动强制重启、静默安装或跳过用户确认的写入操作。
- 移动端原生安装器；未来其他平台应复用状态模型，但不能假设 Windows 安装行为。

## 3. 设计原则

1. 主进程是应用更新唯一事实源，Renderer 只显示、发命令和订阅事件。
2. 更新业务状态与后台任务执行状态分层建模，不用一个枚举承载两类语义。
3. 更新下载不阻断页面使用，不因切换菜单或卸载页面而中断。
4. 顶部 Shell 只提示事件并跳转设置，不直接执行下载或重启。
5. 每个状态只突出一个主操作；错误状态必须允许继续使用当前版本。
6. 长任务使用事件驱动更新，不由页面轮询主进程状态。
7. 自动更新优先使用可验证的签名安装包；未签名包仍可发布和自动下载，下载完成后由用户确认手动重启安装。
8. 所有更新界面使用稳定布局、容器流式排版、明确焦点和模态焦点陷阱，不依赖固定像素位置。

## 4. 目标状态模型

保留现有传输层状态名称，降低迁移成本：

| 状态 | 用户含义 | 主操作 |
|---|---|---|
| `idle` | 尚未检查 | 检查更新 |
| `checking` | 正在检查 | 等待，不允许重复检查 |
| `not_available` | 当前已是最新版本 | 检查更新 |
| `available` | 发现新版本 | 下载更新 |
| `downloading` | 正在下载 | 查看进度 |
| `downloaded` | 已下载，等待重启 | 重启并安装 |
| `error` | 检查或下载失败 | 重试 / 打开下载页 |

快照补充以下元数据：

```ts
type AppUpdateSnapshot = {
  status: AppUpdateStatus;
  operation_id?: string;
  current_version: string;
  available_version?: string;
  downloaded_version?: string;
  progress_percent?: number;
  update_source_label: string;
  retrying: boolean;
  next_retry_at?: string;
  last_error?: string;
  restart_required: boolean;
  last_checked_at?: string;
};
```

`retrying`、`next_retry_at` 属于检查任务的重试信息，不新增大量 UI 状态枚举。`downloaded` 在用户界面统一显示为“待重启安装”。

## 5. 目标用户链路

```text
应用启动
  ↓（启动完成后延迟 8～10 秒，按检查节流策略）
checking
  ├─ 当前已是最新 → not_available
  ├─ 发现新版本   → available
  └─ 网络失败     → error + 后台重试

available
  ↓ 用户点击“下载更新”
downloading
  ├─ 下载成功 → downloaded
  └─ 下载失败 → error

downloaded
  ↓ 用户确认“重启并安装”
安全关闭运行时
  ↓
electron-updater.quitAndInstall()
  ↓
应用重启后核对当前版本并清理待安装状态
```

触发策略：

- 启动后自动检查一次；本地保存最近检查时间，避免短时间重复检查。
- 应用从后台恢复且超过设定间隔时允许再次检查。
- 设置页“检查更新”始终强制检查。
- 发现新版后不自动下载，避免未经确认占用网络。
- 检查失败后台重试；下载失败显示明确的“重试”，不无限自动下载。
- 已下载版本不因切换菜单、关闭设置页或重新挂载页面而丢失。

## 6. UI 设计

### 6.1 顶部 Shell

更新项固定在版本位置，不因状态变化而重新排序：

| 状态 | 顶部短文案 | 权重 |
|---|---|---|
| `idle` | 版本 vX.Y.Z | `quiet` |
| `checking` | 正在检查 | `standard` |
| `not_available` | 版本 vX.Y.Z | `quiet` |
| `available` | 新版本 vY.Z | `attention` |
| `downloading` | 下载 vY.Z · 42% | `attention` |
| `downloaded` | 待重启安装 vY.Z | `critical` |
| `error` | 更新失败 | `attention` |

顶部更新项只执行“打开设置并聚焦到应用更新区域”，不直接下载和重启。

### 6.2 设置页

不新增独立的更新页面，继续放在：

```text
设置 → 概览 → 应用更新
```

现有五个并列按钮改为状态驱动的单主操作布局：

| 状态 | 主按钮 | 次要入口 |
|---|---|---|
| 尚未检查 | 检查更新 | — |
| 检查中 | 无 | — |
| 已是最新 | 检查更新 | — |
| 发现新版本 | 下载更新 | 打开下载页 |
| 下载中 | 无 | 打开下载页 |
| 已下载 | 重启并安装 | 稍后处理 |
| 失败 | 重试 | 打开下载页、复制诊断 |

更新工作区按“当前版本 → 目标版本 → 状态说明 → 主操作 → 辅助入口”排列。宽屏使用双列信息区，`980px` 以下改为单列，`760px` 以下按钮铺满可用宽度。

### 6.3 重启确认

“重启并安装”必须打开共享确认弹窗：

> 更新已准备完成。将关闭 d2-tools 并安装 vX.Y.Z，完成后应用会自动重新打开。

要求：

- 初始焦点落在安全取消操作。
- `Escape` 等同取消。
- `Tab / Shift+Tab` 不得离开弹窗。
- 确认后才进入 runtime shutdown 和安装流程。
- 有未保存配置或未提交编辑时，先经过现有离开保护。

### 6.4 后台任务 Dock

共享 Shell 右下角只显示活跃或失败的更新任务：

```text
应用更新
下载中 · 42%
[查看]
```

成功任务不常驻，不遮挡主内容。点击“查看”进入设置页更新区域；设置页诊断保留完整任务详情、重试次数和技术错误。

## 7. 技术实现切片

### T16.1 更新协调器

状态：✅ 第一轮落地

- 新增主进程 `AppUpdateCoordinator`，集中管理检查、下载、安装和操作互斥。
- 检查和下载命令在状态切换后返回最新权威快照，不返回旧内存值。
- 所有事件携带 `operation_id`，旧请求不能覆盖新请求。
- 使用明确的 `dedupeKey`，同一时刻只允许一个检查和一个下载操作。

### T16.2 状态持久化与恢复

状态：✅ 第一轮落地（最小状态文件恢复；需真实安装包确认 updater 缓存行为）

- 在应用数据目录保存最小更新状态，不保存 Token、Cookie 或完整诊断。
- 应用启动时恢复可用的 `downloaded` 状态，并核对 updater 缓存。
- 安装完成后核对当前版本，清理旧的待安装状态。
- 更新失败保留当前可用版本，不删除旧安装包或破坏现有运行环境。

### T16.3 Renderer 状态订阅

状态：✅ 第一轮落地

- 将更新状态提升为全局 Renderer Store。
- Shell、后台任务 Dock、设置页共享同一份状态。
- 设置页 Hook 不再独占更新生命周期。
- 视觉模拟状态只作为开发环境 adapter，不改变正式 IPC 契约。

### T16.4 安装退出协调

状态：✅ 第一轮落地

- 增加 `updateInstallRequested` 生命周期标记。
- 安装确认后停止新的高风险写操作，等待 runtime coordinator 安全关闭。
- 关闭流程完成后再调用 `quitAndInstall()`。
- 普通关闭窗口仍沿用现有导航保护和 `before-quit` 行为。

### T16.5 更新源

状态：✅ 第一轮落地（官方源失败后切换配置镜像 Feed，并支持镜像下载页）

- 默认使用官方 GitHub Release。
- 官方源失败时切换到配置的稳定国内 CDN / OSS Feed。
- 手动下载页也必须根据当前源提供可用地址，不固定只打开 GitHub。
- UI 只显示“官方更新源 / 国内镜像”，不要求普通玩家填写 URL。
- 诊断中记录实际使用的源和失败原因。

### T16.6 发布安全

状态：✅ 第一轮落地（签名可选；Release workflow 校验安装器、latest.yml 和 blockmap 元数据）

- Windows 安装包预留代码签名配置，但不把证书作为发布前置条件。
- CI 检查 `latest.yml`、安装器和 blockmap 的对应关系。
- 未签名包仍允许自动下载；下载完成后必须由用户确认重启安装。
- 继续保持版本号、tag、安装包和 updater 元数据一致。

## 8. 验收标准

### 功能

- 启动后自动检查不会阻塞首页、账号和资料库使用。
- 手动检查、下载和安装操作不会重复启动并发任务。
- 检查失败会显示可理解原因，并按策略后台重试。
- 下载进度跨菜单保持，设置页重新打开后状态不丢失。
- 下载完成后明确显示“待重启安装”，不会自动重启。
- 重启安装前有确认弹窗，取消后焦点回到原按钮。
- 安装退出与 runtime coordinator 正确协作。
- 官方源失败时可以使用稳定镜像或手动下载。
- 更新失败时当前版本仍可继续使用。

### UI / 交互

- 顶部状态项位置稳定，状态不依赖颜色单独表达。
- 设置页每种状态最多一个主操作。
- `1280 / 980 / 760` 宽度下无按钮溢出、文字裁切或嵌套滚动冲突。
- 键盘可完成检查、下载、打开下载页和安装确认。
- 窄屏状态入口显示待处理数量，展开后保持固定顺序。
- 后台任务 Dock 不遮挡主内容，点击可稳定回到更新区域。

### 验证

- 行为测试覆盖状态机、重试、去重、持久化恢复和安装退出顺序。
- 架构测试确保 Renderer 不直接控制 `electron-updater`。
- 视觉测试覆盖 `idle / checking / available / downloading / downloaded / error`。
- Release CI 验证 Windows 安装包、`latest.yml`、blockmap 和版本一致性；代码签名作为可选发布增强。
- 使用真实安装包至少验证一次“检查 → 下载 → 重启安装 → 版本核对”。

## 9. 暂不推进

- 自动静默下载全部版本。
- 自动强制重启。
- 应用内展示完整更新日志；更新说明继续由 Release 页面承载。
- 多更新通道 UI（stable / beta / nightly）。如果未来需要，先扩展发布策略和配置合同，再增加设置项。
