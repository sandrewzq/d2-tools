## 〇之二、实窗复验「无法切换啊」的成因与修法（2026-09-18）

用户装完新构建后报：推荐区里点开一件本件拥有的 Perk，浮层里**没有「选择」**，换不了 Perk。

**不是推荐区接错了线，是闸门从来没开**。整条链的判据是

```
推荐区「选择」← candidate.canApply ← 配置列.can_apply
配置列可点    ← canWriteConfiguration ← 同一批 can_apply
写面板出现    ← 同一批 can_apply
```

`can_apply` 唯一出自 `buildSelectionColumns`（`buildWeaponDetailView.ts:525` 起），而它当时写的是
`socket?.is_enabled === true && reusablePlug?.can_insert === true && …`。打开详情时 `sockets` **不是**
游戏返回的插槽数据，是 `buildPreviewSocketsFromWeaponRoll`（`packages/app/src/workspaces/itemDetail.ts:253`）
用账号快照（`weapon_roll`）搭的近似值——快照只有「拥有哪些插件、当前装的是哪个」，
插槽可不可用 / 能不能插它并不知道，那三项被那一步统一占位成 `false`。
占位被当事实读，于是**整件武器在读完完整 Roll 之前一律不可切换**；而完整 Roll 只在用户点
「查看完整掉落池」时才读（T71 已定的口径）。表现就是：推荐区、本件 Roll、写面板三处一起哑掉，
用户看到的正是「无法切换」。

验证（临时脚手架 `packages/desktop/test/t73-scratch-swap-gate.test.ts`，走真路径
`createSelectedItemPreview` → `mergeSelectedItemDetail` → `buildWeaponDetailView`，用完即删）：
同一件武器、同一个槽位，`requirement_slot` 正常解析成 `magazine`，但快照状态下
`精确弹药 false / 轻质弹匣 false`——两个都不是可切换项，`canStagePerks` 因此为假，全页没有入口。

**修法**（两处，判据只写一遍）：

| 落点 | 改什么 |
|---|---|
| `buildWeaponDetailView.ts:525-536、588-600` | 判据按「插槽状态是否核实过」分开：`item.detail_loaded?.instance === true` 才用游戏返回的 `is_enabled` / `can_insert` 等硬条件；没核实过就按快照判「拥有且不是当前这项」——与定义没读时的 `buildRollSelectionColumns:338` 同一条规则 |
| 同上 | 顺带把「已经装着的那一项」从可切换项里摘出去（`isCurrentPlug`）。这条原来只在推荐区浮层的动作判定里防了一次，而它在本件 Roll 那一侧本来就是个点了等于取消待提交的空按钮；现在判据只在模型里写一次，两处都读它 |
| `WeaponDetailContent.tsx`（新增 `canStageWeaponPerks`） | 「能不能远程换 Perk」这个判定在文件里原来写着三遍（本件 Roll 的格子、正文底部的写面板、推荐区的 `canStagePerks`），前两遍一字不差、第三遍少了一个「非固定配置」的条件。收到一个函数里，三处都读它——这次是「三处一起哑掉」才被看见，不同步的话下次就是「一处能点、另一处点不动」 |

修完实测（同一条真路径）：快照状态 `精确弹药 false / 轻质弹匣 true`；完整 Roll 读到、
`is_enabled: true` 时 `轻质弹匣 true`；`is_enabled: false` 时 `轻质弹匣 false`（硬条件说了算）。
判据已固化进 `packages/desktop/test/weapon-detail-view.test.ts` 的两条用例（`previewedWeapon` /
`verifiedWeapon` 两个构造器分别造「快照」与「完整 Roll」两种状态）。

没有改 `buildPreviewSocketsFromWeaponRoll` 的占位值：那三项的 `false` 语义是「快照不知道」，
把它改成 `true` 是拿另一个断言换掉这一个，而且 `VaultDuplicateGroups.tsx:1011` 也在读 `can_insert`，
blast radius 更大。真正该记住的是**这套预览值不是插槽事实**，判据要按来源分开——
这一点写进了 `development.md` 的武器详情不变量。

## 二、实测：「当前启用」这一路信号有多弱

真组件渲染出的推荐对照区 DOM + 真样式表 → 无头 Chromium，量的是一张**「本件拥有、未被来源命中、当前启用」**的卡片
（就是用户截图里 测距仪 / 目标锁定 那个形态；样本文档里没有这个组合，脚本按产品的渲染路径补 `data-active` + 蓝点节点）：

| 信号 | 尺寸 | 颜色 | 对卡片底的对比度（dark / light） | 还带什么 |
|---|---|---|---|---|
| 命中：绿勾 | 16×16 实心 | `--status-ready` | 7.8:1 / 3.3:1 | 另加 3px 左缘实色条 + 绿边框 + 绿底 + 绿色状态字 |
| 命中：左缘条 | 3px 实色 | 同绿勾 | — | 结构信号，不只靠颜色 |
| 当前：蓝点（现状） | 外径 10，其中 2px 是**底色环** → **可见蓝芯只有 6px** | `--selected-border` #557288（低彩度灰蓝） | **3.2:1 / 3.8:1** | 无 |
| 当前：状态文字（现状） | 12px / 字重 400 | `--selected-fg`（dark #f2f6f8 / light #13232d） | 14.9:1 / 12.7:1 | 与标题同色＝没有颜色信息 |

- 面积比：绿勾 16² = 256px² 实心，蓝芯 6² = 36px²（**1/7**）；对比度 7.8 vs 3.2（**差 2.4 倍**）。
- 那张卡本身没有绿边框、没有左条、没有绿勾、没有阴影——**与一张普通「本件拥有」卡片看起来一样**，
  只是底色被 muted 压暗一点。所有「当前」信息＝一个 6px 灰蓝点 + 一句与标题同色的白字。

**顺带实测到一处反向问题**（不是用户报的，但同源）：`09-weapon-detail.css:481`
`[data-active="true"] small { color: var(--selected-fg) }` 写在 `:479` 的
`[data-hit="true"] small { color: var(--status-ready) }` 之后，两条同权重、后者生效，
于是**一张「符合 · 当前」的卡，文字反而丢掉了绿色**：实测 hit-only 的状态字是 `rgb(131,214,179)`，
hit+active 变成了 `rgb(242,246,248)`。也就是说「当前」不但自己不明显，还把「命中」的文字信号吃掉了。

## 三、为什么偏偏「未命中的当前启用」最惨

一条卡片能用的通道有五个：底色、边框、左缘条、图标标记、状态文字。
命中至少占四个（底色 + 边框 + 左条 + 绿勾 + 绿字）；未命中的「当前」只占**一个**（图标上的小点），
而这一个偏偏是玩家做决定时最需要看的——「来源要 A，我现在装的是 B」。

### 四之二、卡片状态全表（2026-09-18，照代码穷举 + 现场量对比度）

用户口径：「我感觉你没列全完整的状态，你再重新分析清楚，还有选中和非选中的状态」。
成立——前几版原型都只摆了三五张样卡，而且把「来源要求列」和「本件拥有列」的状态词混成了一行。

穷举的锚点是**条目组件上的开关本身**：`WeaponPerkEntry.tsx:84-91` 只有
`data-hit / data-active / data-pending / data-muted / data-unknown / data-emphasis / data-open / data-action` 八个。
其中前五个是独立状态开关，`emphasis` 是叠加的**语义开关**（选中 / 非选中），后两个是交互态。
各区域实际传了哪几个（决定了能叠出什么）：

| 区域 | hit | active | pending | muted | unknown | emphasis |
|---|---|---|---|---|---|---|
| 推荐对照区 · 来源要求列（`:1348-1362`） | ✓ | ✓ | — | ✓ | ✓ | — |
| 推荐对照区 · 本件拥有列（`:1380-1398`） | ✓ | ✓ | ✓ | ✓ | — | — |
| 推荐对照区 · 组合要求（旧路径，`:1600-1618`） | ✓ | ✓ | — | ✓ | ✓ | — |
| 本件 Roll 配置列（`:1102-1117`） | — | ✓ | ✓ | — | — | ✓ 恒开 |
| 固有能力 / 完整掉落池 / 异域配置候选（`:872/:885` + `weaponDetail.ts:586-608`） | — | — | — | — | — | ✓（无第二态） |

**互斥与可达**（都从传参推的，不是猜的）：

- `muted ∧ hit` **不可达**：三处的 muted 判据都带 `&& !hit`（`:1356`、`:1389`、`:1608`）。
- `pending ∧ hit` **可达**，而且是最高频的一张：把来源要的那项选上就有。
- `pending ∧ active` **在界面上不可达**：浮层动作只在 `canApply || staged` 时给，而
  `can_apply` 排除了当前插件（`buildWeaponDetailView.ts:592、600`）。CSS 没有为这个组合设防，
  万一 `pendingPerks` 残留指向当前项，会画出「选中底 + 待提交边框」的第三种样子。
- `muted ∧ active` **可达**：本件装的这项不在来源要求里、而这一行因另一项命中。
  「当前启用」本来就只有两路信号，再被降权压暗一档——这是最糊的一张。
- `来源要求列的 active ⇒ hit`：那里的 active 由 `ownedMatches` 派生（`:1859-1860`）。
  所以「当前启用但不命中」只出现在**本件拥有列**，前几版原型把它画在来源列是错的。
  另一条构造路径（`:1444-1445`）按 `current_enabled` 单独算 active，代码未强制互斥——理论可达，实际少见。
- `unknown` 只在推荐区：来源要求列取 `candidate.unresolved`（`!visual`，`:1810`），
  旧组合路径取 `!candidate.icon`（`:1609`）。**只读池拿不到**：view 模型算了
  `unresolved_in_definition_pool`（`buildWeaponDetailView.ts:608`），但 `PerkColumn` 没往 `unknown` 上接。

### 四之三、① 状态图鉴重做：把「区分不明显」拆成两个可量的问题（2026-09-18）

用户口径：「状态图鉴我感觉区分不明显，再优化一下」。前几版 ① 的问题是**每张卡单独摆一行**——
孤立地看一张卡，永远看不出它跟另一张卡是不是一回事。重做后 ① 有四件东西：

1. **每组顶部一条对照带**：把这一组的卡片按产品的列宽（`minmax(148px,1fr)`）并排铺开，
   不点、不展开，直接横着比。这是「区分得开吗」唯一能看出来的摆法。
2. **通道矩阵**：六个通道（底色 / 边框 / 左缘条 / 右缘条 / 图标角标 / 状态字）× 每个状态一行。
   格子不是手填的——构建时对每张卡逐属性取计算值，跟**同区域的素卡**逐项比，差 > 2/255 才算亮，
   数字是该颜色对它自己卡片底的对比度。表底一行是「这一列有几个状态在亮」。
3. **逐行通道小标 + 逐行文案**：这行哪几路在亮、亮成什么色、对比度多少，跟矩阵同一批数字；
   切「现状 / 戊 / 己」时矩阵与文案一起重画。
4. **去色开关**：`filter: grayscale(1)` 打在卡片与色块上。能靠位置分开的状态，去色后照样分得开；
   只能靠颜色分的，一去色就并成一张。这一条是给「颜色不是唯一信号」当证据用的。

矩阵里三种标的语义（这是这一版最要紧的一条）：

| 标 | 判据 | 意思 |
|---|---|---|
| 红框 | 同一位置 + 同一颜色，被**另一件不同的事**用着 | 真分不开。要改 |
| 黄框 | 同一位置 + 同一颜色，是**同一件事**的多个状态在用 | 叠加，正常。例如「命中」与「命中 + 待应用」共用那几格绿 |
| 表头「争」 | 这一列在同一区域里被**不止一种颜色**点着 | 颜色不同、人眼认得出，但两路信号挤在同一个通道上 |

红黄框只认「同一颜色」，量的是**真的分不开**；「两种不同的颜色抢同一格」是另一种毛病，用「争」单独数出来。
两张卡算不算「同一件事」，判据是它们**亮着的事情有没有交集**（每张卡带一个 `states` 集合：命中 / 当前启用 / 待应用 / 降权 / 未知）。

> 这里返过一次工：第一版每张卡只带一个 `family` 字符串，把「待应用」与「命中 + 待应用」判成了两族，
> 于是同一支蓝的边框被误标成红框。改成按事情取交集之后这类假阳性没了——红框从 8 格降到 **4 格**，
> 而且剩下的 4 格**全部落在同一列**。

**量出来的四件事**（都在 1440px / 深色下现场量的）：

1. **红框只剩 4 格，全在「状态字」这一列**，现状与建议档都一样：「当前启用」「待应用」「降权 + 当前」的字
   是同一支蓝（`--accent-primary` 与 `--status-pending` 在 `00-tokens.css:150/183` 指向同一个 `--blue`）。
   这一条**图形规则改不掉**——加边、加环、换位置都不动「字是什么颜色」。唯一的解法是从这两支蓝里
   拿掉一支（或改 token 值），那属于改颜色语义，得单独定；所以建议档**不去碰它**，也不假装解决了。
2. **「右缘条」这一列在现状里整列是空的**（矩阵表底计数为 0），而「当前启用」是全表信号最少的格：
   推荐区里它只有两路（16px 空心环 + 蓝字），本件 Roll 里那枚 10px 小实心点更是全表最弱的 **2.53:1**。
   建议档（戊）只做加法：给「当前启用」补一条**右缘 3px 蓝条**（无人占用的位置），
   本件 Roll 的小实心点换成推荐区同一枚近白空心环（**11.79:1**）。实测「右缘条」列 **0 → 1**、
   该行亮点 **2 → 3**、红框 **4 → 4 一格没多**、本件 Roll 的左缘选中条**原样保留**。
   代价也量出来了：**争用通道一处没少**（仍是 4 处），黄框 12 → 14（多出的两格是「当前」与「降权 + 当前」
   共用那条新边，同一件事画两遍）。戊 是拿「多一条边」换「最弱的那格变清楚」，不是拿它换整齐。

   > **这里推翻了上一版建议（丁），是本轮唯一一次改方向。** 丁 走的是「一路一形」：让待应用搬去右缘条、
   > 并让**命中也不再拿边框说话**，把边框整条通道腾空。整齐是整齐了（边框列颜色数 3 → 1、争用 5 → 3），
   > 但用户看一眼就指出来：「你的建议不是更不明显吗」。复核确认是对的——丁 把命中那条最亮的绿框拿掉，
   > 实测命中那张卡的差异属性从 **3 项降到 2 项**，整页比**现状**更安静。为了整齐去削最强的一路，
   > 方向反了。**教训：这一轮的目标是「更好区分」，任何从已有信号里做减法的方案都不该当建议，
   > 哪怕它让表格更漂亮。** 丁 留在 ② 里当对照，不作为建议。
   >
   > （丁 这里还返过一次工：第一版只让**待应用**让出边框，结果是「命中」有绿框、而「命中 + 待应用」的框
   > 被重置成灰的——同一件事两种长相。既然叫「一路一形」就得走到底。这条记录留着，说明丁 自身是自洽的；

   另外两处「争」是它们本来就该重叠的地方：底色（绿底 / 压暗底）与图标角标（绿勾 / 蓝环都在图标上）。
3. **「降权」的底色几乎不是信号**：它只把卡片底从 `rgb(25,37,48)` 压到 `rgb(22,33,44)`，**差 4/255**，
   肉眼基本看不出。真正让一张卡读出来「降权」的是图标透明度 0.66 与标题字色降一档。

   定 6/255 的话这一格恒为「没亮」，我第一版就是那么错的。）
   也顺带确认：`data-muted` 只改 `background` 和图标透明度（`09-weapon-detail.css:469-470`），
   **不碰 `box-shadow`**——所以戊 加的那条右缘条在降权的卡上照样亮着，是唯一压不暗的信号。
4. **「素卡」与「本件拥有 · 可切换」逐属性完全相同**——底色、边框、文字、标记全一样，
   唯一的差别是鼠标指针。矩阵里这两行整行是「—」。这正是 §四之二 结论 3 的可视化版本。

### 四之四、④ 真数据页：把信号放到真 Perk 上看，顺带量到一条对 戊 不利的数（2026-09-18）

用户看过 戊 的实拍后回了一句「**戊不要**」，接着要「找几个真实的武器 perk 看下实际的效果」。
所以这一轮做的是第二件事，但它的产物反过来解释了第一件事——结论先写在这里：

> **戊 也不作数了。** 两次提案（丁 是减法、戊 是加法）都被否。丁 被否我复核得出来原因（削了最强的一路），
> 戊 被否的原因见 §四之五——这一轮把它量出来了。
> 下面这条数是这一轮量出来的，它支持用户否掉戊——但它是**否完之后**才量到的，不是当时就有的判断，
> 这一点得说清楚，别把它讲成「我早想到了」。

**④ 页是什么**：`t73.html` 的第 4 个标签，把真数据灌进产品的 DOM 里看。三个真数据源分工明确：

| 界面上的东西 | 数据源 |
|---|---|
| 本件 Roll（装着哪几项） | 账号快照 `account-snapshot-cache.json` 的 `weapon_roll.sockets[]` |
| 本件拥有列（有哪些可核对项、哪项当前启用） | 同一份快照的 `owned_plugs[]`（带 `selected`） |
| 来源要求列（来源要哪些） | `weapon-recommendations.sqlite` 的 `recommendation_source_rule_requirements` |
| 配置列的候选（完整 perk 池） | `world.sqlite` 的 `DestinyPlugSetDefinition.reusablePlugItems` |
| 图标 | Bungie CDN，构建时下载并 base64 内嵌 |

口径与产品代码逐条对齐，不是近似：状态词照抄 `WeaponDetailContent.tsx:1065-1072` 的 `perkStatusWord`，
栏位胶囊照抄 `recommendMatchView.ts:26` 的 `presentRecommendationSlotMatch`，

命中判定按 `communityPerkRecommendationService.ts:330-339`——**hash 或名字对得上都算**
（只比 hash 会漏掉一大半：来源候选与本地定义常常不是同一个 hash 版本）。
DOM 是产品自己的类名（`.weapon-detail-source-slot-list` / `.weapon-detail-source-slot` /
`.weapon-detail-config-grid` / `.weapon-detail-perk-column`）套同一份产品 CSS，所以看到的就是应用里会长出来的东西。

**量到的两条**（构建时现量，`node build-t73.mjs` 会打出来）：

1. **一屏的「当前启用」不是一两次，是 14~15 次。** 傍晚SI4：一屏 68 张卡，命中 14 张，**当前启用 14 张**；
   最终恐惧：69 张卡，命中 16 张，**当前启用 15 张**。来源是 6 个推荐区栏位各 1 张、5 个配置列各 1 张，
   再加来源要求列里「既是候选又是当前」的那几张。
   —— 这一条直接冲着戊 去：一个**每屏要亮 14 次**的信号，再加一条右缘条，就是**每屏多 14 条蓝边**。
   戊 的立论是「当前启用信号最少、该补」，但「信号路数少」不等于「信号稀有」；它出现得又多又密，
   所以问题恐怕不在「它不够多」，而在「它跟旁边那些长得像」——加码治不了这个。
2. **真数据里「当前启用」和「命中」经常不是同一张卡。** 傍晚SI4 的 特性 1：来源要的是**治疗弹匣**，
   而玩家当前装的是**维持生计**（不在来源候选里，显示「当前启用」）。也就是说「符合来源要求的那一项」
   和「当前装着的那一项」是两件事，各自都能出现在任意一边——这正是 §三 说的「未命中的当前启用」，
   在真数据里是**常见**情形而不是边角。枪管 / 弹匣 / 起源特性三栏也都是「来源要的确实是当前装的」，
   两种都占齐了。

**顺手确认的一条产品行为**：推荐对照区的「本件拥有」列来自 `weapon_roll.sockets[].owned_plugs`，
非锻造武器的快照里每栏有 2~3 项（不是只有当前那项），`selected` 标出当前启用那项；
`summary.ts:2041-2044` 会把当前插件无条件并进 `owned_plugs`，所以**当前那项一定在列里**。

**本地数据的两个坑，写在页面上也不藏**：

- `world.sqlite` 是**裁剪过**的清单（只有 5422 个 plug set、38894 个条目）。带槽位级要求、又在你仓库里的
  武器共 8 件，**只有 2 件四个池子取全**，另外 6 件（崩崖 / 隐秘观测 / 升华 等）的某些栏位池子查出来是空的。
  ④ 页只放取全的，并把「取不全的有几件」写在页面上——不能把「取不到」画成「没有」。
- 抓候选池时同一件 perk 会在池里出现多个 hash（不同定义版本），必须按名字去重；
  不去重的话枪管池会从 11 项虚报成 21 项。

**复现**：`node extract-real.mjs`（读快照 + 两个库，产出 `real-weapons.json` + `icons/`）→
`node build-t73.mjs`（生成 `t73.html`，④ 的两个数字此时现量）→ `node check-t73.mjs`（断言）。
快照只读；两个 SQLite 先拷到 `/tmp` 再开，从不原地打开。④ 的断言有 10 条：
真图标必须真加载出来（0 张破图）、不许混进图鉴那边的合成 SVG、条目数够密（> 40）、
两条「当前启用」在 戊 下必须全部拿到右缘条、现状下必须一条都没有。

### 四之五、把真图标灌进 ① ②，然后才看清楚问题不在图标上（2026-09-18）

用户看了 ① 的截图，一句「**不对啊，没有 perk 图标？图标还是很重要的**」。这一条是对的，而且指到了方法上：
① 之前用的是合成彩色圆点，而图标是整张卡最大的一块内容、也是玩家认「这是哪个 perk」的唯一依据——
拿假图标判断「分不分得开」等于没判。这一轮先把 ① ② 全换成游戏里的真 Perk 图标，再重新量。

**① ② 现在全是真图标**：`build-t73.mjs` 从 `real-weapons.json` 收一张「名字 → 图标 data URI」表（本轮 60 个名字），
`entry()` 一律走它；查不到就记进 `MISSING_ICONS`，构建时打出来——**现在必须是 0**，有一条断言盯着。
不在本地资料库里的条目（a9 / r.unknown）**照产品的做法渲染 `◆` 占位**，不画假图标
（`WeaponPerkEntry.tsx` 的 `GameAssetImage` fallback 就是这样）。
另外把 A 组的 a2 / a3 / a4 / a6 换成**同一件 perk（附加弹匣）**：四张卡图标一模一样，「分不分得开」才只剩信号一个变量。

**先量角标：它没有想象中那么盖。**

| | 位置（相对 36px 图标） | 尺寸 | 真正压在图标上的面积 |
|---|---|---|---|
| 命中 ✓ | 右缘，跨在右上角上（左 69%、上 −14%） | 16×16 | **9.3%** |
| 当前 ○ | 右缘，跨在右下角上（左 67%、上 69%） | 16×16 | **10.2%** |

两枚都**骑在角上**，有一截悬在图标外（✓ 向右悬出 14%、向上悬出 69%），压的是字形笔画最少的那块。
所以「角标挡住了图标」这个说法站不住——**实测下来不挡**。真正的问题是它们都被画在了图标上，
而图标回答的是「这是哪个 perk」、信号回答的是「它算不算数」，两件事挤在同一块 36px 里。
（这条是量出来才知道的，跟我动手前的预判相反，记在这里免得以后又凭印象说。）

**再量真问题：把「色差」和「形差」分开数。**

新写的 `measure-contrast.mjs` 把每张卡的 9 项可见属性按通道类型分成**色**（底色 / 边框色 / 字色 / 图标明度）
和**形**（边框线型 / 左缘条 / 右缘条 / 图标角标 / 字重），然后两两组合，只问一件事：

> **这一对卡片的差异里，有没有一项是「形」？**
> 一项形差都没有 ＝ 去色之后这两张卡完全一样，只能靠读字分——那才是真风险。

36 对组合的结果：

| 档 | 形差为 0 的组合 | 其中要命的那几对（色差/形差） |
|---|---|---|
| 现状 | **5 对（14%）** | `命中↔命中+待应用` **2/0**、`素卡↔待应用` **2/0**、`素卡↔降权` 2/0、`当前↔降权+当前` 2/0 |
| 戊（已否） | **5 对（14%）** | 同上——**戊 一对都没修**：它只动「当前启用」，而上面这几对里没有「当前启用」 |
| 己 | **2 对（6%）** | 只剩 `素卡↔降权` 与 `当前↔降权+当前`——**都是「降权」，本来就只该差一点** |

**戊 被否的原因，量出来了**：戊 补的是「当前启用」的右缘条，而「当前启用 ↔ 旁边那几张」本来就有形差（○ + 字重）；
戊 没有碰最要命的那一对——**「命中 ↔ 命中+待应用」在两张卡上都是同一个绿 ✓、同一片绿底、同一条绿左缘条，
只差边框和状态字的色相**。而这恰恰是用户最常看到的一对：打开一个来源，多数行是命中，
勾过的那几行变成命中+待应用。戊 对它一无所用。

**还有一条成本数（这条解释了为什么戊 会「吵」）**：构建时把一屏真数据里每种状态数出来——

| 武器 | 卡片 | 命中 | 当前启用 | **待应用** | 素卡 |
|---|---|---|---|---|---|
| 傍晚SI4 | 68 | 14 | 14 | **0** | 33 |
| 最终恐惧 | 69 | 16 | 15 | **0** | 38 |

戊 动的「当前启用」**每屏 14~15 张**，加一条边＝每屏多 14~15 条蓝边，而且是在用户什么都没做的时候就亮着。
己 动的「待应用」**每屏 0 张**——它是用户自己勾出来的，勾之前一张都没有，成本只在真用到的那一刻出现。

**己 · 给「待应用」一个形**（① 现在的建议档，② 里按 6 或点按钮可以对照）：

图标**左下角**是空的——现有 ✓ 在右上、○ 在右下，三枚角标最多同时亮两枚（当前与待应用互斥）。
待应用在左下角拿一枚 **16px 圆角实心方块**（蓝底）。于是**勾 / 环 / 方**＝三块不同的形，分居三个角：

- `命中 ↔ 命中+待应用`（最常出现的一对）：从「同一个 ✓、换个色」变成「多了一块方」——形差 0 → 1。
- `当前 ↔ 待应用`：从「同一个蓝、只差一个环在不在」变成「环在右下 vs 方在左下」。
- 去色之后照样分得开——这一档的判据就是为它设的。
- **一个已有信号都没动**，只新占一个空位。代价是卡片多一个 span，产品端要动 `WeaponPerkEntry.tsx`
  （和已有的 ✓ / ○ 两个 span 同一个做法）。

**为什么是实心方块，不是空心的**：空心方块在 3× 实拍下跟那枚 ○ 环只差「圆角 vs 直角」，
而 `命中+当前`（○）与 `命中+待应用`（□）正是一对要分开的卡——两枚都是 16px 空心蓝圈，
靠圆角分辨细到量不出来。填充/不填充是能在 1× 下直接看出来的差别，所以填实。
（这条也是实拍看出来的：先做的空心版，对着 1× 图比过才改的。）

**已知代价，不藏**：那枚方块比 ✓ 和 ○ 都重——它是卡上最亮的一笔。对「等你去提交」这个语义说得通
（它确实是当下唯一要你动手的状态），但如果用户觉得吵，旋钮有两个：缩小到 12px，或改回空心并同时把 ○ 也改形状。

**复现**：`node build-t73.mjs` → `node check-t73.mjs`（① 的图标 / 角标几何 / 己 的方块共约 20 条断言）
→ `node measure-contrast.mjs`（三档规则 × 36 对的两两矩阵）→ `node shot-icons.mjs now ji`（图标近景 1×/4×）。
本轮新修的两个量测坑：`data-strip` 只挂在探针卡上、图鉴的行要用 `data-state`（用错了会让断言**空过**）；
以及没样式的空 span 是 36×0，只判宽度会把它当成一枚角标。

### 四之六、用户看完 ① 之后点名三件事，量下去发现我漏了一整行（2026-09-18 晚）

用户对着 ① 那条 9 张卡的并排带圈了几处，写的是：

> 对啊现在不就很明显了，每种状态的颜色，还有圆点标识不好区分，还有**不符合的**你没列出

三件事逐条落地。**全部是量出来的，不是我看着像。**

#### 一、「不符合的你没列出」——对，图鉴里根本没这一行

产品里「不符」是**栏位级**判定（`WeaponDetailContent.tsx:1566` / `:1588` 的 `stateLabel`，`stateTone="error"`），
它只落在栏头那枚红 chip 上。栏里的**卡片本身一个类都不加**——`muted` 只在 `state === "match"` 时才给（`:1356`），
`state === "different"` 时不给。所以那一栏的卡片和素卡长得一模一样，只差状态词的三个字
（`sourceStatus` 走 `perkStatusWord.missed` ＝「未拥有」）。

补成 a10 之后，两两矩阵里 45 对只有**一对**是真分不开——`素卡 ↔ 不符`：**形差 0、可见色差 0**，
是所有组合里唯一一对「去色之后像素级相同」的。这一对**庚 也没修**（见下）。

#### 二、「每种状态的颜色」——tokens 层面 4 个状态共用一支蓝

`tokens:150` 的 `--accent-primary` 和 `tokens:183` 的 `--status-pending` 指向**同一个** `--blue`。
实测 ① 里 10 张卡的**状态字**只有三支色，其中 **5 张是同一支蓝**：

| 卡 | 状态字 | 字重 | 边框 |
|---|---|---|---|
| 素卡 / 降权 / 资料库没有 / **不符** | `#91a1ae` 中性 | 400 | `#5c7586` |
| 命中 | `#83d6b3` 绿 | 700 | `#7ac1a9` 绿 |
| **当前启用** | `#8cc7ef` 蓝 | 700 | `#5c7586` |
| **命中+当前** | `#8cc7ef` 蓝 | 700 | `#7ac1a9` 绿 |
| **待应用** | `#8cc7ef` 蓝 | **400** | **`#8cc7ef` 蓝** |
| **命中+待应用（最常出现）** | `#8cc7ef` 蓝 | 700 | **`#8cc7ef` 蓝** |
| **降权+当前** | `#8cc7ef` 蓝 | 700 | `#5c7586` |

两个直接后果：

- `当前启用` vs `待应用`：**同一个底（`#192530`）、同一个字色（`#8cc7ef`）**，只差一条蓝边框和字重。
- `命中+待应用` 是用户最常看到的一张，它的字**丢掉了「符合」的绿**，跟 `待应用` 同色。

#### 三、「圆点标识不好区分」——CSS 层面的事实，勾和环都是一个圆

```
.weapon-detail-perk-entry-hit    { border-radius: 50%; }   /* 16px 绿圆盘 + 12px 的勾 */
.weapon-detail-perk-entry-active { border-radius: 50%; }   /* 16px 蓝空心环 */
```

两枚**都是圆**、都是 16px、都在图标右缘、左边界只差 1px（`left:31px` vs `left:30px`）。
16px 的绿盘在 1× 下先被读成「一个绿点」，盘里那个 12px 的勾要凑近才看得见。

#### 庚 · 三形分家 + 待应用换色

**① 把勾的绿圆盘拿掉，只留勾。** 一枪三形：**开口的笔画**（勾）/ **闭合的空心**（环）/ **直角的实心块**（方）。
去色之后三者的轮廓各不相同。

> 第一版翻车记录：用 6 层 `text-shadow` 给勾描边，勾的笔画只有 ~2px，四周各 1px 的暗边把中间那点绿整个吃掉，
> 4× 下成了一坨黑。改成 `filter: drop-shadow(...)` ×3——它描的是**字形自己的轮廓**（透明处不投影），
> 中间那笔绿原样留着。这一条是实拍看出来的，不是推的。

**② 待应用从蓝改成琥珀 `#e5bd70`**（调色板里现成的 `--amber`，语义是 `--status-warning`：一件还没落盘的改动）。
蓝从此只表示「当前启用」。边框、状态字、那枚方块三路一起换，不留半路。

#### 四档横向（10 张卡 / 45 对，全部现场量）

| 档 | 真分不开 | 只靠弱色差 | 两张卡的角标同形 | ① 矩阵红框 |
|---|---|---|---|---|
| 现状 | 1 | 7 | **10 对** | **4 格** |
| 戊（已否） | 1 | 7 | **10 对**（一对没动） | 4 格 |
| 己 | 1 | 3 | 6 对 | 4 格 |
| **庚** | 1 | 3 | **1 对** | **0 格** |

- **「两张卡的角标同形」**＝两张卡都带着角标、且两枚角标的轮廓**集合完全相同**——形状不提供任何信息，
  判断只能落在颜色上。现状 10 对里有 `命中 ↔ 当前启用`（两个完全不同的状态戴同一枚圆）。
- 庚 剩下那 1 对是 `当前启用 ↔ 降权+当前`——**它本来就该长得一样**（降权＝同一件事、只是更安静）。
- ① 的矩阵红框 **4 → 0**：红框的判据是「两件不共享含义的事在同一通道写同一个值」，
  4 格全在「状态字」这一列，就是上面那支蓝。待应用换色之后这一列没有撞的了。
  黄框 12 → 16，多出来的是待应用那一对自己（同一件事画两遍，正常）。
- 戊 再次被验证：改动前后**矩阵逐格相同**，一对没修。

**庚 没解决的问题（不藏）**：`素卡 ↔ 不符` 仍是形差 0、色差 0。
「不符」这一栏整栏只有栏头一枚红 chip 在说话，卡片上没有信号。要不要给卡片补一路，是另一个决定。

**代价**：① 调色板上多占一支（但它本来就是 `--status-warning`）；
② 勾去掉托底之后靠 `drop-shadow` 在图标上站住——原型里验过（a2/a4/a6，真图标、1× 与 4× 都看过），
真机上还得再扫一眼；③ 那枚琥珀方块是卡上最亮的一笔（对比 8.78，比原来那支蓝的 8.55 略高），

### 四之七、补上「不匹配」那一栏（2026-09-18 晚，用户第二次指名）

**这一节要修正上一节的一句话。** §四之六 写「素卡 ↔ 不符 是真分不开、庚 没修」——

> 本件拥有列里「当前启用」这个词，只可能出现在**不匹配**的栏里——`ownedStatus` 是先判 `hit` 再判
> `active`（`WeaponDetailContent.tsx:1325-1327`）：匹配上了就写「符合 · 当前」并多一枚绿勾（a4），

### 四之八、让卡片自己也说一句「不匹配」：两档原型 + 四组实测（2026-09-18 晚）

用户第三次指名，这次是要看到东西：

「二」指的是 ① 控制条旁边那条待办里的第二项——**给不匹配的卡片补一路信号**。做了两档，
开关放在**全局顶栏**（不匹配信号：无 / 辛 / 壬），和四档信号规则（现状 / 戊 / 己 / 庚）正交，
①②③④ 四个标签下都能切。

#### 先钉清楚要标哪张卡：一栏里几乎每张卡都是「不匹配」的

真数据（最终恐惧）实测，`node measure-x.mjs` 第一节：

| 栏 | 卡数 | 来源侧 | 本件侧 | 被标 |
|---|---|---|---|---|
| 枪管 | 5 | 3（全部「未拥有」） | 2（「当前启用」/「来源未要求」） | **1** |
| 大师杰作 | 4 | 2（全部「未拥有」） | 2（「来源未要求」/「当前启用」） | **1** |

「不符」这一栏的定义就是「来源要的没满足」，所以栏里**每一张卡都在说这件事**。
给每张都打标记＝枪管栏 5 个、大师杰作栏 4 个，满屏标记等于没标。

真正值得单说的是**本件当前装着、而来源没要它的那一项**——它是这一栏为什么不符的**直接原因**
（来源要的没装上，占着位置的是别的）。判据就是 §四之七 里那条形状指纹：

```js
// 只有「这一栏不符，而它是本件当前装着的那一项」才配得上这枚标记
mismatch: weapon.state[slot] === "different" && !hit && active
```

于是每栏恰好一枚，每把武器两枚。

#### 辛 · 图标左上一枚裸字形 ✕

左上角是 36px 图标上**唯一没被占的角**：右上＝命中勾、右下＝当前环、左下＝待应用方块。
手法照抄庚的勾（无底无边的字形 + `filter: drop-shadow()` 三层描边），所以在 1× 下不糊、
也不遮挡图标中心。同一张卡上四枚标记的实测矩形（按钮坐标系）：

| 标记 | x, y | 尺寸 | 压在 36×36 图标上的面积 |
|---|---|---|---|
| ✕ | 2, 2 | 16×16 | 9.3% |
| 勾（命中） | 31, 1 | 16×16 | 9.3% |
| 环（当前启用） | 31, 32 | 16×16 | 10.2% |

✕ 与环两两不重叠（`check-t73.mjs` 逐档断言，四个规则 × 三档全过）。

#### 壬 · 左缘 3px 红条

不占角，改占**左缘条**这条通道。理由是「绿＝符合来源 / 红＝不符合来源」是同一件事的两种答案，
而命中与不匹配互斥（`mismatch` 只在 `!hit` 时给），两条永不落在一张卡上。

#### 一个我自己埋的雷，量出来才看见：环不能染红

第一版两档都顺手把「当前启用」那枚**环染成红**。这是错的——
产品里两处列头写着「蓝环表示当前启用」（`WeaponDetailContent.tsx:1283` 和 `:1369`），
环一染红，那句图例当场变假；而且环的含义（这件当前装着它）跟这一栏符不符合是**两件事**，
一支通道背两个意思正是庚要拆掉的东西。已改回蓝，并在 `check-t73.mjs` 加了一条**反向**断言：

```js
if (mm.none.环色 !== mm.xin.环色) fails.push("不匹配信号把「当前」环染色了，…但列头图例写的是「蓝环表示当前启用」");
```

要染红环就得同时改那两句话，留给你定。两档保留的是**状态词**染红（`WeaponDetailContent.tsx`
没有为状态词颜色立图例，且庚已经用状态词颜色表示「待应用」，有先例）。

必须说实话，免得重蹈戊的覆辙。前面戊/己/庚量的都是**成对可分辨性**，而这一条：

#### 补上宽屏那一处：原型原先只画了窄屏的图例

改完才发现，决策 3 说的「连图例一起改」，**改的是两句话，而原型只画得出其中一句**。
产品里这两句写在两个互斥的位置：

| 宽度 | 谁在说这句话 | 产品位置 | CSS |
|---|---|---|---|
| 宽屏（1440） | 推荐区顶上的吸附表头 | `WeaponDetailContent.tsx:1280-1284` | `.weapon-detail-source-slot-columns`，`:611` 显示 |
| 窄屏 | 每栏自己的半区表头 | `WeaponDetailContent.tsx:1369` | `:617` 隐藏、`:743` 才摊开 |

原型原来只画了窄屏那一处。所以在 1440px 下——也就是用户看原型的宽度——图例一个都不显示，
「有没有改」只能靠我嘴说。已经给 `slotBlock` 旁边加了一个 `columnsRow()`，在**问题 1 那一栏的顶上**
画出宽屏吸附表头（问题 3 的卡是单独放大的，不带表头，所以问题 3 的说明里指了一句「改过的那句在问题 1 顶上」）。

不加到问题 3 上是权衡过的：吸附表头是三列网格，单独放一张卡在它下面会落在「栏位」那一列的正下方，
看着像那一栏的内容，比不放更误导。两处都画整栏又变成同一屏重复两遍。所以只在问题 1 画一次。

守卫相应补了宽屏那一遍（`check-t73.mjs` 的 E 段）：1440 查吸附表头**在**且文案是新的，
760 查它**收着**（不然和每栏小表头重两句）。现在两处都被量着，谁改坏了都会红。

#### 实测（`check-t73.mjs`，全过，控制台无报错）

  盒子的 padding box，盒子自己有 1px 边框。守卫第一版照 CSS 写了 `1,1`，被自己抓出来。

#### 一条差点没被发现的错：sed 改注释时行号算错，把模板串里的一行内容替换掉了

清理 `signalsAlt` 那批死数据时删了 4 行，紧接着按**删之前**的行号去 sed 改注释——行号已经偏了 4 行，

## 五、换 Perk 要不要进推荐区

| 角度 | 结论 |
|---|---|
| 数据可行性 | **可行**：推荐候选与实例候选按 hash / 名称对齐已有现成实现（`recommendationPerkMatches` `:1746`、`recommendationTargetPerk` `:1719` 同一套列匹配），`can_apply` 就在实例候选上 |
| 值不值得 | **值得**：对照区的价值就是「来源要 A，我装的是 B」，行动就在这一屏；去本件 Roll 找对应的格子是绕路 |
| 风险 1：待提交 | 推荐区的事实来自账号快照（`source_matches` 在 core/desktop 侧算好后传给 UI，见 `ItemDetailModal.tsx:231`），**不知道本地待提交**。点了不给「待应用」＝点了没反应；要给，就得把待提交状态喂进对照区，两侧共用同一批 pending |
| 风险 2：点击语义 | 推荐区现在「整卡点击＝看说明」，本件 Roll「整卡点击＝换 Perk」。若推荐区也整卡换 Perk，触屏就没有打开说明的路（T69 已记录同一限制） |
| 风险 3：时机 | 换 Perk 本身「有问题、之后要重构」（用户口径）。重构前把它扩到第二个面，很可能返工 |

**建议（待拍板）**：要加就加在**说明浮层里的显式按钮**，只出现在 `can_apply && !pending` 的条目上，
点击后进同一批待提交、两侧都显示「待应用」；不做「推荐区整卡点击＝换 Perk」。
或者**先只做 T72 排布 + 第四节的标记加强**，把「换 Perk 重构」和「入口放哪」合并成一次做。

> 2026-09-17 用户更正（本节的依据）：**换 Perk 一定是批量的**——不能给单个条目一个「切到这项」式的立即动作。
> 已按这条重做试做（见下节）。产品里的模型也确实是批量的：`pendingPerks: Record<socketIndex, hash>`
> （`buildWeaponDetailView.ts:46`），一个槽位一项、多项一起提交，提交后写面板显示
> 「已选择 N 项更改 / 待提交」+「取消选择 / 应用 N 项更改」（`WeaponDetailContent.tsx:986-993、745-780`）。

### 五之一、「浮层内选择」已经按批量重做出来了（`prototype-final.html` 第五段）

- 浮层里那一行**不用新造样式**：`data-ui-kind="button" data-control-variant="secondary"` 是产品现成的按钮，
  放进条目自带的那层说明浮层（`WeaponPerkEntry.tsx:92-106`）即可，实测 280×34。
  文案跟着批量走：没选过是**「选择」**，选过是**「取消选择」**（与写面板的「取消选择」同一套词）。
- 一次选多项：这一段把**同一条来源卡里的几个槽位**各选了一项（「稳定性」「穿透」），都显示「待应用」，
  底部是产品现成的写面板：`已选择 2 项更改 / 待提交 / 确认后才会写入游戏；写入成功前，当前配置保持不变。`
  ＋「取消选择」「应用 2 项更改」（实测面板 1138×66、吸附在视口底部 8px，与产品一致）。
- 实测出来的三件事：
  1. **提交按钮在推荐区看不到**。写面板 `position: sticky; bottom: 8px`，但它长在「本件 Roll」区
     （`09-weapon-detail.css:358`），而 T71 之后推荐区排在它**上面**一屏。所以「在推荐区里选了东西」
     之后，唯一的提交入口在屏幕外——这正是第五节风险 1 的具体形态。第五段原型是把面板挪到推荐区
     才同时看见的；真要这么做，得先把面板做成两区共用（或整页固定）。
  2. **同一列里「当前」与「待应用」是同一支蓝**：`--status-pending` 与 `--accent-primary` 在
     `00-tokens.css:150/183` 都指向 `--blue`（深色 `#8cc7ef`、浅色 `#17698f`）。若标记选 m1，
     同一列会相邻出现「当前」的蓝环与「待应用」的蓝边框，只有形状不同。
     **更正 2026-09-17 早先的说法**：曾写过「同一张卡上环与边框同色」——不成立。
     `buildRollSelectionColumns:337-339` 里 `selected` 取当前插件、`pending` 取 `pendingPerks[槽位]`，
     而 `can_apply` 排除当前项，所以**待应用的卡不会是当前项、也就不会有环**，两者只会在不同卡上相邻出现。
  3. 主按钮绿系（`--control-primary-bg`）在试做里**不再是问题**：浮层那一行改用 secondary，
     绿色只留在写面板的「应用 N 项更改」——那本来就是这个应用里唯一的提交动作，绿得有道理。
     （早先担心的「绿按钮和命中绿撞色」是「单项立即切换」版本才有的问题，随该版本一起作废。）
