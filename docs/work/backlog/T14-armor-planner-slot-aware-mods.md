## 与 T15 的依赖结论

T15 的核心合同已经满足 T14 开发条件。真实库存候选、逐件 Socket 预检、方案穿戴和执行后核对继续消费 T15 的统一账号数据层；T14 不自行实现第二套账号缓存、远程请求时序或失效逻辑。

依赖边界如下：

| T15 提供 | T14 使用场景 | 边界要求 |
|---|---|---|
| 账号快照资源及来源指纹 | 方案可穿戴状态、库存候选初始输入、当前装备差异 | 允许读取本地旧数据，但必须保留 `cached / stale / refreshing / ready / error` 语义 |
| 账号实例详情资源 | 护甲能量、Socket、当前 Plug、`reusable_plugs` 与具体安装能力 | 按 `account + instance_id` 读取，不由配装页重复请求或维护私有缓存 |
| Manifest 与账号事实的版本边界 | 逐部位属性模组和 T5 护甲调整预检 | 候选必须绑定账号快照、实例详情、Manifest 和规则集 revision |
| 写操作刷新与精确失效 | 转移、装备替换、Plug 写入、执行后核对 | T14 只调用统一 action；成功后由 T15 失效受影响实例并发布新的资源状态或刷新结果 |

已满足的恢复条件：

1. 已冻结 `getSnapshot / getItemDetail / prefetchItems / invalidate / subscribe` 或对应跨进程资源入口，以及 `DataResource` 的 freshness 状态。
2. 已按账号与实例稳定键隔离快照和实例详情；Armor Planner 继续使用账号护甲指纹、Manifest 和规则集来源生成候选 revision。
3. 转移、装备和 Plug 写入已接入实例级 invalidate；执行前继续使用权威刷新，执行后重新读取并核对受影响实例。

T15 已完成并通过真实账号诊断验收。T14 继续消费既有账号数据合同与写后精确更新能力；除非发现合同缺口，不修改 `AccountSession`、账号缓存或 Desktop 账号运行时。

## 产品定义修正

T14 必须区分两种不同业务对象，不能把它们合并为同一方案的来源筛选：

| 对象 | 定义 | 核心能力 |
|---|---|---|
| 游戏内配装 | Bungie 官方角色配装槽位，数量和可读字段受游戏接口限制 | 查看官方槽位、调用 Bungie 官方应用、用当前装备覆盖槽位、复制可确认字段到应用配装 |
| 应用配装 | 本应用保存和管理的完整构筑方案，不受 Bungie 槽位数量限制 | 查看、比较、创建、编辑、自动配甲、生成转移/替换/Plug 步骤、一键穿戴、验证后保存到游戏内槽位 |

两者保持一级视图分离：`游戏内配装` 与 `应用配装`。显式“复制到应用配装”和“保存到游戏内槽位”是跨边界转换，不代表两者自动同步，也不允许共用同一个目录对象冒充同一种方案。

## 游戏内配装读取边界与辅助操作

游戏内配装是 Bungie 的官方角色槽位，不是完整的 DIM 配装对象。`CharacterLoadouts` 原始记录只保证返回：

- 槽位索引、名称 Hash、图标 Hash、颜色 Hash。
- 每个装备的实例 ID。
- 每个装备按 Socket 顺序排列的 `plugItemHashes`。

原始槽位不会直接携带装备名称、装备 Hash、属性、能量、Perk 说明或模组分类。页面可以使用当前账号快照和 Manifest 反查这些信息，但必须标明它们是“账号快照补充信息”，不能伪装成 Bungie 槽位原始字段。

### 读取与展示规则

| 数据 | 页面语义 | 缺失时的显示 |
|---|---|---|
| 槽位名称 / 图标 / 颜色 | Bungie 官方槽位标识 | 使用槽位编号，不伪造自由文本 |
| 装备实例 ID | Bungie 保存的实例引用 | 显示实例尾号和“未在当前快照中找到” |
| 装备名称 / 图标 / 位置 | 当前账号快照反查 | 不显示“物品 + 实例 ID”作为装备名称 |
| 装备属性 / 能量 / Perk | 当前账号实例详情 | 标记快照来源和更新时间；缺失时显示“未读取” |
| Plug Hash | Bungie 返回的配置引用 | 按 `socket_index` 展示，未设置 Plug 不显示为真实模组 |
| 模组类型 | Manifest 与规则集推断 | 无法确认时显示“类型未知”，不得按名称猜测 |

游戏内配装的标准装备结构应拆分为：

1. 三件武器：动能、能量、威能。
2. 五件护甲：头盔、臂铠、胸甲、腿甲、职业物品。
3. 子职业。
4. 神器。

不得把“非武器”统一归入护甲与职业物品。槽位数量、已定位数量和未定位数量必须基于有效实例记录统计；Bungie 的 `itemInstanceId: "0"` 及未设置 Plug Hash 只能作为占位数据处理。

### 操作分层

游戏内配装页保留两类操作，但必须在 UI 和确认文案中区分写入目标：

| 操作组 | 操作 | 写入目标 |
|---|---|---|
| 官方槽位操作 | 应用游戏内配装 | Bungie 官方槽位执行 `EquipLoadout` |
| 官方槽位操作 | 用当前装备覆盖槽位 | 读取当前角色状态并执行 `SnapshotLoadout` |
| 官方槽位操作 | 清空槽位 | Bungie 官方槽位执行 `ClearLoadout` |
| 官方槽位操作 | 修改名称 / 图标 / 颜色 | Bungie 官方槽位执行 `UpdateLoadoutIdentifiers` |
| 配装辅助操作 | 单件转移、单件穿戴 | 当前账号装备状态，不自动修改槽位 |
| 配装辅助操作 | 单个模组编辑 | 真实装备 Socket，不自动修改槽位 |
| 配装辅助操作 | 自动补齐、自动换护甲、属性优化 | 应用配装或 Armor Planner 执行计划 |
| 跨边界转换 | 复制到应用配装 | 生成应用配装草稿，不写入 Bungie |

单件装备和单个模组操作可以从游戏内配装页发起，但必须显示为“辅助当前装备”。如果用户希望把修改保存回游戏内槽位，统一走：

```text
修改真实装备 / 转移 / 穿戴 / 修改模组
→ 刷新并核对当前角色
→ 明确提示 SnapshotLoadout 会保存当前完整配装
→ 用户确认后覆盖 Bungie 槽位
```

Bungie 没有“只更新槽位中的单件装备或单个模组”的接口。重新保存槽位会记录当前角色完整的可保存装备和 Plug 配置，因此覆盖前必须告知用户这一点。

### 游戏内配装页面验收标准

- 顶部明确显示 `Bungie 官方槽位`、当前角色和账号数据 freshness。
- 右侧将“官方槽位操作”和“配装辅助操作”分组，不能把穿戴、转移和槽位保存混成一个按钮语义。
- 装备卡片提供“查看装备详情与已接通的转移、穿戴、模组编辑、复制到应用配装”等上下文操作；尚未接通真实核对链路的组合动作不显示为可用按钮。
- 未来开放“替换并保存”时，必须展示两阶段执行步骤，并在最终 Snapshot 前再次确认；当前页面只提供“用当前装备覆盖槽位”这一官方 Snapshot 入口。
- 装备卡片按武器、护甲、子职业、神器分组；Plug 显示具体 Socket 位置。
- 未定位实例、缓存过期和未解析 Plug 均使用状态标签表达，不生成假装备名称或假模组结论。
- 在窄屏或键盘导航下，列表 → 槽位详情 → 装备操作 → 辅助向导使用页面栈推进，返回时恢复原槽位和原装备焦点。

## 背景

配装页当前已经能够区分 `tuning` 与 `armor_stat_mod`，也能在理论和库存规划中统计 `+5 / +10` 属性模组，但现有求解仍主要把模组视为五件护甲共享的全局数值预算，没有完整保留每件护甲的能量、Socket、其他功能模组占用和最终 Plug 分配。

这种模型会产生不可执行的候选：六维总数值在数学上能够达标，但求解器可能把 `+10` 属性模组安排到能量不足的手臂或腿部，或者把两个 `+5` 当作一个聚合加成，没有证明它们分别安装在两个具体部位。结果页也无法解释每件护甲使用了哪一种护甲调整、哪一个属性模组以及最终能量是否超限。

本任务参考 DIM 的逐部位可安装性思路，但基于本项目的 Armor 3.0 领域模型、账号实例、Manifest Plug、配装草稿和安全执行链路原生实现，不导入或依赖 DIM。`d2-armor-solver` 只保留问题分类参考，不采用其先生成全局模组数量、再按件序映射的求解方式。

## 产品目标

配装菜单首先服务两个玩家目标：

1. 查看已有应用配装，并与其他应用配装或游戏内配装快照进行差异对比。
2. 像 DIM 一样创建完整应用配装，选择子职业、武器、护甲和模组，并通过一次确认完成装备转移、当前穿戴替换和可验证 Plug 写入。

逐部位护甲求解不是第三个一级页面，也不是一种方案类型。它位于应用配装创建/编辑器的护甲区域，使用玩家文案 `按属性目标自动配甲`，作用是根据六维、异域、套装、实例和模组限制填入五个护甲槽位。

玩家在自动配甲面板中指定精确的 `+5 属性模组` 和 `+10 属性模组` 数量。计算器读取五个护甲部位的真实可安装能力，在满足每件护甲 Socket、能量和其他已规划模组占用的前提下，把指定数量的属性模组分配到具体部位和具体属性，同时自动选择每件 T5 护甲的零能量护甲调整，联合求解最终六维。

结果必须能够回答：

1. 指定数量的属性模组是否真的能装进这五件护甲。
2. 每个 `+5 / +10 属性模组` 分别安装在哪个部位、增加哪项属性。
3. 每件 T5 护甲自动选择了什么 `+5/-5` 或 `+3` 护甲调整。
4. 每件护甲的其他模组占用、属性模组消耗和最终能量是多少。
5. 接受候选后，保存和执行链路能否按相同实例与 Plug 复现结果。

## 非目标

- 不依赖 DIM 的网页、接口、算法、账号数据或运行时。
- 不把 DIM 配装导入作为本任务前置条件；DIM 只用于验证交互和求解思路。
- 不处理 DIM Wishlist。Wishlist 属于仓库装备目标与匹配能力，是独立功能。
- 不把 `+5 属性模组` 与 `+5/-5 护甲调整` 合并为同一种资源或同一个数量。
- 不允许只计算五件总能量后忽略部位、Socket 或单件上限。
- 不把游戏内配装与应用配装合并进同一个方案目录；比较界面可以投影两者的共同字段，但不得改变各自身份、执行方式和数据完整度。
- 不把自动配甲提升为与游戏内配装、应用配装并列的一级入口。
- 不在 Web 或 Desktop 壳复制一套配装页面；页面继续由 `packages/ui` 共享。

## 术语与业务边界

### 护甲调整

- 当前规则下仅 T5 护甲拥有，具体条件由版本化 `ArmorRuleset` 描述。
- 不消耗护甲能量。
- 不占用属性模组数量，也不与五个属性模组安装位共用预算。
- 由计算器逐件自动选择，不要求玩家填写数量。
- 包括规则集允许的 `+5/-5` 调整和 `+3` 调整。
- 传说护甲遵守其固定 `+5` 目标和可选调整范围；异域按真实 Socket 与规则集允许范围处理。
- 结果必须显示调整前后属性、来源 Plug 和置信度；无法确认时不能猜测。

### 属性模组

- 玩家分别指定精确的 `+5` 和 `+10` 数量，语义为 `exact`，不是“最多可使用”。
- 两种数量之和不得超过五件护甲可用的属性模组 Socket 数量。
- 一个属性模组必须落在一件具体护甲上；两个 `+5` 必须对应两个具体且不同的可安装部位。
- 属性模组消耗能量，消耗值、Plug 身份和 Socket 兼容性以当前 Manifest 与规则集为准。
- 求解器决定具体安装部位和增加的属性，但不得改变玩家指定的 `+5 / +10` 数量。
- 如果精确数量无法安装，结果为不可达或不确定，并说明阻断部位；不得静默减少、升级或降级模组。

### 其他功能模组

- 武器强化、装填、抗性、回收、虹吸等非属性 Plug 继续由配装草稿维护。
- 它们先占用对应护甲的能量和 Socket，再由 Armor Planner 判断该部位还能否安装 `+5 / +10 属性模组`。
- 当前默认携带草稿中能量成本大于零的功能 Plug；未被草稿目标覆盖的候选现有耗能 Plug 保守保留，避免把无法自动清空的能量误算为空闲。
- 求解候选不得移动、删除或替换玩家已锁定的其他模组；允许自动调整时必须作为后续独立策略显式提供，不纳入本任务默认行为。

## 用户工作流

### 游戏内配装

```text
选择角色与 Bungie 官方槽位
→ 查看游戏真实返回的装备记录和账号定位状态
→ 应用游戏内配装 / 用当前装备覆盖槽位 / 清空槽位
→ 或显式复制可确认字段到一份未保存的应用配装草稿
```

### 应用配装

```text
进入应用配装库
→ 查看已有方案，或选择 2–3 个方案进入差异对比
→ 新建或编辑应用配装
→ 在槽位式编辑器中配置子职业、三件武器、五件护甲和模组
→ 需要自动选择护甲时打开“按属性目标自动配甲”
→ 设置六维目标与其他配装约束
→ 指定 +5 属性模组数量和 +10 属性模组数量
→ 读取五个部位的护甲、T5、能量、Socket 与其他模组占用
→ 自动枚举每件 T5 护甲可用的零能量护甲调整
→ 把精确数量的 +5/+10 属性模组分配到可安装部位和目标属性
→ 联合求解最终六维、套装、异域、位置与锁定约束
→ 展示逐件调整、属性模组、其他模组和能量账本
→ 接受库存或升级候选并填入应用配装的五个护甲槽位
→ 保存应用配装
→ 点击“穿戴此方案”，执行前刷新账号和 Manifest 并重新进行逐部位预检
→ 自动转移真实实例、替换目标角色当前穿戴并写入可验证 Plug
→ 刷新核对成功后，可显式保存到一个游戏内配装槽位
```

修改六维、属性模组数量、其他模组、锁定/排除实例、角色、位置、套装、异域或碎片后，当前候选立即变为过期，必须重新计算。

## 请求与领域模型

### Planner 请求

用精确数量替代仅表达可用值范围的全局 `allowed_armor_mod_values`：

```ts
type ArmorStatModPlan = {
  plus5_count: number;
  plus10_count: number;
  usage: "exact";
};

type ArmorTuningPolicy = "auto_t5";
```

`ArmorPlanRequest` 需要携带：

- `armor_stat_mod_plan`：玩家指定的精确数量。
- `tuning_policy`：当前固定为自动 T5 调整。
- 每个部位已规划的非属性 Plug；没有选择时明确为空，而不是未知。
- 当前账号、Manifest、规则集和配装草稿 revision。

旧 `armor_mod_budget` 可以继续作为目标可达性与结果统计结构，但不得同时承担“精确数量”和“最多数量”两种含义。旧 `allowed_armor_mod_values` 只作为迁移输入兼容读取，不能继续作为新 UI 的业务真相。

### 单件护甲快照

`ArmorPieceSnapshot` 或对应规划输入需要保留逐件安装能力：

```ts
type ArmorPieceInstallationContext = {
  gear_tier?: number;
  energy_capacity?: number;
  reserved_energy?: number;
  remaining_energy?: number;
  stat_mod_socket?: ArmorSocketSnapshot;
  tuning_socket?: ArmorSocketSnapshot;
  allowed_stat_mod_options: ArmorStatModOption[];
  planned_non_stat_plugs: PlannedArmorPlug[];
};
```

至少覆盖：

- 护甲部位、实例 ID、定义 Hash、职业、位置和异域身份。
- T5 / gear tier 判断及其数据来源。
- 当前能量容量；容量未知不能默认按 `10` 处理。
- 属性模组 Socket、护甲调整 Socket 和其他相关 Socket。
- 当前已安装 Plug 与草稿计划 Plug 的稳定 Hash、能量成本和兼容类别。
- 其他模组的保留能量、剩余能量和数据完整度。
- 该件可安装的 `0 / +5 / +10` 属性模组选项及具体 Plug。
- `0` 选项必须对应属性模组 Socket 的真实零能量清空 Plug，不能只在数值层省略当前模组。
- 该件可选择的 T5 护甲调整及具体 Plug。

`normalizeArmorPiece()` 必须把 `AccountItemSummary.armor_energy` 和 `sockets` 归一化到规划快照，不得在进入 Planner 前丢失。

### 逐件候选结果

每件候选护甲至少返回：

```ts
type ArmorPlannedPieceAssignment = {
  slot: ArmorSlot;
  instance_id?: string;
  tuning?: {
    mode: "shift" | "plus3";
    values: ArmorStatValues;
    plug_hash: number;
    energy_cost: 0;
  };
  armor_stat_mod?: {
    stat: ArmorStatKey;
    value: 5 | 10;
    plug_hash: number;
    energy_cost: number;
  };
  planned_non_stat_plugs: PlannedArmorPlug[];
  energy_capacity?: number;
  reserved_energy: number;
  stat_mod_energy: number;
  final_energy?: number;
};
```

候选总账本继续分别累计基础属性、大师杰作、护甲调整、属性模组、碎片和最终六维。`candidate_id` 的稳定指纹需要包含逐件调整、属性模组槽 Plug 与耗能功能 Plug 分配，避免两种不同 Plug 方案生成同一候选 ID。

## 逐部位求解规则

### 安装能力预计算

对每件护甲先计算可安装选项：

1. 校验属性模组 Socket 是否存在、可用且与目标 Plug 兼容。
2. 计算 `remaining_energy = energy_capacity - planned_non_stat_plugs_energy`。
3. 依据 Manifest Plug 成本生成该件允许的 `0 / +5 / +10` 选项。
4. 独立读取 T5 护甲调整 Socket，生成零能量调整选项。
5. 缺少容量、Socket 或 Plug 定义时标记为不确定，不用名称或默认成本补造。

### 联合分配

求解状态必须包含五件护甲各自已占用的属性模组位，而不是只保存全局 `plus5 / plus10` 计数。剪枝至少检查：

- 尚未分配的 `+5 / +10` 数量是否还有足够部位承载。
- 剩余部位是否存在足够能量安装对应模组。
- 同一件护甲是否被重复分配两个属性模组。
- 属性模组增加的属性是否仍可能满足硬约束。
- T5 调整与属性模组是否按独立账本累计。
- 固定实例、异域、套装、位置、转移和升级约束是否仍可满足。

只有当 `used_plus5 === plus5_count` 且 `used_plus10 === plus10_count` 时，候选才算满足模组约束。候选排序不能通过少装模组换取更高排名。

### 数据不完整

- 真实实例缺少能量或 Socket 时，严格库存方案排除该实例并说明原因。
- 理论方案只有在规则集能够证明该理论身份的 Socket 与容量时才可判定可达。
- 部分数据足以计算属性、但不足以生成 Plug 计划时，状态为 `indeterminate`，不能开放保存为可执行方案。
- 搜索截断或近似结果必须保留现有警告，不能显示为唯一最优方案。

## 四种配装页模式

| 模式 | 逐部位模组行为 | 可交接结果 |
|---|---|---|
| 库存成装 | 使用真实账号实例、实际能量与 Socket；重新分配属性模组并自动选择 T5 调整 | 可接受真实五件实例和 Plug 计划 |
| 理论上限 | 使用规则集生成各部位理论安装能力，不伪造实例 ID | 只展示理论配置，不可直接执行 |
| 待刷目标 | 已有件使用真实能力，缺口生成包含部位、能量、Socket、T5 和调整要求的抽象身份 | 可保存待刷要求，不可把缺口当成实例执行 |
| 升级路径 | 当前五件作为基线，逐个替换时每一步都重新分配精确属性模组与 T5 调整 | 最终真实组合可接受；每一步展示是否需要换 Plug |

`reachability` 继续作为领域层精确可达性能力，复用同一逐部位分配器，不在配装页新增第五个一级模式。

库存和升级模式不再默认使用“固定当前最终属性、禁止重新分配属性模组”的 `conservative` 行为。需要保留当前 Plug 的场景应作为明确的“锁定当前模组”约束，而不是页面隐藏默认值。

## 配装页 UI 信息架构

### 一级视图

配装菜单保留两个一级视图：

```text
角色：[术士] [泰坦]
视图：[游戏内配装] [应用配装]
```

- `游戏内配装` 只管理 Bungie 官方槽位和官方应用能力。
- `应用配装` 管理本应用保存的完整方案，并承载查看、对比、创建、编辑和穿戴。
- 不出现独立的“护甲优化”“Armor Planner”或“求解器”一级入口。
- 切换一级视图后，键盘焦点进入该视图第一个主要操作；返回子页面时恢复来源方案或按钮焦点。

### 游戏内配装视图

游戏内配装继续显示角色的真实 Bungie 槽位，核心操作使用明确文案：

- `应用游戏内配装`
- `复制到应用配装`
- `用当前装备覆盖槽位`
- `清空槽位`

复制操作只创建未保存的应用配装草稿，并只携带 Bungie 实际返回且能够确认的字段。未返回的 Perk、技能和模组不得补造。

### 应用配装库

应用配装默认进入方案库，而不是直接进入编辑长表单：

```text
应用配装                            [对比方案] [新建配装]

搜索：[____________]  筛选：[职业] [可穿戴状态]

┌ 方案目录 ───────┬ 方案详情 ────────────────┬ 穿戴状态 ─────┐
│ 虚空术士        │ 子职业 / 武器 / 护甲     │ 可穿戴 10/10  │
│ 宗师夜幕        │ 六维 / 套装 / 模组       │ 需要转移 3 件 │
│ 突袭输出        │ 当前方案差异             │ Plug 可写     │
│                 │                          │ [穿戴此方案] │
│                 │                          │ [编辑方案]   │
└─────────────────┴──────────────────────────┴───────────────┘
```

- 目录只显示已显式保存的应用配装；未保存草稿不冒充目录项。
- 方案详情是只读完整构筑视图，查看方案不自动进入编辑。
- `穿戴此方案` 是应用配装的持续可见主操作，与游戏内视图的 `应用游戏内配装` 使用不同文案和执行链。
- 宽屏使用目录、详情、穿戴状态三栏；中等宽度把状态压为详情顶部摘要；窄屏使用单栏页面栈和固定底部主操作。

### 方案对比

点击 `对比方案` 后进入多选状态，允许选择 2–3 个应用配装；游戏内配装可以作为只读参照快照加入比较，但不因此转化为应用配装。

对比至少覆盖：

- 子职业、异域、三件武器和五件护甲。
- 六维属性、套装效果、属性模组数量和关键功能模组。
- 当前账号可穿戴数量、缺失实例、需要转移数量和 Plug 可写状态。
- 与当前穿戴或另一方案相比需要替换的装备数量。
- Bungie 未返回的字段显示 `未返回`，不得与应用配装的完整字段视为相等。

默认突出差异项并提供 `仅显示差异`。每个方案列提供 `查看`、`编辑` 或对应的穿戴操作；退出比较后恢复原选择和滚动位置。

### 应用配装创建/编辑器

`新建配装` 与 `编辑方案` 推入独立编辑页面，采用槽位式构筑而不是把所有能力纵向堆成长表单：

```text
← 返回应用配装      方案名称 · 未保存       [保存] [穿戴]

子职业  [子职业配置]
武器    [动能] [能量] [威能]
护甲    [头] [手] [胸] [腿] [职业物品]
                                      [按属性目标自动配甲]
模组    [逐部位模组配置]

右侧实时摘要：六维 / 套装 / 异域 / 缺口 / 穿戴步骤
```

- 点击槽位打开对应的真实实例选择子页面或抽屉，关闭后恢复槽位焦点。
- 编辑器顶部保存状态与 `保存`、`穿戴` 操作持续可见。
- 未保存修改触发共享离开保护，不使用页面私有 `window.confirm`。
- DIM、攻略成果、游戏内配装复制和当前装备复制都进入同一个未保存编辑器，不建立平行编辑页面。

### 页面状态栈与焦点

应用配装不再使用 `isDimImportOpen / isGuideImportOpen / draft` 等多个布尔值拼接页面状态。共享 ViewModel 使用判别联合或等价页面栈表达唯一顶层状态：

```ts
type LoadoutScreen =
  | { kind: "library"; selected_plan_id?: string }
  | { kind: "compare"; plan_ids: string[] }
  | { kind: "editor"; draft_id: string }
  | { kind: "item-picker"; slot: string; return_focus_id: string }
  | { kind: "armor-planner"; return_focus_id: string }
  | { kind: "wear-review"; plan_id: string }
  | { kind: "publish"; plan_id: string };
```

- 页面 push 后只有栈顶接收输入；返回时恢复来源方案、装备槽或自动配甲按钮的焦点。
- 一级视图、角色切换和 Armor Planner 模式使用 roving focus；方案目录使用稳定上下导航，不因后台刷新重排或抢焦点。
- 确认弹层必须约束焦点，关闭后恢复触发控件；鼠标与键盘焦点可以共存。
- 宽屏采用目录、详情、穿戴摘要三栏；中等宽度采用目录与详情两栏并把穿戴状态放到详情顶部；`760px` 窄屏每次只显示一个页面状态，不把三栏纵向堆成长页面。
- 窄屏的 `保存 / 穿戴` 使用安全区域内的固定底部操作栏；桌面宽屏保持顶部或详情侧持续可见主操作。

### T15 账号数据状态接入

配装共享 UI 接收资源状态 ViewModel，不直接 import Desktop Hook、IPC 或 `packages/services`：

- `cached / stale`：允许查看、比较、编辑和理论计算；库存自动配甲可以计算，但必须标记“穿戴前需要刷新验证”。
- `refreshing`：保留当前方案、候选、滚动位置和焦点，不切回空白 loading，也不自动改变选择。
- `error` 且仍有旧数据：继续开放只读操作并提供邻近重试；没有数据时才显示区域级失败状态。
- 离线时继续允许浏览、比较和编辑应用配装；转移、穿戴、Plug 写入和账号刷新明确禁用并显示原因。
- 点击 `穿戴此方案` 后必须强制刷新账号和目标实例，再生成不可变执行计划；缓存状态不能直接作为可执行证明。
- 账号资源更新通过共享订阅、resource key 或显式刷新事件驱动，不在配装页面轮询。

### 按属性目标自动配甲

自动配甲是应用配装编辑器中护甲区域的辅助页面，负责填入五个护甲槽位。玩家文案固定使用 `按属性目标自动配甲`，技术层可以继续使用 Armor Planner 命名。

输入区提供：

```text
+5 属性模组数量   [−] 2 [+]
+10 属性模组数量  [−] 3 [+]
已规划 5/5 · 属性模组总加成 +40
```

- 单项范围为 `0–5`，两项之和不能超过当前可用属性模组位数量。
- T5 调整不提供数量控件，显示：`T5 护甲调整由计算器自动选择，不消耗能量，也不计入属性模组数量。`
- 计算前显示五部位真实能量、Socket 和功能 Plug 预检，不按部位名称硬编码 `+5/+10`。
- 候选按五个具体部位展示护甲调整、属性模组、其他模组占用、最终能量和阻断原因。
- 接受库存或升级候选只填入编辑器的五个护甲槽位并返回编辑页面，不立即保存或触发写操作。
- 返回编辑器后恢复自动配甲入口焦点；修改六维、模组或实例约束后旧候选立即过期。

## 保存与执行

选择库存或升级候选后，应用配装除了保存稳定 `result_id`、`candidate_id`、规则/来源 revision 和五个真实实例 ID，还要保存玩家已接受的逐件 Plug 意图：

- 护甲调整 Plug Hash。
- 属性模组 Plug Hash。
- 其他已规划 Plug Hash。
- 对应的护甲实例 ID、Socket 和能量账本指纹。

不需要把完整 Planner 搜索结果持久化，但必须保留足以重建和复核所选配置的稳定字段。理论和待刷缺口不能生成可执行实例绑定。

`穿戴此方案` 的执行链路继续遵守 `plan / confirm / execute / refresh`：

1. 用户申请应用方案后刷新账号、Manifest 和实例状态。
2. 重新读取五件护甲的能量、Socket、位置和当前 Plug。
3. 按保存的精确数量重新验证逐部位分配。
4. 任一实例、Socket、容量、Plug 身份或其他模组发生冲突时，整个旧计划失效并保持零写入。
5. 预检通过后才生成换装、转移和 Plug 写入步骤。
6. 执行后再次刷新并核对每个实例和 Plug，不只核对最终六维总数。

若 Bungie 当前能力不能写入某类护甲调整或属性模组，结果仍可保存为应用配装，但必须明确标记为“需要在游戏内手动设置”，不能生成假成功步骤。

应用配装穿戴成功并通过刷新核对后，才开放 `保存到游戏内槽位`。该操作生成独立发布计划，不能与 `穿戴此方案` 或游戏内视图的 `应用游戏内配装` 合并为同一个按钮。

## 状态矩阵

| 状态 | 页面行为 |
|---|---|
| 尚未设置数量 | 默认 `+5 × 0 / +10 × 0`，允许直接计算无属性模组方案 |
| 数量合法、能力未读取 | 保留输入，显示等待账号或规则数据，不提前承诺可达 |
| 逐部位预检通过 | 开放计算，显示可承载 `+5 / +10` 的部位摘要 |
| 精确数量不可安装 | 禁止把聚合数值当候选，显示短缺的模组类型和受限部位 |
| 计算中 | 保留输入；旧候选标记过期且不可选择 |
| 可达 | 显示逐件调整、属性模组和能量账本 |
| 不可达 | 显示六维缺口与模组/部位冲突，提供最近可行结果但不冒充满足 |
| 数据不确定 | 显示缺少的能量、Socket 或 Plug 数据，不开放执行交接 |
| 候选已接受 | 应用配装草稿保存实例和逐件 Plug 意图，仍未写入 Bungie |
| 执行前变化 | 旧计划失效、零写入，要求按当前快照重新计算 |
| 执行部分失败 | 停止后续步骤，逐件显示成功、失败和刷新核对结果 |

## 验收标准

1. 配装菜单明确保留 `游戏内配装` 与 `应用配装` 两个独立一级视图，不把两者合并成同一目录或来源筛选。
2. 游戏内配装提供 Bungie 官方槽位操作，并可提供明确标注的当前装备辅助操作；应用配装提供方案库、对比、创建、编辑和穿戴，两者使用不同主操作文案和写入目标。
3. 应用配装默认显示已保存方案和只读详情，首屏能够直接找到 `对比方案`、`新建配装` 与当前方案的 `穿戴此方案`。
4. 玩家能够选择 2–3 个应用配装进行差异对比；游戏内配装只作为字段可能不完整的参照快照，不改变身份。
5. 新建和编辑使用同一槽位式应用配装编辑器；DIM、攻略、当前装备和游戏内槽位复制均进入该编辑器，不建立平行页面。
6. 自动配甲只位于护甲区域，入口文案为 `按属性目标自动配甲`；它不是一级页面、方案类型或来源。
7. 玩家能够分别指定精确的 `+5` 与 `+10` 属性模组数量，且总数不超过实际可用安装位。
8. T5 护甲调整由计算器逐件自动选择，始终按零能量处理，并且不计入属性模组数量。
9. 两个 `+5 属性模组` 必须分配到两个具体不同部位，结果中可以逐件核对。
10. 求解器先扣除每件护甲的其他功能模组能量，再判断该部位能否安装 `+5 / +10`。
11. 属性模组成本与 Socket 兼容性来自 Manifest 和版本化规则，不按头、手、胸、腿或职业物品硬编码。
12. 精确数量无法安装时，不返回少装模组的伪满足候选，并明确说明短缺类型和受限部位。
13. 库存、理论、待刷和升级模式使用同一逐部位分配规则；`reachability` 复用该能力但不新增页面模式。
14. 候选账本明确区分基础值、大师杰作、护甲调整、属性模组、碎片和最终六维。
15. 每件候选显示护甲调整、属性模组、其他模组、能量容量、最终占用和 Plug 可用性。
16. 缺少能量、Socket、T5 或 Plug 数据时状态为不确定或不可执行，不使用默认值补造。
17. 修改属性目标、模组数量或任一部位其他模组后，旧候选立即过期。
18. 接受库存或升级候选后，应用配装草稿保存五件实例和逐件 Plug 意图，不持久化完整搜索结果。
19. `穿戴此方案` 能生成真实转移、来源角色释放、当前装备替换和 Plug 步骤；执行前账号或 Manifest 变化会使旧计划整体失效并保持零写入。
20. 应用配装穿戴并刷新验证成功后才能 `保存到游戏内槽位`；跨边界动作不自动同步或删除任一方案。
21. Bungie 不支持自动写入的 Plug 明确显示为手动设置，不报告假成功。
22. 配装页能够显示账号数据来自缓存、已过期、后台刷新、同步完成或失败；已有数据在刷新时继续可见。
23. 后台刷新不得改变当前一级视图、方案选择、编辑状态、候选、滚动位置或键盘焦点。
24. 宽屏、中等宽度和 `760px` 窄屏分别使用三栏、两栏和单页状态栈；窄屏不把目录、详情与编辑器纵向堆成长页面。
25. 每个页面状态都有初始焦点；选择器、自动配甲、穿戴核对和发布页面返回后恢复来源焦点，弹层关闭后不丢失键盘操作位置。
26. Web 与 Desktop 继续消费同一个共享配装页面，DIM 和 Wishlist 都不是运行依赖；DIM 导入只作为次级创建方式。
27. 游戏内槽位按三武器、五护甲、子职业和神器分组，10 条原始记录不再统一显示为“护甲与职业物品”。
28. 游戏内装备卡片能区分 Bungie 原始字段、账号快照补充字段和未定位状态；未定位实例不显示伪造装备名称。
29. Plug 展示保留 socket index，并区分真实 Plug、未设置 Plug 和无法解析的 Hash；不能把平铺 Hash 当作完整模组配置。
30. 游戏内配装页提供查看装备详情、已接通的转移/穿戴/模组编辑和复制到应用配装等辅助入口；每项入口都标明是否写入 Bungie 槽位，未接通的组合动作不使用假按钮占位。
31. 未来开放“替换并保存”时，必须先修改当前角色真实装备，再在最终 Snapshot 前确认会保存整个槽位，而不是只保存单件装备；当前使用“用当前装备覆盖槽位”完成显式 Snapshot。
32. 自动补齐、自动换护甲和属性优化可以从游戏内配装页发起，但必须进入应用配装/Armor Planner 辅助向导，不得伪装为 Bungie 原子槽位编辑。

## 风险与待确认数据

- Armor 3.0 的 gear tier、调整 Socket 和 Plug 成本需要以当前 Bungie Manifest 与真实账号响应复核；规则不完整时必须通过 `ArmorRuleset` 版本化维护。
- 异域护甲与异域职业物品可能存在不同调整范围，不能套用传说护甲的固定目标假设。
- Bungie 写接口是否支持目标 Plug、是否要求先升级能量或存在活动状态限制，需要由执行 Adapter 返回真实能力。
- 现有已保存应用配装可能只保存实例而没有逐件 Plug；迁移后保持可读，但在生成穿戴计划前要求重新计算或人工确认。
- 大规模候选加入部位级 Plug 状态后会增加搜索空间，需要通过可安装选项预计算、剩余槽位下界和目标可达上界剪枝，不能通过忽略能量换取速度。
