> 状态：✅ 改动完成，自验通过（2026-09-17），待用户复验（未提交）
> 现象（用户截图，原文「这个按钮交互对吗？数量对吗？？你先分析一下」，后续「对，一起修」）：
> 仓库 → 浏览装备，红框圈住三行的「perk 命中」分段按钮和行尾两个「完整」下拉。

喂进仓库页真正用的那几个投影函数复算，截图状态下的每个数字逐个对上：

另外，新勾上来源时的默认是「全部 / 不限」——截图里的 `2/2` 是用户自己一格一格点的，程序没有替他选。

## 二、缺陷一：点已经按下的那一段，会顺手清掉本行的「完整」

分段按钮是开关（`aria-pressed`），点已经生效的那一格，正常应当什么都不发生。现在的点击处理无条件把
本行的「完整」设回「不限」，于是：

1. 第一行：`perk 命中 2/2` 生效、`完整 6/6` 生效 → 列表 1 件（送魂者）。
2. 用户再点一下那格已经亮着的 `2/2 91`（取消、确认、手滑都算）。
3. 用户没碰右边下拉，`完整 6/6` 自己变回 `完整：不限`，列表从 1 件弹回 91 件。

用户只点了一格，屏幕上两处变了，而且被清掉的是他特意挑的完整档——会当成点坏了。这也不是必要的功能：
想取消 `完整 6/6` 有正规出口（在下拉里选「完整：不限」）。
**处置**：把「换档才清完整」这条规则收进更新选择的那一个函数——补丁里的 perk 命中档与当前相同时整条不动；
两个调用方（分段按钮、其他状态下拉）同时受益，不会两处各写一遍。

## 三、缺陷二：悬停与读屏在「部分命中」这一档把「命中」写了两遍

分段按钮左边已经挂着可见标签「perk 命中」，而工具提示又用 `perk 命中` 起头、后面接一句自带动词的说法，
于是鼠标停在第一行那格 `1/2 14` 上看到的是**「perk 命中 命中 1/2，14 件」**。
`0/x` 是「未命中」、`x/x` 是「全中」，只有部分命中这一档重字。缺陷成立，且是唯一一处这么写的。

## 四、顺带核出的规范漂移（用户「一起修」即采纳处置建议）

UI 规范第 233 行写着：「核心 Perk 或最佳组合的选项使用『命中 x/y / 未命中 x/y』和独立数量徽标，
不能显示成难以断句的 `2/2 110`；**悬停与可访问名称解释分子是命中数、分母是要求数**」。
现状三条对不上：

1. 按钮可见文字是裸键 `2/2` + 独立数量徽标，「命中 / 未命中」的说法只在悬停里（规范那句更早，
   2026-09-15 那次 `sync local changes` 把可见文字从「命中 2/2」改成裸键，规范没跟着改）；
2. 悬停里那句从来没有解释过分子与分母（全仓搜不到对应说法）；
3. 「已生效条件」里那条同样是裸的 `perk 命中：2/2`。

**定案（采纳处置建议）**：可见文字保持裸键 + 数量徽标——分段组左侧已经有可见标签「perk 命中」，
组内再写一遍「命中 2/2」是重复；规范那句改成记录这个结论，并把「悬停与读屏说话」的要求写实：
**一句话说清来源要求的项数与其中命中的项数**，一个函数生成，悬停与读屏共用，可见文字不重复它。
原先那个只产「命中 x/y / 未命中 x/y / 全中 x/y」的小函数随之删掉（删掉后无引用，不留死代码）。

## 七、验收判据

1. 第一行选好 `2/2` + `完整 6/6`（列表 1 件）后，再点一次已经亮着的 `2/2`：列表仍是 1 件，「完整」仍是 `6/6`。
2. 换成另一档（例如点 `1/2`）时，「完整」照旧退回「不限」——换档清完整这条不能一起改没。
3. 悬停任意一段：说明里能看出「要求几项、命中几项」，且不出现连着两个「命中」。
4. 按钮可见文字不变（仍是 `2/2` + 数量徽标）。
5. `pnpm typecheck` / `pnpm test:behavior` / `pnpm test:architecture` / `pnpm docs:check` / `pnpm test:quality` 全绿。
