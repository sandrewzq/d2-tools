## 口径（用户已定，执行时不得偏离）

1. **对用户不存在「DIM 愿望单」概念**——DIM 文本只是**数据来源格式之一**，与人工推荐 CSV 同级。面向用户不出现格式名。
2. **不存在硬编码来源与判定**：来源名一律取 `source_label`；判断只由来源规则产生。
3. **可见性对称**：一条规则覆盖的每个版本（普通版 / 专家版 / 失时版）在各自页面上都要看到它，无主次。**「减少显示」＝应用端错误。**
4. **导入身份 = 用户给的名字**，强制二选一：新建（必填名、不得撞名）/ 覆盖（同名，**全删全增**）。覆盖判定用命名，不用来源名 / 内容指纹。
5. **不做临时双写、不做自动迁移**（做法一）：读取 / 写入 / 状态门 / 管理面 / 导出同一次落地，落地后 **CSV 需用户重新导入一次**（DIM 侧不重导）。这条对外代价**已于 2026-09-17 告知用户并获得确认**。
6. 项目规则：**Agent 自动验证默认禁用**，只有用户明确要求时才跑本地测试 / 构建 / 打包。
7. **推荐跟着武器走，不跟着版本走（2026-09-24 已定）**：一条规则的适用 hash 集按**武器家族**（官方名去掉（专家）这类后缀 + 武器类型 + 栏位桶）展开到**全部版本**，不再按发布组归约；展开只落在**本来源没写过规则**的版本上（声明版本优先），不重复贴到已写过的版本；展开后逐 hash 用这一版自己的插件池自检，装不上的版本直接从规则里剔除（那版就不显示这条推荐）。CSV 与愿望单文本同一套做法，展开口径只留一份实现。六条来源决定与实测数字见〈同名匹配口径（2026-09-24 已定）〉。

## 架构目标（唯一判据）

### 分层与格式边界

```text
① 格式（允许不同）
   CSV 文件        DIM 文本
        │              │
② 解析 / 适配  ← 唯一允许按格式分支的层
        └──────┬───────┘
               ▼
③ 来源实例 + 规则（同一套模型）  一个格式可以产出多个来源实例
               ▼
④ 事实（同一套模型）
               ▼
⑤ 消费（同一套路径）判定 / 筛选 / 卡片 / 详情 / 排序
```

**允许出现在 ② 的差异**：字段映射、清洗、校验、来源实例切分。
**一律禁止出现在 ③④⑤**：`kind === 'dim'`、`startsWith("dim:")`、`sourceId` 前缀判别、`isDim*`、按类型写死的排序权重 / 文案 / 槽位名、格式名进事实主键。

### 不变量

**I1（核心）** 对任意来源事实，把来源类型 `dim` ⇄ `csv` 互换，判定、筛选、卡片、详情、排序的输出必须逐字段相同。仅允许来源名与署名文案不同。

**I2** 新增一种来源格式时，只允许新增 ① 与 ② 的代码；不得新增 ③④⑤ 的判定、筛选、排序分支。

**I3** 任何按来源类型（含 `sourceId` 前缀、`kind` 判别位、格式名进主键）分叉的代码都是缺陷，无论它当前是否可被用户观察到。

**I4** 同一格式产出多个来源实例必须是模型的一等能力；任何「一个格式 = 一个来源」的隐含假设都是缺陷。

## 一、名字 → hash：查找侧与校验侧两套口径（原 Bug #105，已改待重导）

**症状**：导入 `LGpig推荐表_导入模板.csv`（344 行）报「29 行异常将忽略」，其中 23 行给的是「无法根据官方中文名称找到可核对的武器；请补充武器 ID」。这 23 行的名字去掉空格后**每一条**都能精确命中——文件写 `黑桃 A`，官方名是 `黑桃A`。剩下 6 行是重名，见下一条。

**根因**：同一件事有两套口径。

| 位置 | 口径 |
|---|---|
| 校验侧 `normalizeName` | NFKC + 小写 + 删掉所有标点、空格、空白 |
| 查找侧 `normalizeSearchText` | 只 `trim` + 小写 |

导入的顺序是**先查 hash、后做校验**：`collectWeaponRecommendationDefinitionHashes`（`weaponRecommendationKnowledge.ts:289`）先按名字取定义 hash，再用这批 hash 加载定义池；名字查不到的行装不进池子，校验期遍历池子自然找不到它，于是提示指的方向（名字不对）和真实原因（查找口径太窄）正好相反。两条取 hash 的通路都落空：`searchHashes` 用 `instr(search_text, ?) > 0` 连续子串匹配，`getItemHashesByExactName` 是等值比对。

**不能靠「删掉中文与字母数字之间的空格」这条规则修**：资料库里有 12 条官方中文名自带空格（`5p 3AR`、`星旅者 7M`、`布瑞科技RWP Mk.II`……），按位置猜空格只会把本来对的名字改错。

**已改**：

- 新增 `packages/services/src/gameData/lookupText.ts:9` 的 `normalizeLookupText`（NFKC + 小写 + 删 `[\p{P}\p{Z}\s]+`），规则与原来的校验侧逐字相同；校验侧 `normalizeName`（`weaponRecommendationKnowledge.ts:1124`）改成它的别名，行为不变。
- 查找侧加**折叠名兜底**，原样比对仍排在最前：`searchHashes` 追加 `OR hash IN (...)`，并进同一条查询、一起参与排序与代表版本折叠；`queryItemHashesByExactName` 在等值查询之后补一轮折叠名等值查表。折叠表**惰性构建**：`search_documents` 里 kind=item 的全部名字建一次 `Map<折叠名, hash[]>`，本机 14406 行实测约 13ms，一个索引实例只建一次（`sqliteSearchIndex.ts:279`）。
- `memoryCatalog.ts` / `jsonCatalog.ts` 的 `getItemHashesByExactName` 同步改用同一份折叠，三个 catalog 口径一致；`searchIndex.ts` 的接口注释从「精确官方名」改成说明折叠规则。

**影响面**：只动 `packages/services` 的查找与校验口径，没有改导入流程、表头契约和错误文案。

**待办**：先 `pnpm --filter @d2-tools/services build`，再拿同一份 CSV 走一次真实导入，确认 23 行消失、总量对得上。这 23 行的 perk / 大师 / 起源特性栏位是第一次真正进入校验，若冒出别的提示属于新问题。

**回归覆盖**：`packages/services/test/gameData.sqliteSearchIndex.test.ts` 新增一个用例（夹具加一件官方名连写的装备 `Compact02`，断言 `Compact 02`、`compact-02` 在「取 hash」与「搜索」两个接口上都能命中）。用例写在现有测试文件里，没有新增测试文件。

**排查时踩的两个坑**：`world.sqlite` 的 `DestinyInventoryItemDefinition.id` 是**混合符号**存的——值 ≥ 2³¹ 时存成负数，< 2³¹ 时存正数，按固定 `hash - 2³²` 查会把一半武器查成「不存在」；`search.sqlite` / `world.sqlite` 的 hash 列同样分正负，SQLite 里直接写无符号数值查不到。

**用户定的六条**：

| ① | 赛季版本不同 | **匹配全部版本**。旧版本已经过时，推荐表针对的是新 perk 池（原始表怎么分版本，见下） |
| ② | 同发布组的孪生版本（如加速突击的两版） | **同样全部匹配**，与 ① 同一套展开 |
| ③ | 撞译（同名不同枪） | 用「英文名称」列区分，**有英文名就只按英文名匹配**（2026-09-24 改判，原定「中英文名都写就都要命中 / 并集改交集」）；只写中文名而这个名字横跨两个以上家族 → **拒导**，要求补「英文名称」。细分见下 |

**③ 的细分（2026-09-24 已定）：真撞译只有 2 组，「同一把枪的两代」另有 4 组**

全库 1318 个武器名按家族复算，同名跨家族的只有两种，区别在家族键里的武器类型（⑥ 不在下面这张表里——它的家族键相同，是同一家族内的两种枪）：

第一类的英文名是有效判据——两组的两把枪英文名互不相同，本机英文索引 `search-en.sqlite` 已核对。第二类不需要英文名，也不取最新：名称解析把两代一起补进基础集，家族展开本来就不跨弹药槽，最后由逐 hash 自检按各自插件池分开。原定的「取最新版本」要单独写一份发布组排序（`releaseGroupKeysForItemHashes` 现在就是「取最新发布组」，取消归约后这条行为只保留在这一档），从未落地，2026-09-24 用户改判为不做；真实预言这一档只写名字时两代都收，哪一代显示这条推荐由池子自检决定（写了「武器ID」的行仍以声明为准，不展开到另一代）。第一类的英文名是**严格判据、没有回退**：英文名写了却匹配不到，就按「找不到可核对的武器」报错，不悄悄改用中文名命中——不然撞译行还是会两把枪一起导进来。

**⑥ 弹药类型不同（2026-09-24 已定）：算第六种，CSV 单独加一列「弹药类型」，非必填**

弹药槽 = 动能 / 能量 / 威能，弹药类型 = 主 / 特殊 / 重型。`极高反射`（手枪，中英文名完全一样 `High Albedo`）：主弹药 `1197486957`（v500，框架 `适配点射`）/ 特殊弹药 `-1632507338`（v970，框架 `微型导弹框架`）。两版**同家族键**（`极高反射|item.weapon.sidearm|3|1498876634`）、同弹药槽（动能）、同图标，只有弹药类型与框架不同；perk 池基本不重叠——DIM 给主弹药版写的是 螺旋膛线 / 广口弹匣 / 杀人风 / 死亡寻觅者，LGpig 与 YXCR 给火箭手枪版写的是 脉冲增幅器 / 自动装填枪套 / 迷惑爆发 / 动能震颤。**所以不能像 ③ 的两代那样取最新**：取最新会把主弹药那版的推荐整条挂到火箭手枪上。Aegis 自己也拆成白弹（`shopping-primary`，分类「手枪」）/ 绿弹（`shopping-special`，分类「火箭手枪」）两行，给了两套推荐。

- 新列与「英文名称」同一条口径：**写了就要命中**，交集为空拒导；没写就不参与收窄。

**声明版本优先**（2026-09-24 拍板）：展开出来的规则**只落在本来源没写过规则的版本上**。愿望单文本把普通版和专家版分开写，不加这条约束就是 24804 个新配对（比 13527 多出 11277 个重复落在已写版本上），同一版本上会同时出现两条规则、「符合 n 套」从 1 变 2。加上之后计数维持现状，展开纯粹补漏匹配。

## 覆盖口径改判（2026-09-24）：自检不看栏位，两条链覆盖集逐条相同

**起因**：同一份 Aegis 数据、同一个生成脚本产出的两个导入文件，在应用里读出的覆盖数不同——推荐表列出 1072 把、心愿单列出 1077 把。用户的判据：结果要一样，且那 5 个差异版本要**被覆盖**，不是被剔除。

**改判**：逐 hash 自检回答的是「这条规则跟这个版本有没有关系」，不是「这版能不能整套装出来」。判据只看「这把枪上任意一栏能到达」，栏位不参与——推荐表每格都带栏位，愿望单文本只有一串 perk，按栏位判必然算出两个覆盖集。复算（本机只读副本，2026-09-24）：

| 口径 | Aegis 推荐表 | Aegis 心愿单 |
|---|---|---|
| 声明集 | 748 条规则 | 6009 条规则 |
| 展开不做自检 | 1659 个版本 | 1659 个版本（逐条相同） |
| 展开 + 自检（改判前，按栏位） | 1072 | 1077 |
| 展开 + 自检（改判后，任意栏位） | **1077** | **1077** |

（这两列数是**当时**的实现跑出来的；自检判据在〈第八批〉放宽成存在性、并跳过「大师杰作」之后，两侧都是 1600。）

差集：改判前「只有心愿单有」5 个版本、「只有推荐表有」0 个；改判后两侧差集 0 / 0。这 5 个版本是 `1856262127`（新玩意 v610）、`3240434620`（新玩意 v710）、`2187717691`（环形逻辑 v700）、`3381450498`（蒙恩 v730）、`3559361670`（力拔头筹 v700）。

**原始 manifest 取证**：这 5 个版本上规则要的两个 perk 全部落在**同一个**随机槽（例：新玩意 v610 的槽[4] 随机池＝墓碑 / 爆破专家 / 和谐 / 多杀弹匣 / 全面发展 / 敲打），一枪一槽只能装一个，那一套 roll 在游戏里不存在。「装不出整套」是真的，但它不是「这把枪不该看到这条推荐」——推荐跟着武器走。

**「这版装不出整套」去哪了**：不再由覆盖集表达，留给匹配期按各来源自己的匹配语义判（`csvRecommendationSource` / `dimWishlistSource` 的栏位判据照旧）。塞回覆盖集的后果是把整条规则从旧版本上抹掉，用户看到的就是漏武器，正是 #108 要修的。

**落点**：`filterItemHashesByOwnPerkPool`（`weaponRecommendationKnowledge.ts:1948`）的入参 `requirements` 只收 `candidates`，`VersionPerkPool` 只留 `everyHash` / `everyName`（`weaponRecommendationKnowledge.ts:1974`）；CSV 侧在 `resolveRuleRequirements` 里同判据调用（`weaponRecommendationKnowledge.ts:859`），DIM 侧去掉调用点里的 `slot: ""`（`dimWishlistValidation.ts:134`）。两条链此前正是靠这个空串一个按「任意栏位」判、一个按真实栏位判，才算出两个覆盖集。

**没做的**：把「这版配不出整套」标到界面上——要新增匹配状态词（`packages/core/src/community-perks/types.ts` 与 `packages/ui/src/recommendationMatchView.ts:127` 两处词表）与存储标记，本轮不做。生效需要在应用里重导两条来源。

**测试影响**：`packages/services/test/recommendationIdentityExpansion.test.ts` 的夹具每把枪两个特性槽都放 伏特弹 / 快速命中，两侧判据对它结果相同，断言（读取期与展开集逐条一致）不受影响；`packages/services/test/` 下没有按栏位判剔除行为的断言。

# 踩坑（复用，不要重犯）

1. **改了事实结构必须 bump 匹配算法版本**（现为 22），否则读到旧缓存。
2. **归一化会成批生效**：改数据形状时必须同时盘清所有「按来源类型或固定来源写死」的映射与文案——本轮陆续发现 7 处，每漏一处就是一次返工。
3. **`packages/*/test/**` 不在类型检查范围内**（`ui` 与 `services` 都是）：测试全绿 ≠ 结论成立。
4. **改完 core / services 必须重建 `dist`** 才能在下游看到真实类型影响（跨包 import 解析到 `dist/*.d.ts`）。
5. **删除范围必须对着当前文件状态复核**：一次 python 范围删除曾因早前的行偏移误删 `releaseGroupRank` 方法与 `isUnspecifiedRequirementName`。不要用正则做大段删除，按锚点整块替换并用 `git diff` 核对。
6. **先写会红的网再删代码**：本轮靠这个抓到两个真实缺陷——「只写名字」分支漏归约、`saveRecommendationDocument` 循环体误用旧变量导致规则一条都写不进去。**变异测试是证明网有效的唯一手段**（短接某分支，网必须变红）。
7. **布局假设跟着控件数走**：加减控件时同步检查宽屏与窄屏两处 `grid-template-columns`。
8. **事务内绝不能再 `openRecommendationDatabase`**：`ensureRecommendationSchema` 每次打开都跑一次 `BEGIN IMMEDIATE`，内层连接会等外层自己持有的写锁，5 秒 busy_timeout 后报 `database is locked`。`clearImportedRecommendationRules` 就是这样 100% 失败的（用户点「清空导入的推荐规则」必崩）。凡是「已持有连接」的调用方一律走 `...From(database, …)` 变体（如 `listRecommendationDocumentsFrom`）。**这个 bug 是判据复跑抓到的，不是代码评审抓到的**——重写后的测试一直没跑，等于没有网。
