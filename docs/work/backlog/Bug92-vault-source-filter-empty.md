# Bug #92：仓库里勾选任意推荐来源后整仓变 0 件——来源管理给出的键与事实层的键不是同一个

> 状态：🟢 已修复并自检通过（2026-09-16）
> 现象（用户截图，原文「没读取到数据」）：仓库 → 浏览装备，左侧勾上「sayalarry」后，
> 右侧「仓库整理 · 0 件 · 2 项条件」，位置筛选「仓库整理 0 / 当前背包 0」，
> 分段器「perk 命中 / 全部 0」。账号快照里有 1085 件、匹配缓存里 23 件命中该来源，界面却是 0。

## 核实：不是没读到账号数据，是来源白名单把全部事实过滤掉了

拿用户那份库的副本直接跑两个生产函数，结果如下：

```
来源管理给出的键： document:f865fb8c9deb9bee4b963157                （导入文档级）
事实层给的来源键： document:f865fb8c9deb9bee4b963157:f865fb8c9deb9bee （具名来源实例级）
两者的交集：       []
```

界面上的因果链是确定的：

1. 来源管理名册被当成**权威白名单**（`filterVaultRecommendationSummaryIndex` 只保留白名单里的来源事实）。两个键不相等 → 事实被全部滤掉，索引成空。
2. 来源行本身来自名册（所以它还显示着，文案是导入名「sayalarry」，不是事实层的「Sayalarry推荐表」），只是计数永远是 0。
3. 筛选器一旦有选中项，`allowedItemKeys` 就是空集，而这个空集被喂给**位置 / 槽位 / 类型 / 护甲套装**每一处计数——所以是整页全 0，而不是只少几件。

账号数据没问题：快照 1085 件、匹配缓存 764 条实例记录（其中 23 件命中该来源），都在。

## 根因：同一个「来源」，两半代码用了两种粒度，而且各自都写死了

| 半 | 粒度 | 键 | 出处 |
|---|---|---|---|
| 来源管理名册（管理面） | 一次导入 = 一行 | 文档键 | `readRecommendationManagementSnapshot` 按 `document_id` 分组，注释写「一份导入文档是一个可管理来源」 |
| 来源事实（事实层） | 一个具名来源 = 一行 | 实例键 | 两个适配器都以实例身份作 `source_group_id`，注释写「用户拍板：来源列表按来源名分多行，不按导入文件合并」 |

两处注释都写着「用户拍板」，方向却相反——这是粒度决策只落到了一层、另一层没跟上留下的漂移。两边的守卫测试也各钉各的：服务侧的对拍测试钉「一个具名来源 = 一行」（实例级），界面侧的对拍夹具却写死 `source_group_id: document:…`（文档级），所以谁都没红。

Bug #91 把来源管理区变成页面里唯一的清单之后，这个漂移才第一次露在用户面前：筛选器的行来自名册，事实却按另一个键登记。

## 处置：粒度取「一次导入 = 一行」，事实归队而不是改事实

两侧的键必须相等，这一点没有选择余地；有选择余地的是**粒度取哪一级**。定案取甲：

- **一行 = 一次导入**（已实施）。与来源管理区、与「删除 / 停用整份导入」保持完全一致；
  事实层**不动**，仍按具名来源登记（服务侧既有契约 `StoredSourceIdentity` 早已写明
  「筛选与选项用分组键，消费层据此合并同一份来源的多个实例」），由消费层把「这条事实属于哪次导入」归队。
  导入名就是行名（用户看到的就是「sayalarry」）。
- 乙案（一行 = 一个具名来源）未采纳：它要求来源管理区改成按来源名分多行，一份多注释段的导入会从 1 行变 N 行，
  「删除」的语义也随之变成逐来源删除。这属于可见行为变更，与本轮「别让用户先拍板、先让数据出来」的目标相反。

于是要做的只有一件事：**让管理名册把「这次导入下辖的具名来源键」带出来**（`fact_keys`），
消费层据此把事实归到对应的那一行，键统一换成管理面的键。事实层保持实例级，服务侧的既有权衡不受影响。

## 落地清单（甲案，已完成）

| 位置 | 改动 |
|---|---|
| `services/community/recommendationManagement.ts` | 名册每行多带 `fact_keys`：按存储里真实存在的实例算，不按前缀拼（键的写法不携带类型信息） |
| `ui/recommendationMatchView.ts` | `filterVaultRecommendationSummaryIndex`（直接拿管理键去比对事实键）换成 `attributeVaultRecommendationSummaryIndex`：按 `fact_keys` 摊出的对应表把事实归队，键换成管理面的键；键本来就相等时不改写对象，避免无谓打破下游缓存比较 |

## 验收判据

1. 仓库勾选任一已配置且启用的来源后，位置 / 槽位 / 类型计数不再全 0，命中件数与来源管理区给出的「当前账号影响 N 件」同源可核对。
2. 勾选来源的行名与来源管理区那一行的名字一致（不许一处显示导入名、一处显示来源名列的值）。
3. 停用 / 删除后，该来源不得再出现在仓库筛选里，也不得留下旧事实（现有白名单语义不回退）。
4. 新增守卫测试：服务侧断言「名册的每一行必须认领它下辖的全部事实键」，界面侧断言归队（换键、多实例归同一行、名册外的事实一律丢掉）；把它改回修复前的写法时这些测试必须变红——已逐条改坏验证（见上表）。
5. `pnpm typecheck` / `pnpm test:behavior` / `pnpm test:architecture` / `pnpm docs:check` / `pnpm test:quality` 全绿。
