# Bug #97：「有就行」的推荐命中后没记下是哪份来源，于是数不着、也筛不出

> 状态：🟢 代码已改并自验通过（2026-09-17），待用户复验

## 现象

用户截图提问「为什么影响武器数不一样呢」：仓库 → 推荐来源 →「已导入来源」里，
`DIMLGpigWeaponWishlist by moc` 一行写 **1679 条规则 / 422 把武器 / 当前账号影响 305 件**，
而左边来源清单上**同一份来源**写的是 **229**。

核实下来是两件事叠在一起：

1. **两个数字口径不同**——左边只算仓库，右边算全账号（仓库 + 角色身上 + 角色背包 + 邮政官），
   本来就不该相等。这不是缺陷，是设计。
2. **左边那个数还真的偏小**：仓库里被这份来源点到的 **72 件武器**没被算进去，
   而且按这份来源勾选筛选时**也筛不出来**。

可复现的动作（用户可自验，无需看代码）：

> 仓库页勾上「DIMLGpigWeaponWishlist by moc」→ 搜「加拉尔号角」→ **不出现**；
> 取消勾选 → 它出现，而且自己标着「符合推荐」。

同一把枪，一边说它符合这份来源的推荐，一边按这份来源筛选又筛不出来。

## 根因：两种格式的适配器对「武器级规则」处理不一样

DIM 愿望单里的**异域武器**条目写的是「有就行」——只有武器、没有 perk 要求。
导入后它们成为**武器级规则**（一条可定位的栏位要求都没有）。

两边拼「来源事实」时的写法不同：

| 适配器 | 对武器级规则的处理 |
|---|---|
| 人工推荐表格（CSV） | 每条规则都出一条来源事实，武器级规则的**要求列表为空** |
| 愿望单文本（DIM） | 拼来源事实时把「没有可定位栏位要求」的规则**整条滤掉**，只把这条规则放进 `weapon_level_recommendations` |

而 `weapon_level_recommendations` 里**只有来源的名字，没有来源的编号**
（`dimWishlistSource.ts` 拼来源事实那一段的 `.filter(({ requirements }) => locatable(requirements).length > 0)`）。

于是这类武器的比对结果变成「命中了、来源名字也叫得出来，但**说不出是哪份来源**」：
写进缓存的比对结果里只有来源名字，没有来源记录。

下游全部按**来源编号**工作——左边清单按编号计数、来源筛选按编号查事实。
查不到，就成了「数不着 + 筛不出」。

数字也对得整齐：仓库里被这份来源点到的 305 件里，
**233 件**走的是「有 perk 要求」的规则（有编号），**72 件**是「有就行」的（没编号）；
左边显示的基本就是那 233 件。这 72 件全是异域：加拉尔号角、黑桃A、蠕虫低语、狼王、
蒙特卡洛、玉兔、赴险者、越橘、伊邪那岐的重担……

## 处置

1. **DIM 适配器：武器级规则也出一条来源事实**（要求列表为空），与 CSV 适配器同形。
   匹配层本来就把「要求为空」识别成「有就行」并算作命中，所以修完之后
   命中条数、可选项数、覆盖状态这些**一个都不变**，只是比对结果里
   **多出一条「来自哪份来源」的记录**——这正是下游缺的那一样。
2. **缓存算法版本 22 → 23**：比对结果的形状变了，已缓存的行必须整体重算，
   否则修复落不到用户手里已有的数据上（这是仓库里既有的做法，版本号旁边逐条写着改了什么）。
3. **给缓存加一道失效判据**：`advanceVaultRecommendationMatchCacheRevision` 会把
   **所有**没受影响的行直接盖上当前版本号（为的是一次小改动不必全量重算）。
   但新旧两版若是**算法**变了（形状不同），盖号就等于把旧形状宣布成有效——
   修复会被这一次盖号悄悄顶掉，而且以后再改形状也会重演。
   做法：行里存下算法版本，**读缓存时核对它**（不是当前算法写下的行一律重算），
   盖号也只盖**同一算法版本**的行——否则版本号那一列会说一句假话
   （「这行是当前算法核过的」），而别处只信这一列时就会被骗过去。

## 不做（如实记录）

- **候选池那条路的同类缺口不动**：一份来源同时有候选池和「有就行」规则时，
  「有就行」那条仍不进来源事实。来源归属已由候选池给出，只影响命中条数的展示，本次不碰。
- **不动两个数字的口径**（左边只算仓库、右边算全账号）。这是设计，不是缺陷。
- **不改导入期校验、不改 schema 结构**，只动上面三处。

- 原计划的第 ③ 条本只想改「盖版本号」，写测试时才发现**只盖号不够**：读缓存那一步根本不看算法版本，

## 请用户复验

重新打包后进 仓库 → 推荐来源：

1. **打开应用后的第一次账号同步会比平时慢一些**——算法版本从 22 升到 23，缓存里的比对结果
   要整体重算一次（这是设计，不是卡住了）。之后恢复正常。
2. 左侧来源清单上 `DIMLGpigWeaponWishlist by moc` 那个数字应当**变大**（多出「有就行」的那批；
   它仍然只算仓库，所以不会等于右边的全账号数——这两个数字本来就不该相等）。
3. 勾上这份来源，搜 **加拉尔号角**：**应当出现**（修补前它不出现）。它现在既能被这份来源筛出来，
   也仍然标着「符合推荐」——之前是「标着符合、却筛不出来」，两句话互相打架。
4. 顺带可以试黑桃A、蠕虫低语、狼王、蒙特卡洛、玉兔、赴险者：修补前都是同一类。

**口径本身的说明同一天也补齐了（[Bug #98](Bug98-source-impact-scope-label.md)）**：
左边那个数（只算仓库）与右边那个数（全账号）差的那 13 件不在仓库里，
来源行现在把两个范围并排写出来（`仓库 N 件 / 全账号 M 件`），不必再靠「这是设计」来解释。
