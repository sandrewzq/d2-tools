> 状态：三个原型已冻结，应用待重建
> 更新时间：2026-07-23

## 当前收口记录

- 共享壳已固定为 `packages/ui` 的 `ProductShellHost -> AppShell`；Prototype、Web 和 Desktop 只提供页面内容、数据和平台 action，不再各自维护产品外壳。
- 首页、账号、仓库、配装、资料库和商人已删除 `presentation="archive"` 入口参数与 archive/default 双 JSX 分支，并将 archive 专用样式改为各菜单唯一的正式内容样式。
- 唯一视图继续消费原有 ViewModel、真实 action 和错误、加载、空、部分失败或禁用状态；首页仄轮换最多显示八件真实 Offer，账号页保留刷新、重新授权、写操作与活动反馈。

## 背景与问题

上一轮全应用视觉改造把 `archive` 视觉方案实现成了菜单内容层的第二套页面。Desktop、Web 和 Prototype 统一传入 `presentation="archive"` 后，原有完整页面虽然仍在代码中，但被简化分支替代，导致功能、数据和布局层级发生退化。

已经确认的直接问题包括：

- 首页丢失原有图标和完整商人预览，只保留了文字摘要。
- 账号页把按装备位置组织的数据拍平成两个列表，动能、能量、威能和各护甲槽位层级消失。
- 仓库页使用过大的物品卡，信息密度和单屏可见数量显著下降。
- 其他菜单也存在“原功能仍在默认分支，但 archive 分支未渲染入口、状态或回调”的风险。

本任务不是继续补齐第二套页面，也不是保留旧 DOM 后补 CSS。正式实现必须保留当前应用的完整功能契约，但抛弃现有应用的视觉结构和样式，按照三个冻结原型在 `packages/ui` 中重建唯一产品页面。

## 基线优先级

### 功能基线

以当前应用的 ViewModel、props、actions、adapter、IPC、真实数据规则、错误恢复和改版前完整工作流为功能基线。`presentation="default"` 页面可用于盘点遗漏功能，但其 DOM 和样式不是实现模板；必要时使用同 commit 的干净 clone 对照，不得直接复制旧页面形成第三套实现。

功能基线包含：

- 所有真实数据字段、加载状态、空状态和错误状态。
- 所有按钮、筛选、Tab、详情入口、写操作和回调。
- Desktop 的真实 IPC、账号 Session、商人缓存和后台任务接线。
- Web / Prototype 已有 adapter 与 mock 场景，不把 mock 数据写进产品组件。

### 全应用视觉基线

以下三个冻结原型共同构成唯一视觉真相：

- `docs/work/references/ui-prototypes/全应用视觉原型.html`
- `docs/work/references/ui-prototypes/统一武器详情原型.html`
- `docs/work/references/ui-prototypes/统一护甲详情原型.html`

三个原型决定全应用的布局、组件层级、尺寸、密度、颜色、排版、图标、状态样式、响应式行为、信息分组和视觉权重。现有应用的颜色、间距、卡片、页面 chrome、DOM 层级和 CSS 全部不作为兼容目标；与原型不一致的部分应删除或替换。

当前应用决定完整功能清单和真实业务行为。原型没有容纳现有功能时，先更新并确认原型中的位置，再实施产品页面；不得由实现者自行隐藏、删除或降级功能。原型出现当前应用没有真实能力的控件时，先确认需求与契约，不得伪造成功行为。

原型已补充统一数据工作台组件规范，正式实现必须遵守：

- 页面栏位只使用三档宽度：紧凑目录 200px、标准目录 240px、上下文栏 280px；窄窗口按同一断点收缩。
- 装备缩略图统一使用 44px 固定槽位，列表和卡片的水平内边距统一为 12px，避免跨页面图标起点跳动。
- 账号与仓库的浏览区域使用紧凑装备卡；配装、资料库和对比场景使用平面数据行；商人 Offer 才使用商品卡片。
- 蓝色只表达导航、选中和当前对象；绿色只表达成功、可用和主操作；黄色与红色分别表达警告和危险。
- 常规控件统一为 34px 高度，徽标、正文、辅助信息使用统一字号层级，不再由各页面单独缩放。
- 设置页和表单内容使用受控内容宽度，不把稀疏设置行横向拉满整个工作区。
- 统一规则已经同时检查 1920×1080 和 1280×800 的浅色、深色表现；正式实现继续按同一断点与密度收口。

全应用、武器详情和护甲详情三个冻结原型现在共用同一套基础视觉语言：

- `docs/work/references/ui-prototypes/prototype-design-system.css` 是三个静态 HTML 原型的唯一公共样式入口；页面内嵌样式只保留页面布局、领域内容和响应式差异。
- 三个原型及其依赖统一归档在 `docs/work/references/ui-prototypes/`；目录内的 `README.md` 记录原型入口、边框模型和向 `packages/ui` 还原的边界。
- 颜色、字号、圆角、控件高度、按钮、导航、字段、徽标、焦点、禁用、按下、减少动效和边框所有权规则只在该文件中维护。

- 深色与浅色使用相同的页面、chrome、panel、surface、边框和正文 token。
- 统一使用 `Segoe UI / Microsoft YaHei UI / system-ui` 字体栈、6px 外层圆角、2px 蓝色键盘焦点环和相同的按钮/徽标状态颜色。
- 武器与护甲继续共用档案工具栏、身份区、章节导航、正文分隔和实例操作栏的视觉骨架，不合并各自领域内容。
- 武器与护甲在 `1360px` 以下都把同 Hash 实例栏切换为抽屉，避免详情正文被压缩；抽屉必须高于原型控制栏，提供标题、关闭按钮、遮罩和 `Escape` 关闭能力。
- 武器与护甲的传说、异域、来源、AI、选中实例和写操作语义色继续保留，但不得改变蓝色选中、绿色成功、黄色警告、红色危险的全局规则。

### 颜色系统实施约束

三个原型必须使用相同的语义颜色职责，正式实现不得只复制基础 palette 后再由页面写死状态颜色：

| 语义职责 | 原型 token | 使用范围 |
|---|---|---|
| 页面与外壳 | `page`、`sidebar`、`chrome` | 应用底色、左侧菜单、顶部栏和详情工具栏 |
| 内容层级 | `panel`、`panel-2`、`surface`、`surface-2`、`section-bg`、`card-bg` | 主工作区、章节底色、列表行、卡片和弹出层 |
| 普通边界 | `line`、`line-strong`、`control-border` | 分隔线、结构边界和可交互控件边界 |
| 文字层级 | `text`、`body`、`muted` | 标题、正文和辅助信息 |
| 交互状态 | `hover-bg`、`selected-bg`、`selected-border`、`selected-fg` | 悬停、导航选中、Tab 选中和当前对象 |
| 业务状态 | `mint`、`amber`、`red`、`violet` 及对应背景 | 成功/可用、警告、危险和 AI 专属区域 |

实施时必须遵守：

- 蓝色只表示导航选中、当前对象和可跳转信息；当前菜单、当前 Tab、当前实例不得使用绿色。
- 绿色只表示成功、已应用、已激活、可用或主写操作，不作为普通选中态。
- 浅色主题不能复用 `#203445`、`#13202a`、`#0d171f` 等深色主题表面值；组件样式中不得新增对应的硬编码替代值。
- 普通正文与背景对比度至少达到 4.5:1；大量使用的辅助文字同样按 4.5:1 设计，不依赖 9px/10px 小字号掩盖低对比。
- 可交互控件边界与相邻表面的对比目标为 3:1；普通结构分隔线可以更弱，但不能承担唯一的控件识别职责。
- 浅色主题必须保留可辨认的页面、侧栏、主面板和卡片层级，不能用多个接近白色的表面让工作区重新粘成一层。
- 深色与浅色必须共用同一组语义 selector；不再为每个菜单或详情页维护独立的选中态覆盖规则。

三个冻结原型的组件层进一步收口为同一套配方：

- 控件尺寸只使用紧凑 `30px`、标准 `34px`、大号 `40px` 和主导航 `42px`。
- 圆角只使用控件 `4px`、面板 `6px` 和胶囊 `999px`。
- 普通按钮、主要按钮、危险按钮和 AI 按钮共享结构、尺寸、边框与交互状态，只保留语义颜色差异。
- 主导航与二级导航共用 `NavItem` 规则；分段选择器不再使用纵向导航的左侧选中线。
- 物品、商人、配装和账号实例等可选择对象共用 `SelectableRow` 规则，只使用选中背景和 1px 边框，不再使用左侧蓝色标记。
- 搜索、筛选、选择框和文本域共用字段边界、背景、圆角与悬停规则。
- 徽标、状态标签、卡片、数据行、表格、Callout 和 Overlay 使用共享尺寸及表面层级。
- 左侧语义色条只属于 Callout：蓝、绿、黄、红、紫分别表示信息、成功、警告、失败和 AI；导航、Tab、卡片、实例和普通数据行不得复用该色条。
- 武器与护甲继续共用档案工具栏、身份区、章节导航、操作栏、表格和弹出层配方；Perk、Roll、护甲属性、套装与模组保持领域专用结构。

边框必须按所有权而不是按页面分别定义：

- 同一个视觉边界只能由一个元素绘制，禁止父容器、子卡片和内部图标同时使用完整边框。
- 页面章节、左右栏和数据行只使用低对比结构分隔线，不使用圆角。
- 主菜单、二级目录、配装目录、商人目录和详情章节 Tab 属于可点击菜单项，使用低对比 `1px` 菜单边框和控件圆角；当前项使用选中边框与背景。
- 输入框、按钮和分段控件使用控件边框；分段控件只保留外层一圈，内部按钮只保留分隔线和选中背景。
- 装备、Offer、Perk、能力、套装和实例等独立对象使用对象边框；对象内部图标默认不再绘制第二层边框。
- 同一列表层级必须统一选择 Card 或 Data Row，不能一侧使用圆角卡片、另一侧使用水平分隔行。
- 武器与护甲配置列是布局容器，不是卡片；配置列取消外框，内部 Perk 或能力对象负责边界。
- Callout 可以使用左侧语义色条和中性对象边框，但不得和普通结构分隔线共用同一颜色或权重。

### 武器详情基线

武器详情是明确例外：

- 视觉、章节顺序、信息权重和主要交互以最新的 `docs/work/references/ui-prototypes/统一武器详情原型.html` 为冻结基准。
- 资料库定义、商人 Offer、账号实例、完整 Perk 池、本件 Roll、已选 Perk、同 Hash 切换和写操作必须继续使用真实数据与现有业务能力。
- 不允许在全应用收口时恢复旧武器详情布局，也不允许为了匹配全应用外壳删减最新武器原型中的信息。
- 资料库、仓库和商人必须复用 `packages/ui` 中同一套武器详情实现，不能按入口复制页面。

护甲详情继续遵守 `equipment-detail-and-knowledge-analysis.md`、[护甲详情冻结规格](../references/ui-prototypes/specs/armor-detail-layout.md) 和已确认的护甲原型；正式实现不得擅自增加目标值、最高属性、推荐模组或系统生成结论。

## 硬性约束

1. 三个冻结原型是唯一视觉验收基准；未经确认的视觉偏差都视为未完成。
2. 当前应用的旧样式、旧 DOM、旧 chrome 和 archive 页面全部抛弃，不得作为兼容目标或渐进美化基础。
3. 当前应用的数据契约、ViewModel、props、actions、adapter、IPC、状态与错误恢复是功能真相，必须完整迁入新 UI。
4. 每个菜单只保留一套产品 JSX；不得通过 `presentation`、`visualVariant` 或类似属性切换另一棵页面 DOM。
5. 每个菜单直接按原型重建现有 `*ContentView`。菜单完成时立即删除对应 `Archive*Content`、archive 分支和 archive CSS，不能拖到所有菜单结束后统一清理。
6. 不允许只替换颜色、token 或局部 CSS 后声称已还原，也不允许为了贴近原型而删除、隐藏或降级已有功能。
7. 原型未容纳现有功能时必须先更新并确认原型；原型控件没有真实能力时必须先确认契约，不得伪造成功回调或状态。
8. 不以 HTML 的 mock 数组、固定数量、示例状态、演示 toast 或假按钮替代真实 ViewModel、adapter 或 IPC 数据。
9. UI 实现进入 `packages/ui`；Desktop、Web 和 Prototype 只保留平台接线、真实数据回调、mock 场景和演示控制。
10. Prototype、Web、Desktop 必须消费同一棵共享页面，不得在平台壳复制结构或维护端侧视觉分支。
11. 不修改三个冻结 HTML 原型，除非用户先确认原型本身需要变化。
12. 产品组件不得硬编码来自某一主题的选中背景、选中边框、悬停背景或控件边框，必须把原型语义映射到共享 token。
13. 不 push；提交和远端操作必须由用户另行明确要求。

## 还原执行门禁

以下门禁用于防止把“清理 archive”或“补局部 CSS”误报为原型还原完成。它们是每个菜单切片的阻断条件，不依赖实施者自行记忆，也不能以赶进度为由跳过。

### 1. 开工合同

在改动任何 JSX、CSS 或平台接线前，必须把该菜单的四份对照写入本 backlog 的对应菜单小节或链接的菜单规格：

| 合同 | 必填内容 |
|---|---|
| 原型结构表 | 冻结原型中的区域、DOM 层级、视觉文案、信息顺序、边框所有权、尺寸、栅格与每个响应式断点 |
| 功能清单 | 现有 ViewModel 字段、真实数据来源、图片、加载/空/失败/部分失败状态、按钮、筛选、详情入口和写操作 |
| 绑定表 | 每个原型区域对应的真实字段、派生规则、action、权限、禁用条件和平台能力；明确 mock 专用内容 |
| 状态矩阵 | 正常、首次加载、刷新中、空、失败、部分失败、无权限、禁用、进行中及完成后的内容和可用操作 |

原型不存在现有功能的位置、或原型控件没有真实能力时，合同必须标为阻塞项。未经用户确认原型位置或真实契约前，不得开始页面实现，更不得伪造成功状态。

### 2. 唯一页面重建

- 原型决定产品页面的 DOM 结构、视觉文案、目录名称、描述、信息分组、边框所有权、栅格、尺寸和断点；旧应用只提供真实字段、状态和 action。
- 不得从旧页面的 copy、旧卡片、旧 DOM 或旧 CSS 推导视觉设计。原型与旧 copy 冲突时，必须先按原型建立新的视觉 copy 映射，再绑定现有数据。
- 菜单必须直接重建唯一 `*ContentView`，不得保留旧页面结构后覆盖颜色、边框或间距。通用组件只能在其 DOM 与原型组件层级一致时复用；否则应在菜单内重建。
- 在同一菜单切片中删除 `presentation="archive"`、`visualVariant`、`Archive*` 分支、旧 fallback/mock 页面和只服务旧视觉的 CSS。只删除入口但保留旧产品 DOM，或只加后置覆盖 CSS，都不算完成。

### 3. 视觉合同与真实数据分离

- 原型中的标题、描述、标签和信息顺序属于视觉合同，必须逐项还原；现有应用的旧文案不是视觉兼容目标。
- ViewModel、props、actions、IPC 和错误恢复属于功能合同，必须完整保留；原型 mock 数组、固定数量、演示 toast 与假成功反馈不能进入产品实现。
- 原型要求但当前没有真实能力的控件，必须显示真实的不可用原因或等待用户确认契约；不得擅自删改原型语义，也不得做点击后无业务效果的伪控件。

### 4. 完成前的视觉证据

- 每个关键原型区域必须使用稳定 `data-reference-id` 建立原型组件与产品组件映射；验收检查结构和计算样式，不以 class 名或中文源码匹配替代。
- 菜单完成前必须在亮色、暗色和 `1280px`、`980px`、`760px` 宽度下逐项对照冻结原型。重点核对文案、区域顺序、边框所有权、栅格、间距、字号、控件状态和横向溢出。
- 未完成截图或人工对照时，状态只能写“实现中”或“待视觉验收”；不得使用“已还原”“已完成”或将下一菜单作为前置菜单的后续步骤。
- 视觉对照发现旧 DOM、旧 copy、旧卡片边框、断点不一致或任何未确认差异时，菜单立即退回“对照中”，停止局部补丁，回到唯一页面重建。

### 5. 状态与报告约束

`docs/todo.md` 的 UI 切片只允许使用以下阶段：

1. `对照中`：四份合同尚未齐全，或存在原型/功能阻塞项。
2. `实现中`：唯一页面正在重建，旧结构尚未完全删除。
3. `待视觉验收`：功能与旧结构清理已完成，等待规定视口与主题对照。
4. `已完成`：视觉对照通过、真实功能无丢失、旧视觉分支已删除。

任何报告都必须区分“已实现”和“已验收”。没有视觉证据不得把实现状态描述为还原完成。

### 6. 冻结样式提取与双端验收门禁

以下规则用于阻断“按原型意图自行设计”以及“Prototype 看起来接近便宣布完成”的错误。它适用于 Shell、菜单、表单、详情和弹窗的每一个可见组件。

1. **先测量，后实现。** 改动某个组件前，必须从对应冻结 HTML 的目标视口读取该组件及其状态的最终计算样式；不得根据截图印象、文档摘要、旧应用 CSS、通用设计经验或实施者的理解补全数值。
2. **组件规格卡是开工前置条件。** 每个组件都要登记：原型 DOM selector / `data-reference-id`、普通与选中/禁用/加载等状态、目标视口和主题、DOM 层级、`display`、尺寸、margin、padding、gap、边框四边、圆角、背景、阴影、字体、图标尺寸、溢出规则和响应式变化。任何未知值必须标为阻塞项，不能猜测后实现。
3. **边框按边逐项登记。** 不得只记录“有边框”或“线性导航”这类概念描述；必须明确外框由谁绘制、每个子项绘制哪一条分隔线、当前项是否有边框/阴影/左侧标记，以及容器是否有 margin、padding 和圆角。
4. **状态是独立规格。** 普通、hover、focus、active/current、disabled、loading、error、空态与长文案换行分别是独立验收项。不能把普通项的样式外推为选中项，也不能用“更合理”的交互样式替换原型。
5. **先冻结 Prototype，再验 Desktop。** Prototype 只用于确认共享 UI 能按组件规格卡还原，不能证明产品完成；Prototype 与冻结 HTML 有任一差异时不得进入 Desktop。随后必须在 Desktop 实际运行页面复核同一组件、同一主题、同一视口和同一状态，确认其加载的是当前共享 UI 与当前 CSS 资源。
6. **Desktop 是唯一完成依据。** 只有 Desktop 的截图、最终计算样式和 CSS 规则来源均与冻结原型规格卡一致，才允许标记该区域验收通过。Web 与 Prototype 通过只能记为各自的中间证据。
7. **证据必须可追溯。** 每个验收区域记录：冻结原型截图/计算值、Prototype 截图/计算值、Desktop 截图/计算值、差异结论和日期。没有三者的明确记录，状态不得从“对照中”升级。
8. **发现差异立即回退。** 任何一个区域出现旧 DOM、旧 CSS、加载旧 bundle、样式导入顺序覆盖、未记录数值、边框归属不同或断点不同，立即把该区域和所属菜单退回“对照中”。禁止只加高优先级覆盖修补，必须先删除冲突来源或重建对应 DOM。
9. **禁止提前外推。** 一个 Shell 区域通过不代表整个 Shell 通过；一个主题、一个视口、一个页面或一个状态通过不代表其他组合通过。未逐项登记的组合一律视为未验收。

最小组件规格卡模板：

| 项目 | 必填证据 |
|---|---|
| 目标 | 冻结原型文件、hash / 页面状态、视口、主题 |
| 原型结构 | selector、DOM 层级、`data-reference-id`、可见状态 |
| 原型计算值 | 布局、尺寸、间距、边框四边、圆角、文字、图标、颜色、溢出 |
| 产品映射 | 唯一产品组件、稳定标识、真实字段/action、CSS 文件与 selector |
| Prototype 证据 | 同视口/主题/状态截图和计算值差异结论 |
| Desktop 证据 | 同视口/主题/状态截图、计算值、实际加载资源与差异结论 |
| 结论 | 通过 / 对照中；差异的责任区域和后续动作 |

| 大仓库 | 保留分段渲染上限和“加载更多”，搜索时展示全部命中 |
| 定位请求 | 清空冲突筛选并回到筛选列表，不丢弃当前标签与写操作能力 |
| 写操作禁用、进行中、失败 | 批量解锁/转移按 `cleanupActions.writeActionsEnabled` 禁用；进行中和失败反馈继续由 `useVaultBatchActions` 呈现 |
| 无重复、无推荐、无目标规则 | 分别使用真实空态；不补示例重复组、推荐命中或规则 |

- 保留筛选列表、清理工作台、同名对比和推荐数据四个工作流。
- 保留搜索、分类、位置、弹药、标签、锁定、框架、护甲属性规则和排序。

- 物品图标、名称、位置、类型、光等、Perk 摘要、标签和主要状态必须在主行可扫读。
- 次级操作可进入行尾操作区或详情，不允许操作按钮把每张卡撑高。
- 筛选列表只保留左侧筛选与结果两栏；单件操作进入详情，整理摘要只保留在清理、同名对比和推荐工作流中。

验收重点：1920×1080 下显著增加首屏物品数量，同时保留原有筛选和整理能力。

## 验收清单

### 全局

- Desktop、Web、Prototype 消费同一套菜单内容组件。
- 每个菜单只有一套产品 JSX 结构。
- 页面结构、尺寸、密度、颜色、排版、图标、状态和响应式与对应冻结原型一致，不只是配色接近。
- 新视觉没有减少功能、状态、数据字段和操作入口。
- 产品组件不包含从静态 HTML 复制的 mock 数组、固定成功状态或演示交互。
- 已完成菜单不再加载旧样式兼容层，也不存在 archive 专用组件或 CSS。
- 左侧菜单、顶部栏和正文之间没有多余缝隙。
- 明暗主题、窄窗口和长中文文案不发生遮挡或错位。
- 全应用、武器详情和护甲详情的导航、Tab 与当前对象使用同一套蓝色选中语义。
- 浅色主题下辅助文字可读、控件边界可辨，选中态不存在深底深字或依赖深色主题硬编码的情况。

### 首页

- 原有图标恢复。
- 日落打击、轮换突袭和轮换地牢使用真实周报 `entries`；突袭和地牢必须支持同周多项，不得只取数组第一项或保留固定单卡。
- 周报快照未确认限时活动或加成时显示未确认状态，不使用上周内容或手写活动填充。
- 仄首页只展示主商人“多样奇异优惠”的 8 件本周轮换，图标、类型、价格与轮换数量一致；不得混入子库存或账号实例状态。
- 每件轮换商品显示 Manifest `classType` 对应的职业备注；首页不得再显示“职业商品与时效”“职业商品按当前角色显示”或“当前角色库存”汇总文案。
- 仄两个子库存和完整库存继续通过商人页入口查看。
- 周常、轮换、实时情报和商人入口完整。

### 商人

- 地点目录、商人数量、状态和库存数量来自 `vendors-page-snapshot.js`，不保留固定七商人目录或手写开放状态。
- 仄及其他商人只渲染真实 `contentSections`；没有任务、声望进度、子库存或刷新时间时留空或显示保守状态，不生成替代数据。
- 商品卡使用真实 `itemHash`、`iconUrl`、类型、数量和一种或多种价格，不复用账号实例的光等、标签、催化进度、锁定或大师杰作字段。
- “角色维度请求”只用于解析当前可见 Offer，不对外描述为角色背包或“当前角色库存”。账号、角色和公会作用域继续由当前应用 ViewModel 决定。
- 静态原型是冻结视觉与代表性真实状态，`packages/app` 的商人 ViewModel 和 `packages/ui` 的共享商人页仍是功能真相；不得从 HTML 反向复制业务编排。

### 设置

- 设置目录保留八个当前分区及每项 hint，不把设置压缩成只有标题的导航。
- 概览同时显示账号、资料库、Bungie、AI、应用版本和后台任务，并保留应用更新来源、上次检查、下载进度、下载页和更新诊断入口。
- 账号和资料库保留完整状态、上次读取、自动检查、失败保留旧数据、当前/最新版本及手动操作规则；不得只显示一个固定日期或“可用”。
- Bungie 和 AI 配置保留字段帮助、加载/保存/测试状态、模型列表与 light.gg 能力边界；密钥只显示掩码，不写入静态快照。
- 备份明确包含和排除范围、回滚备份及整目录迁移风险；诊断保留结果/类型筛选、时间、真实消息、空状态和失败记录复制诊断入口。
- 颜色主题和界面密度继续由全应用原型工具控制，不冒充当前共享设置页的业务配置。

### 账号

- 装备与背包按位置分类。
- 角色切换和全部写操作保留。
- 活动、材料和邮政官可正常进入。

### 仓库
