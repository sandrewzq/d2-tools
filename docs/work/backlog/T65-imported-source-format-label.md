# T65：「已导入来源」的每一行显示来源格式（推荐表格 / 愿望单文本）

> 状态：🟢 代码已改并自验通过，待用户复验（2026-09-17）
> 用户诉求（截图 + 原文「已导入这里应该显示类型」，随后在选项里拍板）：
> 来源管理区里每一行要能看出这份来源是**推荐表格**还是**愿望单文本**。

## 为什么是这两个词

用户在「哪一种类型」的选项里选了**来源格式**，并给了两个面向用户的说法：

| 存储里的来源类型（`kind`） | 界面显示的来源格式 |
|---|---|
| `csv`（人工维护的推荐表格） | 推荐表格 |
| `dim`（愿望单文本） | 愿望单文本 |

这两个词是**内容描述**，不是格式名（不出现 `DIM`、`CSV` 这类内部/格式称呼），
符合既有口径：「DIM 愿望单只是数据来源的一种格式，不是面向用户的概念」。

## 名字从数据来，界面不判断格式

- 数据来源是**存储里的 `recommendation_source_instances.kind`**：导入时由各格式的适配器写进去，
  读取期一直没被用过（管理面的查询没有 select 它）。这次把它读出来用。
- 格式名 → 面向用户的说法只在一张表里写一次（`recommendationSourceKindLabels`），
  表用 `Record<RecommendationSourceKind, string>` 定义——**新增一种格式时类型上必须补一行，
  否则编译不过**，「新格式没名字」会当场暴露，而不是在界面显示一个内部代号。
- 服务层把算好的字符串（`format_label`）交给界面，界面**照原样显示**：
  这正是「判定只做一次、消费方拿到的就是结论」的既有做法（同文件里的「清空已导入的推荐规则」摘要就是先例）。
  界面因此不需要认识任何一种来源格式，也没有任何 `if (格式 === …)`。
- 结果就是：**来源行显示什么，与新格式无关**——加一种格式只需在表里补一行名字，界面代码一行不动。

## 明确不做

- **不给任何元素加「按格式」的样式钩子**（例如 `data-source-format`）：T56 已经拆掉过一处
  `[data-recommendation-source="dim"]` 的样式分叉，不再往回加。格式名只当**文字**显示。
- **不改导入入口的名字**：入口仍叫「人工推荐表格 / 导入表格文件」和「导入愿望单文本文件」——
  入口是用户挑格式的地方，与来源行的「这份是从哪来的」是两回事。
- **不做多格式混合文档的处理**：一份文档 = 一次导入 = 一种格式（文档键只由名字决定，覆盖是整份替换），
  所以同一份文档下的实例类型必然一致。查询按 `GROUP_CONCAT(DISTINCT s.kind)` 读出全部并逐个换名，
  这是同一行代码在长度为 1 时的表现，不是一条永远走不到的分支。

## 验收判据

1. 「已导入来源」每行在来源名下面显示「格式 · 状态」，例如「推荐表格 · 已启用 · 2026-09-17 09:00」。
2. 推荐表格来源显示「推荐表格」，愿望单文本来源显示「愿望单文本」——**同一屏里两种都在时各自正确**。
3. 名字里带「愿望单文本」的推荐表格来源，仍显示「推荐表格」（显示的是数据里的格式，不是名字）。
4. 详情弹框标题那一行同样带格式名，与列表行一致。
5. 界面源码里没有根据来源名 / 链接 / 来源键猜格式的写法；存储里的类型是唯一输入。
6. 五道闸门与 `pnpm check` 全绿。
