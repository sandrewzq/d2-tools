# T64：导入时认出「每栏任选其一」的展开写法，不再把摊平写的行报成问题行

> 状态：🟢 代码已改并自验通过，待用户复验（2026-09-17）
> 缘起（用户原话）：「一把武器9行改成合集不就行了吗」

## 问题：用户看到的

贴 `DIMLGpigWeaponWishlist by moc.txt` 的链接后，预览卡弹出红框：

> **7291 行将忽略，涉及 257 把武器**
> 第 26 行 · 光鳃之调 · 超充弹匣、羸弱能量球：落在同一栏，不可能同时拥有。

红框里 7291 条几乎全是「同一栏写了两个 perk」。看起来像这份文件坏了一大半。

## 实测：这份文件到底写了什么

（把文件下载下来逐行数过，数字可复核。）

| 事实 | 数字 |
|---|---|
| 规则行 | 8985 行（另有 108 行只写武器、不写 perk） |
| 涉及武器 | 314 把写了 perk，其中 258 把是一把枪写多行 |
| 3 个 perk 及以上的行 | 7306 条 |
| 其中「被同一把枪的某条两 perk 行整个包含」 | **7306 条，例外 0** |

最后一行是这件事的关键：一行要求的 perk 越多，能命中的越少；被更短的一行整个包含，就意味着**它不带来任何新命中**。所以这些长行对结果毫无影响，它们只是作者把「每栏任选其一」摊开写时的产物。

作者自己也是这么写的。文件里第一把枪「光鳃之调」写了 9 行，注释里写着「优先 perk：医治 + 超充弹匣」「震颤反馈 + 羸弱可以用来清怪」。9 行里：

- 留下的 4 行正好是「第一个位置：医治 / 震颤反馈；第二个位置：超充弹匣 / 羸弱能量球」四种搭配；
- 被丢掉的 5 行，每一行写到的 perk 都已经被上面 4 行里的某一行整个包含（例如「医治 + 震颤反馈 + 超充弹匣」被「医治 + 超充弹匣」包含）。

**这不是这份文件的孤例，历史代码里早有结论**（归约那段的注释记着：「作者常把『每栏任选其一』展开成笛卡尔积逐行写出（实测 Aegis 863/863、小棒猪去冗余后 257/257 都是）」）。257 正是预览里那 257 把武器。

## 结论：该改的是报法，不是数据

读取期本来就把同一把枪留下的行**归约成「每栏任选其一」**（这已是既定行为，见 `ui-specs/application-workspaces.md` 与 T56）。导入期没做同一件事，于是把展开写法摊平时多写的行逐行报成了问题行——**用户要的合集其实一直在，只是报错了地方**。

被丢掉的那些行，内容已被留下的某一行覆盖，丢掉不改变任何匹配；把它们叫「问题」是误导。

## 处置：导入期也按「一把枪」看

一把枪的行同时满足下面三条时，把它被丢掉的行记为**展开写法的冗余**（不再计入问题行，也不计入跳过行数）：

1. **留下的行本身构成一组完整的「每栏任选其一」候选**（用与读取期同一份归约判据，且至少两种搭配——单独一条 Roll 不算「一组候选」）；
2. 被丢掉的那一行属于**「同一栏写了两个 perk」**这一类；其余三类（写法不成立、同行重复写同一个 perk、perk 查不到）照旧按笔误报——曾经的第四类「归不到唯一栏位」已由 Bug #102 删除（归栏改为按书写顺序消歧，恒为单值）；
3. **这一行写到的 perk 已被留下的某一行整个包含**——这一条是「丢掉它不改变任何匹配」的可验证依据，也是「展开写法」与「真写错了一行」的分界。

预览对应改成两块：一块中性说明（几行是展开写法的冗余、涉及几把武器），红框只留给真正的笔误（第 2 条排除掉的那三类，以及不属于展开写法的同栏冲突）。

## 不做（本次范围外）

把合集**作为一条规则写进库**（来源管理里显示「一把枪一条」而不是 6 条规则）。读取期已经把它当合集用，条数不影响匹配结果；而改写入形状会动到导入的落库链路与它的测试，正撞上 T56 的存储切换，留到那轮落地后再单独定。

## 判据

1. 这份文件导入时不再出现红框；预览给出「展开写法的冗余」行数与涉及武器数，可导入条数与**实际写进库的行与今天逐条相同**（认不认得出展开写法，只影响报数，不影响数据）。
2. 不属于展开写法的同栏冲突（留下的行凑不成一组候选、或该行内容未被任何留下的行覆盖）仍按问题报，理由与行号照旧。
3. 三类真笔误（写法不成立 / 同行重复 perk / perk 查不到）报法不变——展开写法的识别不吞它们。（「归不到唯一栏位」这一类已由 Bug #102 删除。）
4. 资料库里查不到这把枪的定义时照旧一行都不判（fail-open）。
5. 五个闸门全绿。

## 落地清单

2. **改**：预览类型与主进程预览构造，把两个计数带出去。
3. **改**：预览卡与导入反馈文案——中性说明一行，红框只在真有笔误时出现。
4. **测试**：展开写法识别（含光鳃之调那 9 行的真实形状）、三条反例（凑不成候选 / 未被覆盖 / 三类真笔误不吞）、fail-open 不变；预览卡展示与红框出现条件。
5. **改文档**：`ui-specs/application-workspaces.md`（`DIM Wishlist 预览…` 那段加判据）、`user-guide.md` §8.3、`development.md` 按需。

### 改坏清单（实施中自己踩的坑，如实记）

1. **删掉一处假守卫**：`expansionRowsFor` 里原本写了 `if (entries.length < 2) return null;` 来挡「单独一条 Roll 不算一组候选」。变异成「至少两条才算一组候选」后测试仍全绿——因为共享的归约判据本身就对少于两条组合返回不了池子，这道守卫是死代码。已删，改为注释说明这条判据不必另设守卫（判据 1 里「至少两种搭配」仍由归约判据本身保证）。
2. **删掉一处不可达防御**：`isCoveredByKeptRow` 里的 `keptPerkHashes.length > 0 &&` 同样不可达——留下的行都通过了完整候选判定，必然带 perk。已删并在文档注释里写明这个前提。
3. **变异暴露出 UI 只覆盖了链接这一条路**：「本地文件提示把展开冗余也说成有问题」一开始没被杀掉，因为用例只走「从链接同步」。补了一条走「导入愿望单文本文件」的用例（本地文件路径的提示语气与链接路径必须一致）。
4. **变异暴露出守卫写得太松**：「预览把冗余并进问题计数」一开始没被杀掉——`toContain("skipped_row_count: filtered.skipped_row_count")` 对 `skipped_row_count: filtered.skipped_row_count + filtered.merged_row_count` 同样成立。全部守卫断言改成按行锚定的 `toMatch(/^\s*…,$/m)`。这是 Bug #92 记过的同一个失真模式。
