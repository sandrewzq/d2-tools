# 商人结构、覆盖与官方获取来源

> 状态：Backlog
> 更新时间：2026-07-15

## 目标

统一商人页面结构、商人覆盖和 Bungie 官方获取来源。用户应能确认商人当前卖什么、库存属于哪个页面、刷新信息是否可靠，以及官方数据是否提供了某件装备的获取来源。

本需求负责商人解析和官方来源事实，不负责装备详情的信息架构、实例比较、推荐 Roll、知识库或 AI 分析。后续能力见
[装备详情与知识分析规格](../references/equipment-detail-and-knowledge-analysis.md)。

## 当前基础

- 仄及其子库存、价格、声望和等级奖励已经可用，并已作为统一商人结构的首个配置接入。
- 仄、萨瓦拉、浪客、枪匠和霍桑已经使用统一商人结构配置。
- 当前公共商人、登录后商人库存、公共活动和 Manifest 来源提示已经有基础读取能力。
- 账号拥有状态能够汇总仓库、角色背包、已装备和邮政官中的真实实例。
- 商人 Live 库存能够补充完整路径，例如“浪客 → 聚焦破译 → 武器”。
- 全应用静态原型的商人页使用 `docs/work/references/ui-prototypes/data/vendors-page-snapshot.js` 保存当前 `VendorsPageModel` 的真实冻结投影。原型只渲染最终目录和 `contentSections`，不复制父子 Vendor 编排，也不允许回退到通用账号装备 Mock。

### 已合并人工核对结论

- Manifest 的分类、条目数和隐藏子 Vendor 只说明候选结构，不等同于当前页面、当前库存或实际售卖数量；所有当前可见性、价格、Roll、属性和进度仍以 Live Vendor 数据为准。
- 空分类、帮助页、引导页、未命名历史条目和未被 Live 数据返回的预览 Vendor 必须归为内部或条件定义，不能生成页面结构。
- 父入口、子库存和服务通过 Live 分类、Manifest 分类 identifier 与 `previewVendorHash` 组合识别；隐藏代理定义不能单独渲染为玩家可见页面。
- 同名商人不得按名称合并：高塔仄 `2190858386` 与 30 周年仄 `3442679730` 是不同商人；高塔仄固定保留声望与等级、主库存“多样奇异优惠”及两个子库存 `537912098`、`3751514131`，但只在 Live 返回时展示。
- 武器商人的售卖 Roll、护甲属性与等级奖励数量必须使用当前 Live 数据，不能用 Manifest 候选 Perk、定义条目数量或历史截图补全。

## 统一商人结构

所有商人页面统一组合以下四种结构，不再维护每个商人的独立解析流程：

1. 声望与等级：声望进度、等级、重置次数和等级奖励。
2. 售卖库存：当前页面直接售卖、兑换或领取的物品。
3. 子库存：由父入口进入的库存，可递归嵌套。
4. 任务：任务、悬赏和已放弃任务。

作用域、出现条件、购买动作、刷新周期、展示方式和递归保护是结构配置，不新增页面结构类型。

商人事实规则：

- 左侧目录严格保持“地点 → 商人名称”两级；业务类型、库存类型、推荐数和读取状态只在商人详情中表达，不作为导航分组。
- 当前是否出现、当前库存和购买状态以授权后的 Bungie `Destiny2.GetVendors` Live 数据为准。
- `DestinyVendorDefinition` 只用于名称、候选页面和周期分类，不能证明商人当前在线或商品当前可买。
- 优先使用 Live `nextRefreshDate` 或商品级 `overrideNextRefreshDate`；没有 Live 时间时只保留保守周期，不生成精确刷新时间。
- Manifest 候选商人应动态抽取，产品白名单只能控制优先级，不能冒充完整官方清单。
- 单个库存或定义不可读时局部降级，不影响其他商人。

## 商人与 Offer

一个装备可以有多个商人来源，一个商人也可以通过多个子库存或分类售卖同一装备。

商人是来源主体，具体售卖项是 Offer：

```text
装备
├─ 商人 A
│  ├─ Offer 1
│  └─ Offer 2
└─ 商人 B
   └─ Offer 1
```

商人来源保存：

- 商人名称与 `vendorHash`。
- 所在地点。
- 数据查询时间与刷新时间。

Offer 保存：

- 子库存或分类路径。
- 售卖物品 `hash` 和售卖项索引。
- 一种或多种货币价格。
- 当前售卖 Roll 或护甲属性。
- 实际大师杰作和已安装模组；接口未提供时留空。
- 职业限制、购买条件和数量限制。
- 当前账号是否满足条件、材料是否足够和 Bungie 返回的失败原因。

职业或角色 ID 不是来源：

- 部分 Vendor 接口需要角色 ID 只是查询上下文，不形成“角色商人”这一业务概念。
- 武器通常不限制职业，护甲职业限制属于装备或 Offer 条件。
- 通过多个角色查询到同一 Offer 时按商人和 Offer 合并，不重复生成来源。

## 官方获取来源

### 结果与查询状态

来源业务结果只有两种：

- `known`：至少查询到一条 Bungie 官方来源证据。
- `unknown`：所有要求的官方数据检查完成，但没有来源证据。

查询状态独立记录：

- `complete`：要求的官方数据均查询完成。
- `partial`：已经得到部分结果，但部分官方数据查询失败。
- `failed`：无法形成可信来源结果。

只有 `unknown + complete` 才能显示“来源未知”。查询未完成时显示“来源查询未完成”，不能把网络或缓存错误伪装成来源未知。

### 可接受的官方证据

1. Manifest 官方来源提示：物品、收藏品或关联定义中的 `sourceString`。
2. Bungie 当前商人库存：公共或登录后 Vendor Live 数据直接返回该装备。
3. Bungie 当前活动奖励：里程碑、任务或奖励结构直接包含装备 `hash`。

以下内容不能改变来源结果：

- 社区攻略和第三方掉落表。
- AI 推测。
- 来源文本关键词推断。
- 账号已经拥有该装备。
- 装备所在角色、背包、仓库或邮政官位置。

Manifest 来源提示不能单独证明当前仍可获取。商人或活动 Live 数据命中时可以表达当前在售或当前奖励，但不能把 Manifest 文本统一改写成“当前可获取”。

### 多来源与证据保留

- 一个装备可以同时保留多个商人、活动和 Manifest 官方提示。
- 当前商人来源和 Manifest 官方提示同时存在时全部保留，并明确区分实时事实与官方文字提示。
- 同一商人下不同价格、Roll、属性、子库存或购买条件的 Offer 分别保留。
- 不维护“历史来源”“当前不可获取但仍有效”或根据关键词生成的轮换分类。

### 时效

- 商人 Offer 必须记录 `checkedAt` 和可用的 `refreshAt`。
- 刷新点之前可以标记当前售卖。
- 经过刷新点但尚未重新查询时，只能表达“上次查询时在售，待重新确认”。
- 重新查询未命中后移除当前 Offer，不把它转成历史售卖记录。

## 账号拥有边界

账号数据只证明是否拥有和实例位置，不能反推出获取来源。

账号拥有汇总包含相同 `hash` 的真实实例：

- 已装备。
- 角色背包。
- 仓库。
- 邮政官。

收藏解锁、已经失效的配装引用和没有实例 ID 的定义记录不计入拥有数量。完整实例内容和详情复用规则由
[装备详情与知识分析规格](../references/equipment-detail-and-knowledge-analysis.md) 负责。

## 当前实现与需要收口的差异

当前代码已经能读取 Manifest 来源、Vendor Live 命中和公共里程碑线索，但仍有以下旧模型需要移除：

- `current / historical / unknown` 获取分类。
- 把 Manifest 来源命中归为 `historical` 的推断。
- `character_vendor` 对外显示为“当前角色商人售卖”的文案。
- 根据铁旗、试炼、夜幕、轮换、传承等关键词推断来源状态。
- 把商人价格、刷新、售卖 Roll 复制到多个详情区块。

内部可以保留“通过登录角色查询 Vendor”的技术标记，但不能把它暴露成新的商人类型。

## 完成标准

1. 仄和目标商人全部使用统一四结构编排，不保留商人专属解析流程。
2. 目标商人的库存、子库存、声望、任务和刷新结构均有明确支持或降级结果。
3. 一个装备可以返回多个官方商人、Offer、活动和 Manifest 提示。
4. 只有完整官方查询无结果时显示来源未知。
5. Manifest、社区内容、AI 和账号拥有均不会被错误标记为当前获取事实。
6. Offer 刷新后未经重新查询不会继续显示当前在售。
7. 统一装备详情只消费一份来源与 Offer 数据。
