# Bug #96：确认条插在清单下方把内容顶开，应改成弹框

> 状态：🟢 代码已改并自验通过（2026-09-17），待用户复验
> 现象（用户截图，原文「删除不应该是弹框吗？现在往下放这个交互体验很不好」）：
> 仓库 → 推荐来源 → 「已导入来源」里点某一行的「删除」，确认条（标题 + 说明 + 取消 / 确认）
> **插在清单下方**——清单被顶下去一截，确认条自己孤零零挂在页面底部，
> 它说的那一行还留在上面，眼睛要在两处之间来回找。

## 根因：确认块是「内容流里的一块」，不是「盖在上面的一层」

仓库里已经有一份写好的模态确认 `packages/ui/src/overlay/ConfirmationDialog.tsx`
（遮罩、把背景设为 `inert`、Tab 锁在框内、Escape 取消、关闭后焦点回到触发点、
危险动作走 `danger` 色调），并且已经在配装整理、设置页、账号页、产品外壳四处用过。
但推荐来源这一族页面当年是各写各的：确认状态存成组件里的一个变量，然后
**在内容流末尾条件渲染一个 `div`**。于是同一个「确认」动作在仓库里有两份实现，
一份是弹框、一份是把内容顶开的横条。

全仓点了一遍，这一族一共 **4 处**（都是同一个写法，都在仓库的推荐来源区域）：

| 位置 | 确认的动作 | 现在的样子 |
|---|---|---|
| `VaultRecommendationSourceManager.tsx:216` | 来源的停止 / 启用 / 删除 | 清单下方，用户截图那一处 |
| `VaultRecommendationSourceManager.tsx:380` | 来源详情里的「移除规则」 | 详情弹框内容流末尾，同样把内容顶开 |
| `VaultWishlistManager.tsx:799` | 来源管理的停止 / 按来源移除 / 移除规则 / 清空规则 | 管理面板下方 |
| `VaultWishlistManager.tsx:852` | 「移除全部来源」 | 导入区下方 |

四处的类名都是 `vault-wishlist-confirm`（其中三处叠 `vault-management-confirm`）。
只改用户截到的那一处，另外三处立刻成为「同一件事的另一份实现」——
这个仓库为这类分叉已经付过几次代价（Bug #91 就是两份清单）。

## 顺带发现：确认弹框叠在详情弹框上时，键盘会串台

来源详情里的「移除规则」确认，是**弹框之上再叠一层弹框**。两个弹框都自己往
`document` 上挂了一个捕获阶段的键盘处理：

- 详情弹框先挂上，所以它先跑。按 Escape 时它看到 `defaultPrevented` 还是 false，
  于是**把详情弹框关掉**，而确认状态还留着——确认条随即在页面上以横条形式冒出来。
- 按 Tab 时它发现焦点不在自己框内（焦点在确认框里），就把焦点抢回详情弹框，
  确认框的 Tab 锁当场失效。

这两个都是「确认框已经盖住它了，它不该再管键盘」。处置是让详情弹框在有确认框时
**交出键盘**（Escape 与 Tab 都归上层确认框），与它已有的「忙时不许关」同一条思路。

## 处置

1. 四处的手写确认条全部换成共用的 `ConfirmationDialog`，文案与动作不变；
   确认按钮文案取「确认 + 行上那个动作」，与触发它的行内按钮区分开
   （如行上是「删除」，框里是「确认删除」），避免同一个名字在页面上出现两次。
2. 来源详情弹框在有确认框时不再处理 Escape 与 Tab。
3. 顶层那一处按 **动作种类** 渲染（来源动作才在顶层渲染），
   规则动作只归详情弹框——不再靠「详情关没关」这一个条件兜着。
4. 样式表里 `vault-wishlist-confirm` / `vault-management-confirm` 的选择器全部删掉
   （四处标记都不再用这两个类名，留着就是死代码，正是 Bug #95 的教训）。

## 验证（自检，非用户要求）

行为用例（`packages/ui/test/vault-recommendation-sources-refresh.test.tsx`，从 9 条增到 12 条）：

- 点「删除」→ 出现 `role="dialog"` `aria-modal="true"` 的一层，标题「删除sayalarry」，
  说明在框内，**这层不在「推荐来源管理」区域里**（在内容流里就会落进那个区域）；
  焦点落在「取消」，框里的确认按钮是「确认删除」。
- `Escape` 取消：框消失、一份来源都没删、焦点回到刚才那个「删除」按钮。
- 「移除全部来源」→ 框内说明仍指向保留下来的那个「删除」入口。
- 「停用」→「确认停用」后当场生效。
- 详情里「移除规则」：确认框盖在详情之上；`Tab` 之后焦点仍在确认框内；
  `Escape` 只关确认框——详情还在，规则没被移除。

架构守卫（`packages/desktop/test/architecture-maintenance.test.ts`）：
两个面板里都不许再出现行内确认的类名、都必须用共用弹框、确认按钮文案必须以「确认」开头
（与行内按钮区分）；样式表里那两个类名的选择器一条都不许留。

定向改坏，每条只让对应断言变红（均已还原，`grep -rn MUTATION` 与 `find -name "*.mutbak"` 无残留）：

| 改坏 | 结果 |
|---|---|
| 详情弹框不再交出键盘（删掉 `inert` 那一句） | 叠框用例变红（Escape 把详情关掉 / Tab 抢走焦点） |
| 来源确认退回内容流里的横条 | 守卫 + 4 条行为用例变红 |
| 确认按钮改回与行内同名（「确认删除」→「删除」） | 守卫 + 删除用例变红 |
| 「移除全部来源」退回内容流里的横条 | 守卫 + 该用例变红 |

五道闸门在最终代码上全绿：`pnpm typecheck`（7 包）、`pnpm test:behavior`（145 文件 615 条）、
`pnpm test:architecture`（15 文件 77 条）、`pnpm docs:check`、`pnpm test:quality`，另 `pnpm check` 通过。

**没有做的事**：没有跑无头浏览器量尺寸（Bug #94 / #95 那种做法）。这次换的是**已经在配装整理、
设置页、账号页、产品外壳用了四处的同一个组件**，居中、遮罩、`inert`、焦点都由它自己的全局样式给出，
没有新写任何布局；弹框打开后的实际观感留给用户复验。

## 这次的教训

「确认」在一页上有两种写法（弹框、横条）时，分叉不会自己暴露——横条一样能用，
只是每次点都把内容顶一下。这类「同一件事两份实现」的代价不会以报错形式出现，
所以判定要写成「所有破坏性确认都走共用弹框 + 行内确认的类名两边都不许留」，
而不是去断言某一处的样式数值。

## 验收判据

1. 「已导入来源」里点「删除」：出现居中的确认弹框，清单**原地不动**，不被顶开。
2. 弹框里说清删的是哪一份来源、删掉会怎样；按钮是「取消」和「确认删除」。
3. Escape 与点遮罩都能取消；取消后焦点回到刚才点的那一行按钮上。
4. 停用 / 启用 / 移除规则 / 清空规则 / 移除全部来源，同样都是弹框。
5. 详情弹框里点「移除规则」时，确认框盖在详情之上，Escape 只关确认框。
6. 五道闸门全绿。

## 请用户复验

重新打包后进 仓库 → 推荐来源 → 「已导入来源」，点任一行的「删除」：
应当是页面正中弹出一个小框（标题、说明、取消 / 确认删除），**下面的清单不再被顶下去**；
按 Escape 或点框外能收回，焦点回到刚才那个「删除」。
顺带可以看一眼「停用」「移除全部来源」和详情里的「移除规则」，都应该是同一个样子的框。
