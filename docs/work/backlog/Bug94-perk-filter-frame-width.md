# Bug #94：仓库来源行里的「perk 命中」分段框撑满整栏，框内大半是空的

> 状态：🟢 已修复并自检通过（2026-09-17）
> 现象（用户截图，原文「样式不太对」）：仓库 → 浏览装备勾选来源后，每行右侧的「perk 命中」分段框
> 横跨到两个下拉之前，框里只有左边几个命中项，右边一大片空白；命中项少的行空得更多。

## 核实：把这一块按真实 DOM 与真实样式表重建出来量

这类问题只看截图容易看走眼，所以我把这些行的标记和真实样式表原样搭成一个静态页，
用无头浏览器按同样宽度渲染，直接量出尺寸：

```
来源行宽 990
分段框   x=275  宽 464   ← 整栏（1fr）被它撑满
框内内容 到 x=526 结束
空框宽度 行一 213 / 行二 267   ← 同一个列表，两行空得还不一样多
两个下拉 x=743 / x=869        ← 固定在右列，于是空框夹在中间
```

原因很直白：分段框写的是 `width: 100%`，而它所在的列是 `1fr`，所以框宽跟内容无关。
同行右侧的「位置」筛选是另一种做法——每个选项各自带边框、随内容排布，从不撑成空框。
两者不一致，才有「画歪了」的观感。

## 处置：只让框收回到自己的内容，控件一个都不挪

分段框改为**贴着自己的内容**（`width: fit-content` + `max-width: 100%`，放不下时照旧换行）。
其余位置全都不动：分段控件仍在来源名右边，两个下拉仍在右侧各自的定宽栏目里。
于是每一行读起来是「来源名 ｜ 命中项…… ｜ 两个下拉」，与同行「位置」筛选的排布一致。

另外两条路都试过，都不采纳，记在这里免得下次再走：

| 方案 | 结果 |
|---|---|
| 框撑满整栏（原状） | 就是本次要修的样子：框内大片空白，各行空得多寡不一 |
| 框收回后整组挤到右侧、紧贴两个下拉 | 已按此改过一版，用户复看后回「这样更丑啊」——一排控件忽然挤成靠右的一团 |
| 框收回后让控件跟在下拉左边连成一排（整列改成按内容排） | 各来源的命中项数量不同，两个下拉会跟着左右错位，列表里逐行对不齐 |

窄屏的连带调整：700 像素以下控件整行归它时，原先那条「把分段框拉满整行」的覆盖删掉——
贴合内容 + 自动换行本来就够用，撑满反而又造出空框。

## 验证（自检，非用户要求）

| 改坏 | 结果 |
|---|---|
| 分段框退回撑满整栏（`width: 100%`） | 架构守卫变红 |
| 分段框整组改回靠右（补 `justify-self`） | 架构守卫变红 |
| 条件行列宽从定宽改成按内容（`auto auto auto`） | 架构守卫变红 |

写守卫时先踩了自己一脚：第一版用「不含 `width: 100%`」来断定它没被撑满，
而 `max-width: 100%` 本身就含有这串字符，断言因此假红；改成按行锚定后才准确。
三处改坏均已还原，`grep -rn MUTATION` 无残留。五道闸门在最终代码上全绿：
`pnpm typecheck`（7 包）、`pnpm test:behavior`（573 条）、`pnpm test:architecture`（69 条）、
`pnpm docs:check`、`pnpm test:quality`，另 `pnpm check` 通过。

## 验收判据

1. 来源行里「perk 命中」分段框只包住它自己的命中项，框内不再留大片空白。
2. 分段控件与两个下拉的位置和从前一致，没有为了填空当挪动位置。
3. 命中项数量不同的来源行，两个下拉仍然逐行左右对齐。
4. 窄屏下分段框仍能铺开并在放不下时换行，不溢出、不截断。
5. 五道闸门全绿。
