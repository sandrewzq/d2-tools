# 仓库护甲属性筛选设计

## 1. 背景

仓库页当前已有护甲属性筛选基础，但实现仍基于旧护甲六维，并且交互是单个“护甲属性 + 最低值”控件，不能满足玩家按多项属性组合筛选护甲的使用方式。

当前游戏护甲属性已切换为新六维：

- 生命值
- 近战
- 手雷
- 超能
- 职业
- 武器

本次改动必须以新六维为唯一模型，不做旧六维兼容。

## 2. 目标

本次目标是让仓库页护甲筛选更接近 DIM 的使用节奏，但保持当前产品的中文下拉式交互：

- 用户能自由添加任意数量的护甲属性条件。
- 每条条件由“属性 + 最低值”组成。
- 所有条件默认同时满足。
- 只使用新六维属性。
- 不引入自动清理判断或完整护甲优化器。

## 3. 非目标

本次不做以下内容：

- 不做筛选预设。
- 不做比较符选择，统一按“最低值”处理。
- 不做搜索框条件语法。
- 不做旧护甲六维兼容。
- 不自动判断护甲是否应该清理。
- 不实现整套护甲搭配求解器。

## 4. 产品设计

仓库页切到“护甲”分组后，在通用筛选工具栏下显示“护甲属性筛选”面板。

每条属性条件包含：

- 属性下拉：生命值、近战、手雷、超能、职业、武器
- 最低值输入：数字，范围 0-100
- 移除按钮

面板操作：

- “添加属性条件”：追加一条空条件，不限制数量。
- “清空护甲条件”：只清空护甲属性条件，不影响搜索词、标记、锁定、部位等通用筛选。

筛选规则：

- 多条有效条件为 AND 关系。
- 空属性或空最低值不生效。
- 重复属性不报错。例如“生命值 20+”和“生命值 30+”同时存在时，实际效果等同于生命值至少 30。
- 条件只在护甲物品上生效；没有护甲属性的物品不会匹配有效护甲条件。

示例：

```text
生命值 >= 20
手雷 >= 20
职业 >= 20
```

结果只显示三项都满足的护甲。

## 5. 数据模型

共享护甲属性类型改为新六维字段：

```ts
export type ArmorStatKey = "health" | "melee" | "grenade" | "super" | "class" | "weapon";
```

展示文案固定为：

```text
health -> 生命值
melee -> 近战
grenade -> 手雷
super -> 超能
class -> 职业
weapon -> 武器
```

core 侧 Bungie stat hash 到字段的映射要同步更新。后续如果 Bungie manifest 字段名称变化，仍以当前游戏内新六维显示为产品真相。

## 6. 技术设计

实现范围主要包含：

- `packages/core/src/account/summary.ts`
- `packages/core/src/loadouts/analysis.ts`
- `packages/desktop/src/renderer/api/sharedTypes.ts`
- `packages/desktop/src/renderer/features/vault/vaultFilters.ts`
- `packages/desktop/src/renderer/features/vault/VaultFilterToolbar.tsx`
- 护甲详情、同名对比、账号页摘要等现有护甲属性展示组件

新增或调整的前端筛选模型：

```ts
export type VaultArmorStatRule = {
  stat: ArmorStatKey | "";
  min: string;
};
```

`filterVaultItems()` 接收 `armorStatRules?: VaultArmorStatRule[]`。过滤时将有效规则转换为数字阈值，并逐条判断对应护甲属性是否达到最低值。

现有单属性筛选状态 `armorStat` / `armorStatMin` 会被新的数组规则替代。排序仍保留按单个护甲属性排序和按总值排序，但排序标签也必须使用新六维文案。

## 7. 测试设计

核心测试：

- core 能从 Bungie stat hash 解析出新六维字段。
- 护甲总值按新六维求和。
- 仓库筛选能按单个属性最低值过滤。
- 仓库筛选能按多个属性最低值同时过滤。
- 重复属性条件按 AND 关系自然生效。
- 空条件不影响结果。

UI 测试：

- 护甲分组下展示“护甲属性筛选”面板。
- 面板只出现新六维中文名。
- 旧六维中文名不再出现在护甲详情、同名对比、账号页摘要和仓库筛选中。
- 武器分组不展示护甲属性筛选面板。

回归测试：

- 仓库标记、锁定、部位、弹药、框架筛选不受影响。
- 同名对比和批量选择仍使用筛选后的可见结果。
- `docs/todo.md` 同步记录本次工作的状态和后续真实账号验收点。

## 8. 风险

主要风险是 Bungie stat hash 映射错误。实现时需要通过测试夹具覆盖新六维，并在真实账号验收时对照游戏内同一件护甲确认数值。

另一个风险是旧六维字段在多个测试和展示组件里散落。实现时必须一次性替换类型、解析、展示和测试断言，避免出现新旧属性混杂。
