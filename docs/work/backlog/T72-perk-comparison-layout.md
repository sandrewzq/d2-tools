## 一、这一区现在是怎么搭出来的

展开一张来源卡后，每个槽位是一行三段：

```
.weapon-detail-source-slot        grid: [栏位 112px][来源要求 1fr][本件拥有 1fr]   ← :547
  > header                        栏位名 + 状态点 + 实色徽标（符合 / 不符 / 无法判断）
  > .weapon-detail-source-slot-comparison   display: contents（两半直接落进上面那两列） ← :560
      > section                   表头 + 条目列表；min-height 72；align-content: center ← :561
          > header                「来源要求」+「满足其中一个即可」/「本件拥有」+「蓝点表示当前启用」
          > .weapon-detail-perk-entries   flex-wrap; gap 7; min-height 50            ← :449
              > .weapon-detail-perk-entry  min-width 132; max-width 220; flex 1 1 148 ← :451
```

标记在 `packages/ui/src/item-detail/weapon/WeaponDetailContent.tsx:1219-1307`（`RecommendationSlotComparison`），
条目本身是 `WeaponPerkEntry`（T69 统一的那一个盒子，这里不动）。
两处用的都是「列表决定一行放几张」——`development.md:208` 的不变量要求这么写，
所以**问题不在条目、在列表的排布方式**。

## 三、为什么看起来乱（按证据强度排）

1. **卡片宽度不是卡片的属性，是「这一行恰好有几张卡」的属性。**
   `flex: 1 1 148px` 让每行的卡把本行宽度均分，`max-width: 220px` 再封顶：两张的均分到 220 就停住（留空），
   三张的均分 156.7，四张换行后最后一张独占一行又涨回 220。
   证据：1512 下同一行的同一栏里，`膛线枪管` 在「来源要求」是 220、在「本件拥有」是 156.7；
   `暴徒` 在「来源要求」156.7、「本件拥有」220。眼睛把宽度当结构信息读，这里宽度不携带任何信息。

2. **两半各自换行、各自垂直居中，行内首行不在同一水平线。**
   两半是各自独立的 flex 容器（`display: contents` 只把它们塞进外层栅格，互不知道对方多高），
   半区又写着 `align-content: center`（`:561`）。于是 Perk 1 行：左边 2 行 150 高、表头在 y=8；
   右边 1 行、表头被居中推到 **y=36.5**，下面留 36.5px 空。看过去像右边整块「掉下去半格」。
   单张卡只有 50 高、来源卡有 6 行，这种错位每屏出现两次以上。

3. **同一个 Perk 在同一行被画两遍，占全部卡片的 31%。**
   样本里 36 张卡有 11 张是「同一行另一侧已经画过的那一个」（暴徒、精确弹药、双击、灵魂驱散……）。
   对照本身需要两边都出现，这不算错——但当前排布下它变成了纯噪音：两张卡长得一样、宽度还不一样，
   读者要来回扫两列才能确认「这是同一个东西」。

4. **图例和词表在每一行重复。**
   一张 6 行的来源卡里，「满足其中一个即可」出现 6 次、「蓝点表示当前启用」出现 9 次（每个「本件拥有」半区一次，
   包括那些根本没有当前启用项的槽位）。同一件事还有两套说法：来源侧写「本件命中 · 当前」/「推荐候选」，
   本件侧写「符合 · 当前」/「符合」/「当前启用」/「本件拥有」——**4 个词说 2 件事**，且本件侧的这四个词是
   `WeaponDetailContent.tsx:1293-1295` 里的硬编码字符串（来源侧走 `props.sourceStatusLabels`，两边不对称）。

5. **状态信号多路叠加（这一条是规格定的，动它要改规格，先列不改）。**
   一行里同时有：4–5px 左缘实色条、栏位名前的状态点（不符时还变菱形）、实色填充徽标（符合/不符）；
   命中卡再加：绿边框 + 绿底 + 绿左条 + 绿勾 + 绿色状态字；当前启用再加：蓝点 + 蓝字。
   样本里 22/36 张卡带绿勾。规格（`equipment-details.md:93`）要求「不得只靠颜色表达状态」，
   所以这些信号不是随手加的，是执行规格的结果——**本文不改这一条**，只在第四节的方案里避免再叠新信号。

## 四、候选方案（方案 A 的几何是实测的，不是估的）

### 方案 A：两半共用同一套等宽列网格 + 两侧顶对齐（推荐）

- 列表从 flex-wrap 改成等宽列网格：`display: grid; grid-template-columns: repeat(auto-fill, minmax(148px, 1fr))`，
  条目去掉 `flex` 与 `max-width`（宽度仍由列表决定，符合 `development.md:208`）。
- 因两半等宽，列模板相同 → **两张半区的卡片落在同一组列线上**。
- 半区 `align-content: center` → `start`：两侧表头同高，余白留在半区底部而不是把内容整体推下去。
- 实测（同一份 DOM 只加这段覆盖样式）：

| 窗口 | 卡片宽度取值（现状 → 方案 A） | 表头 y（现状 → 方案 A） | 来源卡高 |
|---|---|---|---|
| 1760 | 198 / 220 → **198** | 8 / 36.5 → 8 / 8 | 850（不变） |
| 1512 | 156.7 / 220 → **156.7** | 8 / 36.5 → 8 / 8 | 850（不变） |
| 1361 | 200.8 / 220 → **200.8** | 8 / 8 → 8 / 8 | 964（不变） |
| 1024 | 198.5 / 220 → **198.5** | 8 / 8 → 8 / 8 | 964（不变） |
| 760 | 167.3 / 220 → **167.3** | 9 / 9 → 9 / 9 | 1651.5（不变） |

- 代价/边界：窄窗口下每行能放的张数由列数决定（1512 下 505 宽放 3 列），4 张候选仍会换行——
  **这一方案不降高度**（850 不变），只把「宽度跳动 + 首行错位」消掉。
- 会覆盖：架构守卫 `architecture-maintenance.test.ts:331-332` 现在钉着
  `.weapon-detail-perk-entries > .weapon-detail-perk-entry` 必须含 `min-width/max-width/flex`，要跟着改成钉列模板。

### 方案 B（可选，加在 A 之上）：两张列头合并成一张，图例上提

- 每行的「来源要求 / 本件拥有」表头（含「满足其中一个即可」「蓝点表示当前启用」）不再逐行渲染，
  改成每张来源卡一处列头 + 一处图例；行内只剩卡片。
- 实测高度收益（把两个表头隐藏后量）：来源卡 850 → **712**（1512/1760）、964 → **814**（1361/1024）、
  1651.5 → **1387.5**（760）；三行那张 408 → 345。省下的是每行 ~22px 的重复表头。
- 代价：逐行读时少了一个「这一列是什么」的就地提示；列头必须换成粘性（sticky）或每张来源卡顶部固定一行，
  否则滚到第 5 行时读者要靠记忆。**要不要 sticky 需要拍板**（详情正文区本来是 `IntersectionObserver` 管悬挂，
  多一个 sticky 头要确认不与章节导航打架）。

### 方案 C（与 A 并行，纯文案）：同一件事只说一次、只说一种

- 本件侧的状态词表不再硬编码（`WeaponDetailContent.tsx:1293-1295`），与来源侧统一到规格已有的词表
  「符合 / 不符 / 无法判断」；「本件命中 · 当前」与「符合 · 当前」并成一句。
- 「蓝点表示当前启用」从每个半区上提到来源卡一处。
- 这一条不改变几何，但直接削掉第三节第 4 条的重复；且**与规格已有的词汇表一致**（`equipment-details.md:93`
  的「保留『符合 / 不符 / 无法判断 / 来源未要求』文字状态」）。

### 不推荐：把两列合并成一列（同一 Perk 只画一张卡）

看起来能省掉 31% 的重复，但代价是把「来源要什么 ｜ 我有什么」的对照语义压进单张卡的两个布尔位，
读者要重新学会怎么读；`equipment-details.md:93` 明确写了「宽屏逐栏采用紧凑三列：栏位与结果、来源要求、本件拥有」，
选它就要改规格。**对照的两列是这个功能的卖点，不是缺陷**；本节的问题出在对齐与重复表述，不在「有两列」。

## 七、验证与验收判据（预设 + 代码写完后的实测）

1. 八档窗口（1920 / 1600 / 1360 / 1180 / 1024 / 900 / 700 / 560）× dark 下实测（脚手架 `verify-product.mjs`，
   读的是仓库里当前那份 `styles.css`）：
   - **同一半的卡片宽度取值唯一** —— 全档通过（如 1920 下 170.3px、1180 下 167.5px，同档内 0 偏差）；
   - **两半落在同一套列线上** —— 断言方式是「相对列线 = 0 + k×列距，且两半列距相等」。
     这里改过一次判据：一开始比的是两半卡片的**绝对** x，量出来必然不等（两半各自是一个栅格容器，
     起点天然差一个半区宽度），那不是缺陷。绝对坐标比不出来的东西，正是老写法真正坏掉的地方——
     老写法里两半的卡片宽度由各自内容定，同一个半区里最后一行还会被撑宽；
   - **同一行两半的首张卡 y 相同** —— Δy=0.0（现状曾是 8 vs 36.5）；
   - **栏头与槽位行同列线** —— Δx=0.0；**栏头吸附**~~在滚动口顶部 Δ=0.0~~，滚出这张来源卡后让位。
     ⚠️ 这条判据写错了：「吸附在滚动口顶边、Δ=0.0」当时是照着实现写的，而实现本身就是 bug——
     顶边已经被章节页签占了。吸附位应该是**页签底边**，见第十节修正后的量法。
   - 窄屏（≤760）两半纵向堆叠、栏头隐去、逐半区表头恢复 —— 700 / 560 两档通过。
2. 来源卡高度按第四节的实测值下降，不出现水平滚动 —— 未见横向滚动。
3. 架构守卫：钉住「列表用等宽列模板、条目不设宽度」，能被定向改坏（改回 flex 均分 → 变红）。
   守卫已从「钉 `min-width`/`max-width`/`flex` 三件套」改成钉
   `grid-template-columns: repeat(auto-fill, minmax(` + 条目只许 `min-width: 0`；
   顺带把「浮层动作按钮必须 point 得到」也钉进去了（见 T73 第〇之一节：那是个真 bug）。
4. 不回归：换 Perk、写面板、完整掉落池、T69/T70 的条目盒子与选中语义照旧。
5. 实窗复验由用户在 `light / dark × 1280 / 980 / 760` 完成——**脚手架只跑 dark，本轮自验不等于实窗验收**。
6. （2026-09-18 补）**吸附要量两相，不能只量「吸住」**：吸住相（栏头贴页签底边、无重叠、
   页签点得到）与**出界相**（被自己的列表底边推出界，页签全程仍要点得到）。后者见第十一节——
   只量吸住相正是「修完还说有问题」的原因。

> 原因是原型壳照抄了 `.app-shell`，而 `.app-shell` 是 `grid-template-rows: var(--topbar-height) minmax(0,1fr)`
> （`shell/01-chrome.css:1`，`--topbar-height: 52px`）；原型里没有顶栏这个第一个子元素，
> 正文 `<main>` 就落进了 52px 的顶栏行，再被 `.shared-item-detail-body` 的 `overflow-y: auto` 裁住。
> 现在原型壳改成 `display: block` + `overflow: visible`，并把所有 `<details>` 强制展开；
> 实例栏占位（>1360 停靠 / ≤1360 产品里变抽屉）在原型里也按同一断点处理。
> 修后实测（1600 视口）：三段首张来源卡分别 **1148×850 / 1148×850 / 1148×783**，全部完整可见，
> 页面里现场量到的数字与上表一致。
>
> 2026-09-17 再修：改完展开后整页**滑不动**（用户「没做滚动条，我不能往下滑啊」）。
> 因为产品样式里 `body { overflow: hidden }`（`foundation/02-elements.css:3`，真应用的滚动发生在
> `.shared-item-detail-body` 内部），而原型把内层滚动关掉了，于是没有任何一层能滚。
> 现在原型改成**页面级滚动**：`html { overflow: auto }` + `body.proto { overflow: visible }`——
> body 不能设 `auto`，否则 body 自己成为滚动容器、吸附表头会失去可粘的滚动口。
> 实测五档窗口（1760/1512/1280/1024/760）都能滚到末段（如 760 下 7785/7785），
> 方案 A+B+C 段的合并列头在卡片可见期间稳定贴在视口顶（`top: 0`）。
> 窄屏（≤760）两半改为纵向堆叠，原型不再报「两侧首行高差」这个不成立的量，改标「不适用」。

## 十、修正（2026-09-18）：栏头「飘到最上层」

> 来源：用户实窗截图 +「看到没，这个区域飘了，飘到最上层了」，红框圈的是吸附栏头的「栏位」格。
> 第七节把「栏头吸附在滚动口顶部 Δ=0.0」当成验收通过项——**这个量本身没错，错的是它被当成了目标。**
> 栏头吸附在滚动口顶边、章节页签也吸附在滚动口顶边，两条不透明的东西就是逐像素重合。

**成因**（不是「z-index 写小了」）：`.weapon-detail-nav`（`:270`）与 `.weapon-detail-source-slot-columns`（`:626`）
都是 `position: sticky; top: 0; z-index: var(--layer-sticky)`（=10），滚动容器同为 `.item-modal`（`07-item-detail.css:30`）。
同 `top` ⇒ 同一片像素；`z-index` 平局 ⇒ **按 DOM 顺序裁决**，栏头在来源卡里、DOM 远在页签之后，
于是栏头画在页签上面。页签那颗 `is-active` 按钮实测**点不到**（命中测试落在栏头的 `SPAN` 上）。

**改法**（`09-weapon-detail.css`）：

1. `.weapon-detail` 上新增 `--weapon-detail-nav-height: calc(var(--control-h) + 17px)`——两处让位值只此一处定义。
2. `.weapon-detail-source-slot-columns` 的 `top: 0` → `top: var(--weapon-detail-nav-height)`。
3. `.weapon-detail-instance-rail` 的 `top: 55px` → 同一个变量（55 只是 comfortable 一档的页签高，
   standard 该是 51、compact 是 49，另两档差 4~6px）。
4. `.weapon-detail-perk-entry:focus-within/:hover/[data-open="true"]` 的 `z-index` 从 `--layer-popover`(20) 收到
   `calc(var(--layer-sticky) - 1)`(9)：抬这一下只为压过兄弟条目（都停在 0），原来抬到吸附头之上，
   悬停的卡片会连浮层一起盖住页签。

**`+ 17px` 是量出来的**（真标记 + 真样式表，无头 Chromium，`measure-nav.mjs`）：

| 密度 | `--control-h` | 页签实测高 | 差 |
|---|---|---|---|
| compact | 32px | 49 | 17 |
| standard | 34px | 51 | 17 |
| comfortable | 38px | 55 | 17 |

三档都精确 +17（7+7 内边距 + 分页组上下各 1px 边框 + 1px 底边框），所以按 token 推、不写死像素。

**两臂对照实测**（`verify-sticky.mjs`，1319 / 1440 两个宽度 × 三档密度；
`before` 臂是现场注入 `top: 0` 复现修前，不是翻代码）：

| 量 | 修前 | 修后 |
|---|---|---|
| 栏头与页签重叠高 | 49 / 51 / 53px | **0 / 0 / 0** |
| 栏头顶边 − 页签底边 | −49 / −51 / −55 | **0 / 0 / 0** |
| 页签 `is-active` 按钮 | **点不到**（命中栏头的 `SPAN`） | 点得到（命中 `is-active`） |
| 悬停卡片骑在页签下缘时，压在带子里的那半 | 命中**卡片**（z 20） | 命中**页签**（z 9） |
| 实例栏顶边 − 页签底边（1440 分栏） | 写死 55 ⇒ +6 / +4 / 0 | **0 / 0 / 0** |

两个宽度都测是因为媒体查询把它切成两种形态：栏头 ≤1040 隐去、实例栏 ≤1360 变抽屉，
所以实例栏那条 `top` 只在 >1360 生效，窄宽度量不到它。

**同批扫过、确认不是问题的**：`.weapon-detail-rail-drawer-head`（`top: 0`）在抽屉自己那层里，
不是同一个滚动容器；`.weapon-detail-identity-icon` 里那张锻造叠加图虽然也写着 `--layer-popover`，
但它是 `object-fit: contain` 的装饰图，出不了图标盒。

**没动、留给用户的**：`.weapon-detail-section { scroll-margin-top: 58px }`（`:299`）是同一类写死的数字
（58 只在 comfortable 一档对得上），但改它会让章节锚点的落点位移 3~9px，属于另一件事，本轮没动。

## 十一、修正（2026-09-18，同日第二轮）：出界相里栏头照样爬过页签

> 来源：用户第二张截图 +「红框部分还是有问题」。红框还是那条栏头，帧落在**出界起点**
> （页签 → 栏头带 → 其他栏位未要求 → 折叠卡 Aegis，四段顺序与间距和脚手架渲染结果同构）。
> 第十节只改了 `top`，管的是「吸住不动」那一相——**`position: sticky` 有两相，出界那一相没修。**

**成因**：sticky 的边界是几何钳制——栏头顶 ≤ max(吸附位, 包含块底 − 栏头高)。
列表最后一行滚过吸附位之后，栏头**逆着滚动方向往上走进章节页签那条带子**。
这一段里位置躲不掉（钳制是强制的），只能靠层级；而两条的 `z-index` 都还是 `--layer-sticky`(10)，
平局按 DOM 顺序裁决，栏头在来源卡里、DOM 靠后 ⇒ 画在页签上面。
所以第十节那句「让开页签高度即互不重叠，z-index 平不平就不重要了」**只对吸住那一相成立**。

**实测**（`exit-sweep.mjs`，1440 宽，步长 8px，命中测试）：

| 滚动位 | 栏头顶 | 页签底 | 栏头压进页签带 | 页签按钮 |
|---|---|---|---|---|
| 1271（出界起点） | 78 | 79 | 1px | 点得到 |
| 1303 | 46 | 79 | 33px | **点不到**（命中的是栏头的 `SPAN`） |
| 1319 | 30 | 79 | 49px | **点不到** |
| 1343 | 6 | 79 | 73px | **点不到** |

三档密度一致（回退两条后每档各 22 个滚动位页签点不到）。

**改法**（`09-weapon-detail.css:277`）：

```css
.weapon-detail-nav { z-index: calc(var(--layer-sticky) + 1); }
```

章节页签是**窗口构件**，压在所有内容级吸附件之上——同一个惯用法见 `loadouts/03-workspace.css`
的 `.loadout-editor-head` 和 `account/03-workspace.css`。加完出界相里栏头从页签**底下**滑出去：
`after` 臂全程 0 个滚动位被盖住（`shot-exit-after.png` 对照 `shot-exit-before.png`，后者栏头把四条页签全盖住）。

**复现要回退两条**：只注入 `.weapon-detail-source-slot-columns { top: 0 }` 复现不出来——
老 bug 需要「位置平局 + 层级平局」同时成立，只回退位置的话页签照样赢，`verify-sticky.mjs` 的
before 臂会报「bug 没复现，对照不成立」（假绿）。两个脚本的 before 臂现已同步改成双变量回退。

**本轮量过、确认不是问题的**：

- 实例栏：它的包含块底边就是正文底边，滚到最底也进不了页签带（`rail-exit.mjs`，三档
  「实例栏进页签带」全 0）。护甲详情同理，且它没有内容级吸附件，所以没跟着改。
- 页签透明度：`--chrome` = `rgb(248,251,253)` 全不透明；栏头在页签背后时，页签矩形逐像素 **0 差**（`nav-diff.mjs`）。
- 栏头透明度：吸住区间内换三处背后内容，栏头矩形逐像素相同（`alpha-test.mjs`）。
- 页签高度：1050–1600 各宽度 × 三档密度都等于 `--control-h + 17px`（`sweep-nav.mjs`）。
