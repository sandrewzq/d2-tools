# 资料库命名与更新体验重设计

> 状态：Backlog
> 更新时间：2026-07-01

## 背景

当前设置页和状态栏把面向开发者的 `Manifest` 概念直接暴露给用户：

- 设置页显示“本地 Manifest”“最新 Manifest”“必要组件”。
- 顶部状态栏显示“资料库 06/30”，但这个日期来自本地缓存时间，不是资料库版本。
- 完整版本号 `244164.26.06.16.2053-2-bnet.65465` 出现在普通状态卡里，普通用户无法理解。
- Manifest 检查目前会在启动后和读取状态时触发，没有“每天自动检查一次”的持久化节流规则。

用户心智里只有“资料库”这个菜单和功能，不需要理解 Manifest、资料包、数据来源等多层技术概念。因此需要把普通 UI 收口为“资料库”，同时保留完整版本号用于设置页和诊断。

## 目标

1. 普通 UI 只使用“资料库”这一套命名，不再展示 Manifest。
2. 顶部状态栏显示资料库日期版本，例如 `资料库 2026/06/16`。
3. 设置页保留完整版本号，但字段名改成用户能理解的“当前版本 / 最新版本”。
4. 自动检查规则改为每天一次；手动检查和立即更新不受每日限制。
5. 更新失败时保留旧资料库，不让用户误以为资料库不可用。
6. 内部可以继续使用 Manifest 类型和 API，通过 UI adapter 转成资料库文案。

## 非目标

- 不改资料库菜单的核心功能。
- 不重构商人库存、活动轮换或账号读取逻辑。
- 不要求把 core 层所有 Manifest 类型重命名。
- 不删除诊断信息中的技术字段，但普通 UI 不展示 Manifest 文案。
- 不做完整多语言 copy 系统。

## 命名规范

普通 UI 使用：

- 资料库
- 资料库版本
- 当前版本
- 最新版本
- 上次更新
- 上次检查
- 更新方式
- 资料完整性

普通 UI 不使用：

- Manifest
- 本地 Manifest
- 最新 Manifest
- 必要组件
- 资料包
- Bungie 官方资料包
- 数据来源

“资料库”既是菜单名称，也是用户看到的资料数据名称。不要再拆成“本地资料库 / 资料包 / Manifest”。

## 版本展示规则

Bungie 原始版本号示例：

```text
244164.26.06.16.2053-2-bnet.65465
```

### 资料库版本

从原始版本号中解析日期段：

```text
244164.26.06.16.2053-2-bnet.65465
       ^^ ^^ ^^
       26 06 16
```

展示为：

```text
2026/06/16
```

规则：

1. 匹配 `YY.MM.DD` 日期段。
2. `YY < 80` 时按 `20YY` 处理。
3. 解析成功时顶部显示 `资料库 YYYY/MM/DD`。
4. 解析失败时顶部不展示原始长版本号，显示 `资料库 可用`。
5. 设置页仍展示完整原始版本号。

### 顶部状态栏

顶部状态栏只展示短状态：

| 状态 | 顶部文案 |
|---|---|
| 可用且版本可解析 | `资料库 2026/06/16` |
| 可用但版本不可解析 | `资料库 可用` |
| 检查中 | `资料库 检查中` |
| 更新中 | `资料库 更新中` |
| 有新版 | `资料库 可更新` |
| 未准备 | `资料库 未准备` |
| 不完整 | `资料库 需修复` |
| 本地可用但检查失败 | 继续显示日期版本或 `资料库 可用` |
| 无本地资料库且检查失败 | `资料库 不可用` |

顶部不显示完整长版本号，也不显示本地缓存日期。

## 设置页设计

设置页模块标题改为：

```text
资料库
```

副标题：

```text
装备、perk、活动和商人数据。
```

设置页展示完整信息：

| 字段 | 示例 | 说明 |
|---|---|---|
| 资料库版本 | `2026/06/16` | 从当前完整版本号解析出的日期版本 |
| 当前版本 | `244164.26.06.16.2053-2-bnet.65465` | 当前本机资料库完整版本号 |
| 最新版本 | `244164.26.06.16.2053-2-bnet.65465` | 最近一次检查到的远端完整版本号 |
| 上次更新 | `2026/06/30 11:17` | 本机成功更新资料库的时间 |
| 上次检查 | `2026/07/01 14:20` | 最近一次检查是否有新版的时间 |
| 更新方式 | `每天自动检查一次` | 固定文案 |
| 资料完整性 | `完整` / `缺失 2 项，需修复` | 替代“必要组件 8 个已就绪” |

按钮文案：

| 当前按钮 | 新文案 | 行为 |
|---|---|---|
| 重新检查资料库 | 检查更新 | 立即检查远端最新版本，不受每日限制 |
| 后台更新资料库 | 立即更新 | 立即下载并重建资料库，不受每日限制 |
| 缺组件时 | 修复资料库 | 执行完整重建 |

## 错误与降级

### Bungie 配置缺失

```text
无法检查资料库更新：请先完成 Bungie 配置。
```

Manifest / 资料库更新依赖 Bungie API Key，不依赖账号登录。普通文案只提示“Bungie 配置”，不需要解释 API Key。

### 检查失败但本地资料库可用

```text
未能连接 Bungie 检查新版。本地资料库仍可继续使用。
```

顶部继续显示资料库日期版本，不把失败暴露到顶部。

### 检查失败且本地资料库不可用

```text
未能连接 Bungie 下载资料库。请检查网络或 Bungie 配置后重试。
```

### 更新失败但旧资料库可用

```text
更新失败，已保留旧资料库。你可以稍后重试。
```

### 资料库不完整

```text
资料库内容不完整，部分搜索和解析功能可能不可用。
```

按钮显示“修复资料库”。

## 更新规则

自动检查改成每天一次。

### 自动检查入口

- 应用启动后延迟检查。
- 打开 / 刷新资料库状态时可以触发检查。
- 上述自动入口受每日检查规则限制。

### 每日检查判断

建议持久化 `last_checked_at`，按用户本地日期判断：

```ts
shouldRunAutomaticLibraryCheck =
  !last_checked_at || localDateKey(last_checked_at) !== localDateKey(now)
```

例外：

- 本地资料库未初始化：不等每日检查，允许自动更新。
- 资料库不完整：不等每日检查，允许自动修复。

### 手动操作

手动按钮不受每日限制：

- “检查更新”总是立即检查远端版本。
- “立即更新”总是立即下载并重建。
- “修复资料库”总是立即重建。

### 自动更新条件

检查完成后：

| 条件 | 行为 |
|---|---|
| 本地资料库未初始化 | 自动后台更新 |
| 资料库不完整 | 自动后台修复 |
| 最新版本 != 当前版本 | 自动后台更新 |
| 版本相同且资料完整 | 不下载，只记录检查时间 |
| 检查失败 | 保留旧资料库，记录失败状态 |
| 更新失败 | 保留旧资料库，允许稍后重试 |

## 数据模型建议

内部可以继续使用 `ManifestStatus`。UI 层增加 adapter，把技术字段转换成资料库文案。

```ts
type LibraryStatus = {
  initialized: boolean;
  status:
    | "ready"
    | "checking"
    | "updating"
    | "update_available"
    | "missing"
    | "incomplete"
    | "check_failed"
    | "update_failed";
  libraryVersion?: string;       // 2026/06/16
  currentVersion?: string;       // 完整当前版本
  latestVersion?: string;        // 完整最新版本
  lastUpdatedAt?: string;
  lastCheckedAt?: string;
  updatePolicyLabel: "每天自动检查一次";
  integrity: {
    label: "完整" | string;
    missing: string[];
  };
};
```

建议新增纯函数：

```ts
formatLibraryVersion(version?: string): string | undefined
```

以及：

```ts
toLibraryStatus(manifestStatus, backgroundTasks): LibraryStatus
shouldRunAutomaticLibraryCheck(status, now): boolean
```

## 持久化建议

当前 `checked_at` 主要来自内存状态，重启后会丢。为了支持每日检查，应持久化最近检查信息。

推荐扩展现有 metadata cache：

```ts
type ManifestMetadataCache = {
  cached_at: string;
  language: string;
  sqlite_path: string;
  metadata: DestinyManifestMetadata;
  last_checked_at?: string;
  latest_version?: string;
  last_check_error?: string;
};
```

说明：

- `cached_at` 继续表示上次成功更新资料库时间。
- `last_checked_at` 表示上次检查远端版本时间。
- `latest_version` 表示最近一次检查到的远端版本。
- `last_check_error` 用于设置页错误提示和诊断导出。

## 测试要求

必须覆盖：

1. 版本解析：
   - `244164.26.06.16.2053-2-bnet.65465` -> `2026/06/16`。
   - 空版本返回 fallback。
   - 异常版本不泄漏到顶部。
2. 每日检查规则：
   - 今天已检查时自动入口不重复检查。
   - 昨天检查时自动入口检查。
   - 未初始化和不完整时允许自动修复。
   - 手动检查 / 立即更新不受每日限制。
3. 设置页文案：
   - 不出现 `本地 Manifest`、`最新 Manifest`、`必要组件`、`资料包`、`数据来源`。
   - 出现 `资料库版本`、`当前版本`、`最新版本`、`上次更新`、`上次检查`、`更新方式`、`资料完整性`。
4. 顶部状态：
   - 显示 `资料库 2026/06/16`。
   - 不显示完整长版本号。
   - 不再把本地缓存日期误当作资料库版本。
5. 失败降级：
   - 检查失败但本地资料库完整时，资料库仍显示可用。
   - 更新失败时保留旧资料库。

## 验收标准

1. 普通 UI 不再出现 Manifest 文案。
2. 设置页“资料库”模块字段符合本 backlog。
3. 顶部状态栏使用资料库版本日期，而不是缓存日期。
4. 自动检查具备每日节流。
5. 用户手动检查和立即更新不受每日节流限制。
6. 完整长版本号仍可在设置页看到。
7. 旧资料库在检查或更新失败时不会被删除或标记为不可用。
