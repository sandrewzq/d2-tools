# Bug #89：人工推荐表格导入报「表头不受支持」，且不支持 Excel 文件

> 状态：✅ 代码已完成并变异验证（2026-09-16），待用户用自己的那份文件复验
> 现象（用户截图，v0.0.26）：在「推荐来源」页点「导入 CSV 文件」选完文件后，页面红字报
> `Error invoking remote method 'community:knowledge:import:select': Error: 武器推荐 CSV 表头不受支持：请使用中文模板（12 列）或英文模板（12 列）。`
> 用户诉求：**CSV 和 XLSX 都要能导入。**

## 一条报错，两种真实来路

现实现只按「表头逐列完全相等」认四种表头（T20 完整数据包 31 列 / 旧版普通玩家 13 列 / 统一模板中文 12 列 / 统一模板英文 12 列），**对不上就用同一句话拒绝**。用户手上那份文件属于下面哪一类，从报错里看不出来：

| 来路 | 现状 | 是不是缺陷 |
|---|---|---|
| 用户在 Excel 里维护的 `.xlsx` | 选择器只允许 `.csv`；即使选中也是按文本读二进制 → 表头当然对不上 | **是**（用户明确要求支持） |
| 上一版（v0.0.25 及更早）**导出 / 下载**的模板 | 那一版的统一模板是 **11 列**（没有「推荐来源」列，来源名写在「规则名称」列），当前代码只认 12 列 → 直接拒绝 | **是**：上一版自己产出的文件，这一版导不回来 |

第二类还带着一处**文案与实现长期不一致**：界面一直写着「11 列字段……支持 11 列模板」，而代码从 v0.0.26 起只认 12 列。用户看到的承诺与拿到的行为相反。

## 处置（四条）

1. **表格格式按文件内容识别，不按扩展名**：先看前几个字节——
   - `PK\x03\x04` → Excel 工作簿（`.xlsx` / `.xlsm`），解出**第一个工作表**再走原有链路；
   - `\xD0\xCF\x11\xE0`（OLE2）→ 旧版二进制 `.xls`，**明确告诉用户另存为 `.xlsx` 或 CSV**，而不是笼统的「表头不受支持」；
   - 其余 → 按 UTF-8 文本（CSV）读。
   **格式判定与单元格→列的映射只存在于这一处适配层**，与 T56 的单向链路一致（格式 → 解析适配 → 来源实例与规则 → 事实 → 消费）。下游仍然只看到「一张表」，指纹、校验、切分逻辑一律不动。
2. **兼容上一版 11 列模板**（中英文各一套，来源名取「规则名称」列——这正是上一版的映射）。界面承诺过的兼容性必须真的成立。
3. **行宽校验改为「与该文件自己的表头同宽」**，不再写死 12 列：否则 11 列文件即使表头认了，每一行还是会被判「该行有 11 列，要求 12 列」。表格文件里**空单元格与缺列无法区分**，所以 `.xlsx` 的行一律补齐到表头宽度（末尾空的「备注」再常见不过）。
4. **报错要能定位**：表头不受支持时带上**文件名**和**实际读到的表头**（截断显示），并说明支持哪些表头；不再让用户对着四种可能猜。

5. 真正表头不对的文件，报错里含**文件名**与实读表头。

## 残余风险 / 明确不做

- **`.ods` 与其它 zip 形态的表格**：会落到「压缩包里没有 Excel 工作表」的提示，不会误读成 CSV。
- **Excel 日期单元格**：工作表里存的是序列号，读出来是数字而不是日期文本。当前字段（武器 / 来源 / 用途 / 栏位 / 评级 / 备注）没有日期列，不做转换。
- **多工作表**：只读第一个工作表；其余工作表不提示。要支持得先有「选哪个表」的交互。
- **公式单元格**：读缓存值（`<v>`），不重算。
- **ZIP64 / 加密工作簿**：走的是「找不到 ZIP 目录记录」的损坏提示；真实用户的表格不会到这个量级。
- **导出仍只有 CSV**：用户只要求导入支持 Excel；导出用 CSV 也能被 Excel 打开。

## 对用户的代价

无。新格式是新增通道；`.csv` 的行为逐字段不变（判据 3 的回归由既有用例守着）。
