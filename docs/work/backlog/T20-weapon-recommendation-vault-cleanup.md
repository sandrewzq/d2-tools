# T20：武器推荐汇总与仓库精确清理

> 更新时间：2026-08-31
> 状态：三位置双 CSV 样表已生成，数据架构与应用接入顺序已确认
> 优先级：P1
> 范围：武器推荐资料标准化、外部数据源审计、账号实例 Roll 精确匹配、独特组合保护、仓库整理建议与 light.gg 按需复核；不直接分解游戏内装备

## 1. 背景

用户仓库存在约 1000 把武器，逐件判断第三、第四栏 Perk、枪管、弹匣、大师属性和用途成本过高。当前已有三份互补的本地武器推荐资料：

- `aegis推荐表`：原始工作簿为 `攻略/aegis推荐表.xlsx`，当前官方中文标准化目录为 `攻略/aegis推荐表_官方中文CSV/`
- `YXCRALLXY推荐表`：`攻略/YXCRALLXY推荐表.xlsx`
- `Sayalarry推荐表`：`攻略/Sayalarry推荐表.xlsx`

初步只读分析表明：

- `aegis推荐表` 包含 748 条传奇武器记录、729 个名称，并已提供 748 个明确武器 Hash。
- `YXCRALLXY推荐表` 包含 461 个武器位置、454 个名称，其中 453 个带 PVE 推荐、309 个带 PVP 推荐。
- `Sayalarry推荐表` 包含 72 条实际武器记录、70 个名称和 116 条模式配置。
- `YXCRALLXY推荐表` 与 `aegis推荐表` 有 440 个同名武器，其中 432 个至少共享一个经官方中文映射确认的推荐 Perk，404 个在第三、第四栏都存在共同推荐。
- `Sayalarry推荐表` 与 `aegis推荐表` 有 69 个同名武器，其中 68 个至少共享一个推荐 Perk。
- 三份本地推荐表共同覆盖 41 个武器，其中 38 个存在三表共同推荐 Perk，29 个在第三、第四栏都存在三表共同推荐。

这些资料足以形成高覆盖的武器推荐证据库，但不能把不同来源的单个 Perk 打散后自由排列，也不能仅按武器中文名、当前启用 Perk 或单一总分决定分解。

对社区工具和公开数据接口的补充调查还确认了以下可复用来源：

- `DIM社区推荐` 不是 Bungie 官方数据，也不是 Bungie 或 `DestinyItemManager` GitHub 组织直接维护的官方攻略；其底层 `voltron.txt` 由社区维护者 `48klocs` 的仓库维护，README 明确说明它是 DIM 默认加载的社区 Wishlist。它可以作为 DIM 生态中的默认社区推荐来源，但不能解释成 Bungie、DIM 官方编辑或玩家投票结论。
- `voltron.txt` 公开、仓库声明 MIT、可固定 Git commit，使用精确武器 Hash 和 Perk Hash。截至 2026-08-31，文件最近一次提交是 2026-08-03 的 `ce2cbcc3b3b3d4b7ebc62f2ddf0502b00f4dadfd`，提交说明为 `PvE episode 173 + bonus`；之前在 2026-07-17、2026-04-24、2026-04-18 和 2026-04-04 也有更新，说明仓库仍在维护，但没有更新 SLA。
- 当前文件约 26.7 MB，包含 255,373 条展开后的正向组合、1,234 个唯一武器 Hash，并已出现 2026 年推荐内容。它与 `aegis推荐表` 中可直接解析为单一数字 Hash 的记录重合 462 个，另有 772 个武器 Hash 不在该表中。
- `DIM社区推荐` 的 `voltron.txt` 文件级更新时间较新，不代表其中每一把旧武器都在最近提交中重新审核；应用必须区分“来源快照最近更新”和“单条推荐缺少独立更新时间”，不能把整个文件的提交时间显示为每条 Roll 的审核时间。
- `voltron.txt` 的大行数主要来自枪管、弹匣和 Perk 候选的排列展开，不能把每行当成独立投票；必须还原来源块、作者说明、用途标签和原始组合语义。
- Roll Report 的 MIT 源码可以根据官方 Manifest 本地计算第三栏、第四栏和起源特性组合的独特性；其线上 API 地址不是稳定公开协议，因此适合作为本地派生保护，不作为远端依赖。
- D2Clarity 提供按 Hash 组织的详细机制、倍率、持续时间和 PVE/PVP 差异，但公开数据库要求查看 Partnership 使用条件；未确认授权前只能预留 adapter，不打包数据。
- D2Foundry 的公开计算项目适合射程、换弹和属性派生；其 Felicity 推荐 Roll 数据最后更新时间为 2023-08-21，只能作为历史或格式参考。
- d2-additional-info 提供 MIT 的赛季、来源、任务武器和催化剂补充数据，适合构建文档和来源语义，不替代官方 Manifest。
- Checkinfo 和 D2 Arsenal 均存在可访问的 JSON 接口，但属于站点内部协议；Checkinfo 可作为开发交叉核对，D2 Arsenal 对当前样本武器 Hash 返回 404，二者都不应成为正式运行时依赖。

当前应用已经具备仓库筛选列表、同名整理、推荐数据、DIM Wishlist、个人目标、玩家标签、备注和社区推荐证据，但现有社区匹配主要按 `itemHash` 聚合，无法可靠区分同一版本下的不同账号实例；普通账号快照也主要提供当前启用 Perk，不足以完成所有可切换 Perk 的精确清仓扫描。

对当前实现的只读核对还确认了以下具体缺口：

- DIM Wishlist 当前持久化到 `dim-wishlist.json`，本地社区推荐持久化到 `local-community-recommendations.json`；SQLite 尚未承接推荐数据。
- 当前 DIM 解析器跳过所有 `//` 注释行，只读取愿望单规则行尾的 `#notes:`；`voltron.txt` 使用的 `//notes:...|tags:...` 来源块会丢失作者、用途和标签。
- 当前社区推荐服务按 `itemHash` 汇总，再由 App 转成 `Map<number, VaultItemMatchInfo>`；UI 也按 `item.hash` 读取，因此同一版本多把武器无法得到独立结论。
- 仓库列表项虽然已经接收 `communityMatch`，但当前卡片没有实际展示实例级命中状态。
- 以上问题意味着 T20 不能只生成 CSV；CSV 格式确认后仍需新增 SQLite 导入、完整 Roll 扫描、`instanceId` 级匹配和 UI 接线。

## 2. 执行结论与目标

T20 不是一个单纯的 Excel 汇总任务，也不应该一开始就修改仓库界面。主流程固定为：

```text
aegis推荐表 + YXCRALLXY推荐表 + Sayalarry推荐表 + DIM社区推荐
          ↓
CSV本地知识库 / DIM Wishlist交换文件
          ↓ Manifest校验、事务导入、异常隔离
SQLite推荐数据库
          ↓
Bungie 真实仓库完整 Roll
          ↓
Core按instanceId执行实例级匹配与安全保护
          ↓
JSON兼容TypeScript DTO / Electron IPC
          ↓
真实仓库只读报告、人工抽查与现有仓库页
          ↓
用户确认后写入本地整理状态
```

实施分为七个可独立验收的切片：

| 切片 | 做什么 | 主要产物 | 与应用的关系 |
|---|---|---|---|
| 1. 三份本地推荐表标准化 | 将 `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表` 绑定官方武器 Hash、Perk Hash 和栏位 | 两个中文知识库 CSV、异常清单、来源元数据 | 暂不改产品 UI；先证明数据准确 |
| 2. DIM社区推荐接入 | 将 `DIM社区推荐` 作为第四个独立一级来源加入同一字段合同 | 固定 revision 的 `voltron.txt` 规范化结果、DIM Wishlist 导出和来源审计 | 暂不改产品 UI；不能与三份本地推荐表混成投票 |
| 3. SQLite推荐库 | 将审核通过的 CSV 与 DIM Wishlist 经 Manifest 校验后事务导入 SQLite | 规范化关系表、导入摘要、数据指纹、旧 JSON 一次性迁移 | 推荐数据内部只查 SQLite；不保留推荐 JSON 文件作为运行时真相 |
| 4. 真实仓库只读扫描 | 读取 Bungie 完整实例 Roll 并逐把匹配 | 账号级 CSV/XLSX 扫描报告、实例级 DTO | 复用应用登录和 AccountSession；只补后台能力，不开放批量状态 |
| 5. 安全保护与严格候选 | 加入独特 Roll、锁定、配装、手动保留和异常保护 | 可解释的保留、待复查、资料不足、待处理候选 | 先真实抽查；通过前不写玩家状态 |
| 6. 仓库页面接入 | 在现有仓库页展示扫描、筛选、同名比较和原因 | 实例级扫描 ViewModel 和仓库 UI | 需要修改应用，但不重建仓库页面 |
| 7. 批量整理 | 用户预览确认后应用本地标签或安全转移 | 保留、待复查、待处理的待应用结果 | 不调用游戏分解，不自动解锁武器 |

第一版主流程只依赖 Bungie API/Manifest、四个一级推荐来源和 Roll Report 式本地独特组合保护。D2Clarity、D2Foundry、light.gg、d2-additional-info、Checkinfo 和 D2 Arsenal 全部后置，不阻塞前四个切片。

具体目标：

1. 将 `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表` 和 `DIM社区推荐` 转换为有来源、有版本、可审计、可由应用消费的结构化武器推荐库。
2. 保留每个来源的原始推荐组合和说明，不生成任何来源都没有推荐过的混合组合。
3. 使用 `itemHash + instanceId + 实际拥有的 Plug Hash` 对玩家每把武器进行实例级匹配。
4. 使用本地派生的独特组合证据保护稀有 Roll，避免“没有命中主流推荐”直接等于“没有保留价值”。
5. 输出“必留、保留、独特 Roll、待复查、待处理、资料不足”等可解释结果，帮助用户批量整理仓库。
6. 将 light.gg 作为按需复核和同分比较来源，不把不稳定的实时网页抓取作为全仓批量扫描的前置依赖。
7. 复用仓库现有三个一级视图和整理状态，只允许应用写入本地标签或执行已有安全转移，不直接分解游戏内装备。

## 3. 核心原则

### 3.1 精确身份优先

- 运行时只按官方 `itemHash` 匹配武器版本，不按中文名、英文名或近似文本匹配账号实例。
- 名称只用于离线资料解析和人工审核；解析结果进入运行库前必须绑定明确 Hash，或明确保持 `ambiguous / unresolved`。
- 同名复刻、专家版、普通版、不同赛季版本不得静默合并。
- 推荐 Perk 必须解析为属于目标武器官方 Perk 池的 Plug Hash；无法验证的名称只作为原文证据，不参与自动清仓结论。

### 3.2 保留来源组合

例如：

```text
来源 A：重建 + 诱导推销
来源 B：嫉妒军械库 + 爆炸光能
```

只能形成两个来源组合，不能自动生成：

```text
重建 + 爆炸光能
嫉妒军械库 + 诱导推销
```

同一来源在一行中明确列出的第三栏候选与第四栏候选可以按该来源原始语义匹配；涉及特定配对、触发条件或替代关系的说明必须保留原文，不从自由文本猜测新的组合约束。

### 3.3 资料未覆盖不等于可分解

- `covered_no_match`：该武器版本存在有效推荐资料，完整 Roll 已读取，但没有命中任何推荐组合，可以进入待处理候选。
- `uncovered`：所有启用的一级推荐来源均未覆盖该版本，只能显示资料不足。
- `indeterminate`：版本、完整 Roll、推荐 Hash 或来源状态无法确认，只能进入待复查。
- 任何不确定状态都不得被折叠成“未命中”。

### 3.4 推荐证据不直接替代玩家决定

- 系统可以生成只读建议和待应用整理状态。
- 玩家确认后才能写入现有“保留、待复查、待处理”本地标签。
- 应用不得调用不存在或不可逆的远程分解能力；最终分解仍在游戏内完成。
- 已锁定、精确配装实例、玩家手动保留等保护状态必须在应用待处理前复述冲突。

## 4. 数据源定位

### 4.1 一级推荐来源命名合同

四个一级推荐来源使用稳定 `source_id` 保存身份，使用固定显示名称面向玩家；原始链接按用户提供内容原样保存，不擅自精简参数或改写地址。

| 顺序 | `source_id` | 玩家显示名称 | 原始链接 | 当前本地导入或快照 |
|---|---|---|---|---|
| 1 | `aegis` | `aegis推荐表` | `https://docs.google.com/spreadsheets/d/1JM-0SlxVDAi-C6rGVlLxa-J1WGewEeL8Qvq4htWZHhY/edit?gid=346832350#gid=346832350` | `攻略/aegis推荐表.xlsx`；官方中文标准化目录为 `攻略/aegis推荐表_官方中文CSV/`；人工阅读派生目录为 `攻略/aegis推荐表_中文阅读版CSV/` |
| 2 | `yxcrallxy` | `YXCRALLXY推荐表` | `https://docs.qq.com/sheet/DYkR5enNIdUt1VFhK?tab=000001&_t=1788087335795&nlc=1` | `攻略/YXCRALLXY推荐表.xlsx` |
| 3 | `sayalarry` | `Sayalarry推荐表` | `https://sa7vp10ytxr.feishu.cn/wiki/W3ySwdahTiNRUJklJNBc0CMPnkb` | `攻略/Sayalarry推荐表.xlsx` |
| 4 | `dim_voltron` | `DIM社区推荐` | `https://github.com/48klocs/dim-wish-list-sources` | 按固定 Git commit 读取 `voltron.txt`，不把移动中的 `master` 文件当作可复现快照 |

命名和汇总规则固定如下：

- Excel、应用、报告和玩家说明只显示上述四个固定名称；`Endgame Analysis`、`d2-文本版`、`S28`、`DIM Voltron` 不再作为一级来源显示名。
- 本地文件名只是导入路径，不参与来源身份判断；即使以后移动或改名，`source_id` 也保持稳定。
- 一级来源固定按 `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表`、`DIM社区推荐` 排序。
- 来源数量只按不同 `source_id` 计数。同一来源出现多行、多个用途记录或多个作者块，最多仍只贡献一个一级来源计数。
- `DIM社区推荐` 内部的作者、标题、标签和 `//notes:` 来源块必须单独保留，但不能冒充多个一级来源或多张推荐票。
- 各来源的评级语义独立保存：`aegis推荐表` 的 Tier、`Sayalarry推荐表` 的获取优先级、作者说明和 `DIM社区推荐` 的社区 Wishlist 记录不得直接平均成统一分数。
- 只在同一来源、同一用途记录的原始语义内展开 Perk 组合；不得把不同来源的第三栏和第四栏自由拼接。
- 只有用途相同、第三栏与第四栏完全相同的组合才允许跨来源合并证据；`未标注` 不得自动猜成 PVE、PVP 或通用。合并后列出所有支持来源，并按不同 `source_id` 计算来源数量。
- 人工表的用途只允许 `PVE`、`PVP`、`通用`、`未标注`；“终局”“首领输出”“高难”“切枪”等属于使用场景或说明，不作为用途枚举。

### 4.2 来源能力与边界

| 来源 | 主要用途 | 不应解释为 |
|---|---|---|
| `aegis推荐表` | 武器版本 Hash、Tier、用途、推荐栏位、伤害与打法说明 | 玩家手中具体 Roll 的最终结论 |
| `YXCRALLXY推荐表` | 广覆盖的 PVE/PVP 第三四栏推荐和中文实战评价 | 可直接机器推断情绪与强度的自由文本评分 |
| `Sayalarry推荐表` | 模式、枪管、弹匣、第三四栏、起源特性、大师属性、获取优先级和备注 | 与 `aegis推荐表` Tier 等价的纯强度评级 |
| `DIM社区推荐` | DIM 默认加载、由 `48klocs` 社区仓库维护的精确 Hash Wishlist 聚合 | Bungie 官方推荐、DIM 官方编辑结论、255,373 次独立投票，或不经来源块还原的全局总分 |
| 用户 DIM Wishlist | 用户主动导入或订阅的愿望单组合 | 系统官方推荐或自动覆盖玩家偏好的全局评分 |
| Roll Report 本地派生 | 第三四栏与起源特性组合的独特性、相似武器数量 | 强度推荐、当前环境元数据或专家 God Roll |
| d2-additional-info | 赛季、来源、任务武器、催化剂和官方资料库补充关系 | 玩家 Roll 推荐或账号事实 |
| D2Clarity | Perk、异域与模组的倍率、触发、持续时间和 PVE/PVP 机制说明 | 未确认 Partnership 条件即可打包的开放数据，或推荐结论 |
| D2Foundry / Oracle | 射程、换弹和属性派生计算 | 当前专家推荐源；历史 Felicity Roll 不参与当前共识 |
| Checkinfo / D2 Arsenal | 开发阶段的中文定义、来源别名、Perk 池和接口结果交叉核对 | 有第三方 SLA 的运行时主数据源 |
| light.gg | 社区使用、流行组合、单件复核和同分参考 | 稳定 API、专家共识或全仓实时批量真相 |
| 玩家标签与个人推荐 | 玩家最终偏好和已确认知识 | 可被外部数据自动覆盖的临时状态 |

四个一级推荐来源不得直接取平均。`aegis推荐表` Tier、`Sayalarry推荐表` 获取优先级、`DIM社区推荐` 来源块、作者实战说明、独特组合数量、机制数据和社区流行度分别保存、分别展示，只在派生置信度中记录不同 `source_id` 的数量和完整组合命中情况。

外部数据源按以下级别管理：

| 级别 | 来源 | 使用方式 |
|---|---|---|
| 官方事实 | Bungie API、Manifest | 武器与 Perk 身份、插槽、属性、账号实例和来源事实的唯一权威 |
| 批量推荐 | `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表`、用户显式启用的 `DIM社区推荐` | 生成标准推荐库和仓库批量匹配 |
| 本地派生保护 | Roll Report 独特组合算法、D2Foundry 计算 | 本地执行，不依赖第三方在线服务 |
| 条件扩展 | D2Clarity | 确认 Partnership / 授权后用于机制说明 |
| 开发核对 | Checkinfo、D2 Arsenal | 只做人工或开发交叉检查，不进入运行时依赖链 |
| 按需复核 | light.gg | 用户主动打开单件或同名组后查询并缓存 |

### 4.3 DIM社区推荐身份与时效性

- 玩家显示名称：`DIM社区推荐`
- 来源仓库：`https://github.com/48klocs/dim-wish-list-sources`
- 原始文件：`https://raw.githubusercontent.com/48klocs/dim-wish-list-sources/master/voltron.txt`
- 身份：非 Bungie 官方、非 Bungie 数据；由社区维护，但仓库 README 明确将其定义为 DIM 默认加载的 Wishlist。
- 许可：仓库声明 MIT；正式使用仍需保留来源、作者块和许可信息。
- 当前固定候选 revision：`ce2cbcc3b3b3d4b7ebc62f2ddf0502b00f4dadfd`，提交时间 2026-08-03，核对时间 2026-08-31。
- 时效性结论：仓库仍活跃，文件级时效性较好；单条推荐新鲜度不统一，旧记录可能跨版本保留，且没有官方更新 SLA。
- 产品定位：只作为第四个独立推荐证据；命中可以支持保留或待复查，未命中不能单独支持待处理。
- 展示要求：同时显示固定 revision、文件抓取时间、作者/来源块和缺少单条更新时间的警告，不把文件更新时间冒充每条推荐的审核时间。

账号 OAuth Token、Cookie 和私有库存不得发送给任何第三方工具；账号数据只通过本应用直接调用 Bungie 官方接口读取。外部来源只接收公开 `itemHash / perkHash` 或不包含账号身份的查询。

## 5. 标准推荐库

### 5.1 推荐结构

建议建立版本化的运行时数据结构：

```ts
type WeaponRecommendationDataset = {
  version: 1;
  generated_at: string;
  manifest_version: string;
  sources: RecommendationSourceMetadata[];
  weapons: Record<string, WeaponRecommendationRecord>;
  issues: RecommendationResolutionIssue[];
};

type WeaponRecommendationRecord = {
  item_hash: number;
  official_name_zh: string;
  official_name_en?: string;
  release_label?: string;
  recommendations: WeaponRecommendationEvidence[];
};

type WeaponRecommendationEvidence = {
  id: string;
  source_id: string;
  source_record: string;
  mode: "pve" | "pvp" | "general";
  source_tier?: string;
  acquisition_priority?: string;
  barrel_hashes?: number[];
  magazine_hashes?: number[];
  perk_column_3_hashes: number[];
  perk_column_4_hashes: number[];
  origin_trait_hashes?: number[];
  masterwork_names?: string[];
  author?: string;
  tags?: string[];
  note?: string;
  uncertainty_flags: string[];
};

type RecommendationSourceMetadata = {
  id: string;
  label: string;
  source_type: "local_file" | "git_snapshot" | "official_api" | "derived" | "on_demand";
  source_url?: string;
  license?: string;
  retrieved_at: string;
  revision?: string;
  content_fingerprint: string;
  redistribution_status: "allowed" | "local_only" | "permission_required" | "unknown";
};
```

字段名称可以在实现时按现有 Core 命名习惯调整，但必须保持以下事实：

- 来源记录不可丢失。
- 第三栏和第四栏不可合并成无栏位的大集合。
- 原始作者说明与官方中文实体分开保存。
- 正常版、强化版等多个 Plug Hash 只有在目标武器官方 Perk 池中可验证时才共同进入候选。
- 无法解析、同名多版本并列和原始数据异常必须进入 `issues`，不能静默忽略或猜测修正。
- GitHub Raw 来源生成正式推荐库时必须固定具体 commit SHA，不能只记录会移动的 `master / main / live` URL。
- `DIM社区推荐` 内部 `voltron.txt` 的 `//notes:` 来源块、标题、作者、用途标签和后续排列必须保留关联；展开行数不参与来源权重。
- 外部响应不能直接写入最终推荐库，必须先保存原始快照、完成 Hash 与插槽校验，再生成规范化记录。

### 5.2 产物

第一阶段同时生成：

1. 应用消费的机器可读推荐库，例如 `weapon-recommendations.v1.json`。
2. 供人工检查的两个 UTF-8 BOM CSV：`武器列表.csv` 和 `Perk推荐组合.csv`。
3. 单独保存异常的 `武器推荐_未解析与异常.csv` 或 CSV 目录。
4. 数据源 URL、许可、固定 revision、文件指纹、Manifest 版本和生成时间摘要。
5. 外部数据源原始快照清单与规范化统计，不把未授权原文复制进公开产物。
6. 表头和数据稳定后，如仍需要单文件人工审核，再从两个 CSV 一键生成双 Sheet XLSX；XLSX 不作为数据真相或当前迭代必需产物。

运行时推荐库优先进入 `packages/services/src/community` 的只读来源边界；确定性匹配规则进入 `packages/core`。若第三方资料没有明确再分发授权，生成结果只保存在用户本地数据目录，不打包进仓库、安装包或公开发布物；实施前必须记录来源和授权状态。

## 6. 匹配规则

### 6.1 实例输入

每把账号武器至少需要：

```text
itemHash
instanceId
当前启用 Plug Hash
该实例实际拥有的可切换 Plug Hash
锁定状态
位置与装备状态
精确配装引用
玩家本地标签
```

定义池中的候选 Perk、角色级或账号级已解锁 Perk不得冒充该实例实际拥有的 Roll。

### 6.2 来源命中

对每条来源推荐分别计算：

- `full_match`：实例实际拥有的第三栏至少命中一个候选，第四栏至少命中一个候选。
- `partial_match`：只命中第三栏或第四栏。
- `no_match`：两栏均未形成完整组合。
- `indeterminate`：实例完整 Roll、来源 Hash 或栏位归属无法确认。

枪管、弹匣和大师属性作为独立增强匹配项：

- PVE 首轮可以第三、第四栏完整命中作为核心判断，枪管、弹匣和大师只提高解释完整度。
- PVP 待处理结论必须结合来源已提供的枪管、弹匣和大师信息；无法完成这些字段的精确比较时降级为待复查。
- 不使用单一不可解释的总分隐藏上述差异。

### 6.3 派生置信度

| 条件 | 派生状态 |
|---|---|
| 三份本地推荐表完整命中 | 本地三表命中 / 必留候选 |
| 两份本地推荐表完整命中 | 本地双表命中 / 保留候选 |
| 一份本地推荐表完整命中 | 本地单表命中 / 建议保留 |
| `DIM社区推荐` 完整命中 | 社区愿望单命中；与三份本地推荐表分别展示 |
| 只有部分栏位命中 | 待复查 |
| 主流推荐零命中但组合独特 | 独特 Roll / 待复查保护 |
| 本地来源完整命中且 light.gg 支持 | 社区支持，不改变原始来源事实 |
| 本地资料不命中但 light.gg 命中 | 来源冲突 / 待复查 |
| 版本已覆盖且所有来源零命中 | 待处理候选 |
| 版本没有资料 | 资料不足 |

### 6.4 严格清仓模式

用户可以显式选择严格模式。只有同时满足以下条件才生成“建议待处理”：

```text
推荐资料覆盖当前 itemHash
+ 完整实际 Roll 已读取
+ 没有完整命中任何启用来源组合
+ 没有来源冲突或未解析状态
+ 未锁定
+ 不是精确配装实例
+ 没有玩家手动保留
= 建议待处理
```

默认模式可以把同样结果先标为“待复查”，由用户在确认规则和误判率后切换为严格模式。

### 6.5 同版本去重

- 只在相同 `itemHash` 内比较账号实例。
- 按 PVE 清怪、PVE 输出、PVE 功能、PVP 等来源明确表达的模式保留覆盖，不强制同版本只留一把。
- 一把 Roll 只有在另一实例完整覆盖其所有已确认用途，且另一实例至少多出一项高可信用途时，才可以标记为“同版本有更优”。
- 不能只按推荐来源数量、光等或当前启用 Perk判断支配关系。

### 6.6 独特组合保护

- 使用当前资料库在本地计算第三栏 + 第四栏，以及 Perk + 起源特性组合在其他武器上的可出现数量。
- 独特性只表达“组合少见或仅此武器可出”，不表达强度、模式或当前环境价值。
- 主流推荐零命中但存在唯一或低重复组合时，结果从待处理降级为“独特 Roll，待复查”。
- 独特组合阈值、比较范围和过滤条件必须显示，例如同武器类型、同框架、同弹药或全武器池，不能只显示一个无解释的稀有分数。
- 计算逻辑参考 Roll Report 的公开 MIT 实现，但使用本应用当前 Manifest 和稳定 Socket 分类重新实现，不调用其未公开部署地址。

## 7. 完整 Roll 扫描

当前账号普通快照包含 `ItemSockets`，适合展示当前启用 Perk，但不包含完成全仓精确整理所需的全部实例可切换 Perk。已有物品详情和 Armor Planner 使用 `ItemReusablePlugs` 的能力可以作为实现基础。

推荐新增用户主动触发的“精确武器扫描”：

1. 使用一次账号 Profile 请求读取全仓所需的 `ItemReusablePlugs`，避免对约 1000 把枪逐件请求详情。
2. 只将来源包含 `instance` 的实际拥有项纳入完整 Roll；排除只来自 `character / profile / manifest` 的候选和解锁项。
3. 按账号、资料库版本和实例 Roll 指纹缓存扫描结果。
4. 普通启动继续使用紧凑账号快照，不因清仓功能永久增加所有页面的数据负担。
5. 扫描未完成、部分失败或缓存版本不一致时，只显示当前启用初筛，不生成待处理结论。

## 8. light.gg 接入策略

### 8.1 当前能力

项目已经存在 AI 联网读取 light.gg 单件页面、解析推荐组合并按 `itemHash` 缓存的实现，但默认批量社区匹配不启用该来源。

当前环境直接访问 light.gg 武器页、`robots.txt` 和条款页会被 Cloudflare 返回 403，因此本任务不得依赖直接批量爬取上千个页面。

### 8.2 推荐定位

light.gg 只用于：

- 单源命中时的额外复核。
- 两把同版本 Roll 难以取舍时的社区流行度参考。
- 三份本地推荐表未覆盖的新武器或新版本。
- 玩家主动打开单件详情或同名组后发起查询。
- 用户确认后保存为已有“我的推荐”外部知识。

light.gg 不用于：

- 应用启动时扫描全部武器。
- 把网页流行度直接解释成专家最优组合。
- 覆盖本地双表或本地三表已经确认的推荐事实。
- 未经授权的长期批量抓取或公开再分发。

### 8.3 精确校验

现有 light.gg AI 解析需要在进入清仓流程前收紧：

- AI 返回的 `itemHash` 必须与当前武器一致。
- 返回的 Perk Hash 必须属于该武器官方 Perk 池。
- 名称只允许官方中英文精确匹配，不允许 `includes` 模糊包含。
- `hash: 0`、无法验证的名称和纯文本 AI 推断不得参与实例匹配。
- 缓存必须记录来源 URL、读取时间、资料库版本和解析警告。
- 若未来获得稳定、明确允许使用的 API 或数据导出方式，再单独评估批量更新；不在本任务中假设其存在。

## 9. 应用架构边界

### `packages/core`

- 推荐库 schema、规范化结果和解析问题类型。
- 按实例执行的确定性组合匹配。
- 来源命中、覆盖状态、置信度、保护冲突和同版本支配关系。
- 不读取本地文件、不联网、不直接访问 SQLite。

### `packages/services`

- 三份本地推荐表、固定 commit 的 `DIM社区推荐` 快照及其他已授权来源的本地读取、版本和缓存。
- 推荐库导入、来源状态、原始快照审计和 light.gg 按需 adapter。
- d2-additional-info 等 MIT 补充数据按固定 revision 读取；D2Clarity 在许可确认前只保留接口占位和来源状态。
- 第三方来源授权不明确时只保存到用户本地数据目录。

### `packages/app`

- 仓库扫描 workspace、进度、错误、筛选和实例级结果 ViewModel。
- 将 `Map<itemHash, VaultItemMatchInfo>` 式版本聚合扩展为实例级结果，避免同版本一把命中后所有实例都显示“社区同款”。
- 保留现有标签、Wishlist、装备目标和配装引用的独立事实。

### `packages/ui`

- 继续复用仓库的筛选列表、同名整理和推荐数据三个 `tabpanel`。
- 不新增平行仓库页面或第二棵产品 DOM。
- 系统建议与玩家整理状态分开展示，不自动改变玩家状态。

### `packages/desktop`

- 接入用户主动触发的完整武器扫描、缓存和最小 IPC。
- 复用现有 AccountSession、Profile 请求、资料库和物品详情能力。
- 不在 renderer 直接读取推荐文件、SQLite 或网页。

本任务将跨越 `packages/core`、`packages/services`、`packages/app`、`packages/ui` 和 Desktop IPC，实施时属于共享高冲突改动，应按阶段串行集成，不与仓库页面、账号快照、推荐服务或武器详情的大型改造并行修改同一公共文件。

- 单源命中
- 部分命中

### 10.3 同名整理

- 只在同一版本内比较具体账号实例。

- 显示每个来源的原始组合、命中情况、评级语义、说明和更新时间。

- 提供“使用 light.gg 复核”按需操作；读取失败不影响本地推荐显示。
- 外部结果经用户明确确认后才允许保存到“我的推荐”。

## 11. 实施切片

### 切片 1：三份本地推荐表标准化

目标是先证明推荐资料本身准确，不修改产品 UI。

- 固化 `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表` 的解析规则、原始链接、本地输入路径和来源元数据。
- 使用当前中英文 Manifest 校验官方武器 Hash、Perk Hash、栏位和版本。
- 保留每个来源的原始组合、评级、打法说明、伤害分析和异常标记，不跨来源拼接。
- 保留 `Sayalarry推荐表` 的 `待测试`、`？` 和无法确认项，不猜测修正。
- 生成 `weapon-recommendations.v1.json`、`武器列表.csv`、`Perk推荐组合.csv` 和未解析异常清单；当前迭代不生成 XLSX。
- 完成门槛：所有参与自动匹配的记录都有可追溯来源、明确 Hash 和栏位；其余记录只进入异常清单。

### 切片 2：DIM社区推荐第四来源

目标是扩大覆盖率，但保持其社区来源身份和时效性边界。

- 固定具体 commit SHA、抓取时间、文件指纹和许可，不读取会移动的 `master` 结果作为不可追溯运行数据。
- 解析标题、描述、`//notes:` 块、作者、标签、用途和正向组合。
- 使用官方 Socket 将展开行还原为枪管、弹匣、第三栏、第四栏和其他 Plug；排列数量不作为投票权重。
- 支持普通与强化 Perk 的官方可验证对应关系。
- `DIM社区推荐`、用户导入的 DIM Wishlist、三份本地推荐表和玩家个人推荐保持独立来源身份。
- Trash List 默认禁用；负向规则不能在第一版成为待处理依据。
- 完成门槛：推荐库可以分别回答“哪份本地推荐表命中”和“`DIM社区推荐` 的哪个内部作者/来源块命中”，不能只输出混合总分。

### 切片 3：真实仓库只读扫描

目标是验证推荐库能否精确匹配用户约 1000 把真实武器；开始复用应用后台能力，但仍不开放产品批量操作。

- 复用现有 Bungie 登录、AccountSession 和完整 Profile 读取，一次取得全仓 `ItemReusablePlugs`，不逐把请求第三方网站。
- 使用 `itemHash + instanceId + 实际拥有 Plug Hash` 形成实例 Roll 指纹。
- 在 `packages/core` 实现完整命中、部分命中、零命中和不确定；在 `packages/services` 加载推荐库和扫描数据。
- 输出账号级 CSV/XLSX 报告，列出武器实例、来源覆盖、完整命中组合、缺失条件和原因。
- 第一轮只输出“保留、待复查、资料不足”，不输出自动“待处理”。
- 完成门槛：同一 `itemHash` 的不同实例得到独立结果，扫描失败或 Roll 不完整时不会被归为零命中。

### 切片 4：安全保护与严格待处理候选

目标是在真实数据上验证误判边界，再允许系统产生只读的待处理候选。

- 加入 Roll Report 式独特组合保护，并显示比较范围和其他可出武器数量。
- 加入锁定、精确配装引用、玩家手动保留、版本冲突、来源冲突和解析异常保护。
- 只在当前 `itemHash` 有可靠覆盖、完整实际 Roll 已读取、所有启用来源零命中且没有任何保护冲突时产生“待处理候选”。
- 对本地三表命中、本地单表命中、`DIM社区推荐` 独立命中、覆盖零命中、资料不足和来源冲突分别进行真实仓库抽查。
- 完成门槛：人工抽查确认规则后才能进入仓库 UI；在此之前不写本地标签，也不开放批量严格模式。

### 切片 5：接入现有仓库页面

目标是把已经验证的扫描结果接入应用，不重建仓库页面。

- `packages/app` 增加实例级扫描 workspace、进度、错误、筛选和结果 ViewModel。
- `packages/ui/src/vault` 在现有推荐数据、筛选列表和同名整理中显示来源、组合、原因和保护冲突。
- 单件详情显示每个独立来源的原始组合和命中情况；light.gg 只保留用户主动发起的按需复核。
- `packages/desktop` 仅补充完整扫描、缓存和必要的最小 IPC；renderer 不直接读取文件、SQLite 或网页。
- 系统建议与玩家整理状态分开展示，不因扫描完成自动改变标签。
- 完成门槛：用户可以筛选并解释每个实例为何保留、复查、资料不足或成为待处理候选。

### 切片 6：用户确认后的批量整理

目标是复用应用已有本地标签和安全转移能力，帮助执行整理决定。

- 推荐保留的实例可由用户确认后写入“保留”。
- 不确定、来源冲突和独特 Roll 写入“待复查”。
- 严格满足条件的候选只有在结构化确认后才能写入“待处理”。
- 批量操作最多写本地整理状态或执行已有安全转移；不调用游戏分解，不自动解锁，不覆盖玩家手动保留。
- 完成门槛：所有写入都有预览、数量、保护冲突和撤销/恢复边界；最终分解仍由用户在游戏内逐件确认。

### 后置扩展：不阻塞第一版

- D2Clarity：确认 Partnership / 授权后补充机制详情。
- D2Foundry Oracle：补充射程、换弹和属性派生；历史 Felicity 推荐不参与当前共识。
- light.gg：只用于单件或同名组按需人工复核。
- d2-additional-info：补充赛季、来源、任务武器和催化剂关系。
- Checkinfo、D2 Arsenal：只作为开发核对，不成为产品运行时依赖。

## 12. 验收标准

- `aegis推荐表`、`YXCRALLXY推荐表`、`Sayalarry推荐表` 均可生成结构化推荐记录，输出数量、来源和异常可以人工追溯到原文件位置。
- `DIM社区推荐` 可以按固定 commit 生成可复现快照；来源块、作者、用途标签和组合排列关系不会在解析中丢失。
- `voltron.txt` 展开行不会被错误计算为独立来源票数，用户 Wishlist 也不会与系统启用的 `DIM社区推荐` 静默合并。
- 每条参与自动匹配的武器和 Perk 都有明确官方 Hash；未解析项不参与待处理判断。
- 普通与强化 Perk 的兼容命中必须有官方可验证关系，不通过名称相似度猜测。
- 不产生任何来源都没有表达过的跨来源混合组合。
- 同名不同版本不会因为名称相同而共享推荐结论。
- 同一 `itemHash` 下每个 `instanceId` 得到独立匹配结果，不因另一把实例命中而显示相同结论。
- 完整扫描只使用该实例实际拥有的 Perk，不把资料库候选或账号解锁项冒充实际 Roll。
- 扫描不完整时不生成待处理结论。
- 本地三表、本地双表、本地单表、`DIM社区推荐`、部分命中、覆盖零命中、资料不足和来源冲突均有明确、可筛选、可解释状态。
- 默认模式不自动写标签；严格模式只有用户显式启用并确认后才填充待应用状态。
- 锁定、精确配装实例和玩家手动保留在待处理应用前触发结构化冲突确认。
- 唯一或低重复 Perk 组合会触发“独特 Roll”保护，并显示比较范围和其他可出武器数量。
- 独特性、Clarity 机制数据和 Foundry 属性计算不会被解释成专家推荐票数。
- 外部来源均记录 URL、许可、revision、读取时间和指纹；授权不明确的数据不会进入公开发布物。
- light.gg 失败、不可访问或返回无法验证的数据时，四个一级推荐来源的本地结果和仓库整理仍可正常工作。
- 应用不直接分解装备；批量操作最多写本地整理状态并复用已有安全转移流程。
- 推荐数据、筛选列表、同名整理和单件详情继续消费真实账号数据，不引入 mock Roll 或平行仓库页面。
