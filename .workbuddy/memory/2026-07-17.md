# 2026-07-17

- 复核 `docs/work/references/desktop-framework-comparison.md` 并只读对比当前 Electron 主线与 `origin/tauri2-rebuild`。
- 确认 Tauri 分支是 clean-slate 重建而非简单换壳：相对当前主线涉及 388 个文件，约新增 9,620 行、删除 38,253 行；当前 Electron 主进程约有 85 个 IPC handler，而 Tauri 底座只有 12 个 Rust command，绝大多数产品能力尚未迁回。
- 技术路线判断：个人 Vibecoding 场景下继续 Electron + Node.js + TypeScript 更合适。Tauri 会额外引入 Rust/Cargo、MSVC/Windows SDK、WebView2、capability、updater 与签名发布双轨；当前真正性能瓶颈是大型 Definition JSON、IPC 大对象和重复 Bungie 请求，应优先推进 T6 的 SQLite 按需查询、紧凑账号快照和请求去重，而不是更换桌面框架。
- 若未来重新评估桌面框架，应由安装包、打包版内存、启动时间等硬指标触发，并采用保留现有 TypeScript 业务层的小型壳层 PoC，禁止再次 clean-slate 重写。
- 补充评估 Wails v2：Windows 开发环境比 Tauri 简单，主要是 Go、Node/npm 与 WebView2，通常不要求 Rust/Cargo 或 MSVC C++ 工具链；但 Wails 后端必须使用 Go，当前约 85 个 Electron IPC 及 Node 文件、worker、OAuth、更新能力仍需改写或桥接。因此 Wails 适合作为未来轻量壳层 PoC 候选，不适合作为当前主线迁移目标。
- 截至 2026-07-17，Wails v3 已存在且持续开发，但仍是 Alpha 预发布；最新查到 `v3.0.0-alpha2.117`（2026-07-08），官方明确警告可能有 Bug 或未完成功能。当前稳定正式版本仍为 Wails v2.13.0（2026-07-06）。正式产品应选 v2，v3 仅适合实验或 PoC。
- Wails v2 未来可迁移到 v3，但不是普通依赖升级：v3 重做了应用初始化、窗口/生命周期、runtime、事件、bindings 和构建系统。若从 v2 开始就把 Wails API 限制在 `cmd/desktop`、`internal/platform/wails` 和前端 platform adapter，保持 React UI、Go 领域服务、SQLite/HTTP/OAuth 独立，则正式版 v3 后可把升级控制为桌面壳适配；若业务和页面到处直接调用 v2 runtime，升级会接近壳层重构。
- 补全 Wails v3 功能评估：d2-tools 的 React UI、Go HTTP/SQLite/OAuth、后台任务、窗口菜单托盘、NSIS/签名/文件关联/单实例均可实现，没有核心业务硬缺口。主要风险是 v3 仍为 Alpha；内置 updater 采用整包下载并原地替换 EXE，不等同于 NSIS 安装器升级，未见 Electron blockmap 差分更新，且受安装目录写权限影响。OAuth token/AI key 的运行时安全存储也需自行接 Windows Credential Manager、DPAPI 或 Go keyring 库。
- 分析 MaaNTE/MXU 作为架构参照：MaaNTE 本体是 MaaFramework PI v2 资源项目 + Python Agent + Pipeline/模板/模型，并携带嵌入式 Python；外部 GUI MXU 是 Tauri + Rust + React/TypeScript，不是 Wails。该项目能采用 Tauri 的原因是业务自动化主要隔离在 Python/MaaFramework 后端，GUI 只是通用薄客户端，不能直接证明 d2-tools 适合换壳。
